# P20 第 1 步：放置的离线上限（bound）

Claude Code，2026-10-22。纯离线，没有跑模拟。脚本在 `scripts/`，数据在 `bound.csv`（每个 workload 一行，列名见下）/ `bound.json`。

- **数据**：(a)(c)(d)(e) 用 P19 的 W = 128 主配置 baseline（`9e87ac5`，384 GB/s、`-rdma-max-outstanding=128`，`-report-pgcls` 的精确聚合：每页、每个读者、每 512 B 的 L1V 读数和重读数）；MoE 的 W = 128 baseline 还没跑完，用 pgcls 的 W = 256 baseline（`149dff0`）。(b) 要时间信息，用 pgcls 的 W = 256 baseline 原始 trace（按页哈希采 1/16 的页，这些页的全部访问）。页类别用 `pgcls/scripts/pgcls_page.py` 在同一批数据上重新分类。
- **口径**：1 次远程读 = 1 条 L1V line 读由别的 GPM 服务（baseline 下一次往返）；读×跳 = 远程读 × 曼哈顿跳数。只算读（这批数据没有按子块的写，pass 1 会补 `-pgcls-place-ext`）。保留（M3+）的模型和 pgcls 的 R_retain 相同：同一 GPM 重读（本 kernel 内，或更早 kernel 读过且之后没被写）不再上网。路由先 Y 后 X，链路负载 = 回复（owner → 读者）经过的链路。"主要使用者" = 读得最多的 GPM（并列时不动）。中心 tile 24 是 CPU，不放数据。
- 脚本：`place_bound.py`（每个 workload：各放置策略后的远程读、读×跳、带保留的版本、最忙 owner 份额、最忙链路、搬运量）、`place_stability.py`（(b)）、`place_bound_agg.py`（汇总）。

## 0. 结论

1. **(a) 热点页：拆到中心周围比整页放中心好，但要拆得够散**。只看读×跳，拆分和整页放中心一样（0.60–0.78，都是"离大家近一点"），省读次数要靠保留 / 复制（4 份副本 0.28–0.41）。拆分的作用是**分散 owner 和链路**：
   - 热点原来集中在一个角落 owner 的 workload（PR、MM、npbcg、atax、FW；owner 份额 1.0）：整页放中心只把最忙链路降到 0.23–0.71，最忙 owner 仍是 0.44–1.0；k = 4（tile 17/23/25/31 各 1 KB）降到 0.17–0.24、owner 0.25；**环 12**（每页 4 个 1 KB 块轮流放到离中心 ≤ 2 跳的 12 个 tile）降到 **0.11–0.20、owner 0.09**，比 4 份副本（0.17–0.29）还低。
   - 热点原来就分散在很多 owner 上的 workload（sssp、IVF、embbag、LUD、npbis、bfs、ar；owner 份额 0.02–0.11）：任何"往中心放"都会**把链路负载集中起来**（整页放中心 ×1.6–7.7，k = 4 ×1.4–2.8，环 12 ×0.9–1.8）。
   - k = 2 和 k = 4 的读×跳一样，k = 2 的 owner / 链路分散得更少。**结论：热点页用"环 12"（k = 4 块，散到 12 个 tile），不用 k = 2；对热点本来就分散的 workload 收益可能为负，由第 2 步的时序结果判断。**
2. **(b) 最优位置在 kernel 之间几乎不变**：私有放错 + 流式的 1 KB 块，相邻 kernel 换主要使用者的比例在 22 个有数据的 workload 里有 20 个是 0；**例外 MG**（0.74，其中一半是来回，按 kernel 动态跟随反而读×跳 ×2.6）和 bfs（0.02）。按 10 µs 窗口看会抖（MT 0.92、embbag 0.32、PR 0.23、FW 0.20，来回占 15–86%），只有 FW（0.75）和 PR（0.91）跟随窗口划算，其余不划算（动态÷静态 1.0–1.9）。**在线版应该按 kernel（或更长）决定位置、并且钉住来回迁的块，不要按微秒级窗口迁。**
3. **(c) 搬运量**（P-按类 v2，一次性搬）：私有放错和热点为主的 workload，搬运的 line×跳只占 baseline 读×跳的 0–13%、是省下的 0–14%（KM 0.06、fft2d 0.12、FW 0.06、PR / MM / tc / npbcg ≤ 0.02、CFD 0.14）。**流式和读得少的不划算**：MT 1.37、embbag 1.37、PA 0.96、ar 0.86、MoE 0.71、SPMV 9.0、gups 1.02（搬运 / 省下的；每条 line 只读一次，搬一次和远程读一次差不多）。所以流式只有"分配时就放对"（oracle / 首次触碰）才有收益，在线迁移不值得。
4. **(d) 页大小**：整页放置的效果随页变大迅速消失：KM 读×跳 4 KB 0.06 → 64 KB 0.61 → 2 MB 0.96；fft2d 0.02 → 0.06 → 0.12；CFD 0.11 → 0.49 → 0.62；PA 0.02 → 0.06 → 0.46；MoE 0.08 → 0.10 → 0.21；MT 0.67 → 1.00 → 1.01。1 KB 子块放置和页大小无关（KM、fft2d 0，MT 0.27，CFD 0.08）。**这是"子块放置"的主要理由：大页下页级放置基本无效。**
5. **(e) 按类策略合起来**（都叠加保留 M3+；P20 的 14 个 workload 平均，剩下的读×跳 / baseline）：只保留 0.42；P-按类 v1（私有放错、流式 1 KB 子块，热点环 12，其余不动）+ M3+ 0.16；**P-按类 v2（热点环 12，其余所有页 1 KB 子块给主要使用者）+ M3+ 0.13**（25 个平均：0.46 / 0.27 / **0.24**）。v1 在 CFD（0.27 对 0.07）、MG（0.25 对 0.09）、BH、npbis、i2c、shocsort 上明显差：这些 workload 的"亲和 / 随机 / 自己反复读"页其实也有一个主要使用者，放给它再加保留更好。**第 2 步的 P-按类 用 v2**（分类只用来找热点页）；v1 只作离线对照。
6. 远程读（不是读×跳）剩下的比例：只保留 0.43，P-按类 v2 + M3+ 0.17（P20 的 14 个平均）；剩下的主要在 IVF（0.64）、embbag（0.46）、MT（0.51：页内各块的读者交错，1 KB 也不够细）、sssp（0.27）、CFD（0.12）。

**第 2 步据此的调整（报告主会话）**：P-按类 = v2（热点页环 12 拆分，其余页 1 KB 子块给主要使用者）；"热点拆分砍不砍"按 P-按类 对 P-按类-中心（热点整页放到读者加权最优 tile，其余同 v2）在 5 个热点 workload 上的 GMEAN 判断。

- `R_<策略>` / `H_<策略>`：剩下的远程读 / 读×跳（相对 baseline）；`Rret_` / `Hret_`：再叠加保留；`own_`：最忙 owner 的远程读份额；`link_`：最忙链路负载 / baseline；`mig_`：搬运 line×跳 / baseline 读×跳；`migsaved_`：搬运 / 省下的读×跳。
- 策略：`none`、`page`（整页给主要使用者）、`sub1k`（1 KB 子块给主要使用者）、`center`（整页放读者加权最优 tile）、`k2` / `k4` / `ring`（所有页按热点方式拆；只作对照）、`rep4`（热点页 4 份副本，tile 8/12/36/40，每个读者读最近的一份）、`cls_k2` / `cls_k4` / `cls_ctr` / `cls_ring` / `cls_hotnone`（v1：私有放错、流式 1 KB 子块；热点按后缀；其余不动）、`sub_ring`（**v2**：热点环 12，其余 1 KB 子块）、`page64k` / `page2m`（按物理页号 16 / 512 页一组整组放置）。
- `hotH_` / `hotown_` / `hotlink_`：只动热点页、只统计热点页。`share_<类>`：该类占远程读。`stab_<kernel|window>_<P_classes|hot>_<chg|pp|dyn>`：(b) 的换位置比例、来回比例、动态÷静态读×跳（含搬运）。

## 补充（主会话审核 10-22）：热点页只在"原来集中"时才搬到环 12

- **规则**：一个 workload 的热点广播页里，最忙 owner 服务的远程读份额 ≥ **0.3** 才把热点页拆到环 12；否则热点页留在原 owner（其余页照样 1 KB 子块给主要使用者）。阈值按表 A：集中的 workload 0.63–1.0（PR、MM、npbcg、atax、FW 1.0，tc 0.63），分散的 ≤ 0.11（sssp 0.08、IVF 0.11、embbag 0.04、LUD 0.03、npbis 0.06、bfs 0.08、ar 0.02），0.3 落在中间的空档里。第 2 步的放置表（`scripts/server/mktable.py`）按这条规则生成。

## 补充（用户 10-22）：主要使用者 vs 访问者中心（"med"）

- **med**：每个 1 KB 块放到它所有访问者（按读加权）的曼哈顿加权中位 tile（`best_tile`，不含中心 tile 24）；热点广播页和 v2 相同（集中的拆到环 12，分散的不动）。私有块（主读者占绝大多数）的中位就是主读者，所以私有放错、自己反复读两类和 v2 完全相同。数据 `bound_med.csv`（逐 workload）。
- **结论**：
  1. 差别只在**多个访问者真正共享的块**（随机共享、轮转广播、写共享、亲和）：med 读×跳更低（随机共享 0.53 对 0.58，加保留 0.39 对 0.43；轮转广播 0.63 对 0.81；写共享 0.76 对 0.98），但**远程读次数略多**（随机共享 0.63 对 0.60）——放到中位以后，原来的主要使用者也要走网络。
  2. 最忙链路：med 往往更集中（embbag 1.55 对 1.17，gups 3.39 对 1.37，spmv 2.62 对 1.53；25 个平均 0.62 对 0.50），因为中位点倾向于落在 mesh 中部，很多块挤到相同的几个 tile。LUD 相反（0.94 对 1.38）。
  3. 合起来（含 M3+）：P20 的 14 个平均读×跳 0.147 → 0.138、远程读 0.174 → 0.176；25 个 0.256 → 0.232 / 0.274 → 0.279。在 P20 的 workload 里只有 BH（0.070 → 0.065）、embbag（0.476 → 0.378）、IVF（0.638 → 0.625）有差别，CFD、sssp、FW、tc 几乎不变。
  4. 主配置下瓶颈是往返次数和 owner / 链路排队（不是链路字节），所以"远程读略多、读×跳略少、链路更集中"的 med 不一定更快，要看第 2 步的时序结果（med、med + M3+：CFD、BH、embbag、sssp、IVF，加 FW、tc 作对照）。
