# M1-wafer 分析：和 wafer 有关的 RDMA 端机制，上限统计和原型评估

Claude Code，2026-10-22。场景：**384 GB/s、W = 256**（`-bandwidth=24 -switch-buffer-flits=16 -rdma-max-outstanding=256 -t18-window=256 -t18-compose-table-entries=512`），新基线 `c08698b`（`isca27/fix-l2tlb-wakeup`），8 个 workload。按用户 10-22 的决定，48 GB/s 不再跑，旧二进制（`e714d47`）的上限统计只作参考。加速比 = T(v4complete) / T(变体)，大于 1 表示变快。数据见 `speedup.csv`、`runs.csv`、`bound_summary.csv`（全部列在 `bound_c26d97e.csv`）、`mech_stats.csv`、`verify.csv`。

## 0. 结论

1. **上限统计**：v4 之后还剩的跨 GPM 共享集中在 PR、graphtc、MM 三个 workload 上，都是角落热点 owner；其余 5 个基本没有。
   - 拐点 hub 能合并的需求 line（已核实合并点时间）：PR 0.29、tc 0.17、MM 0.08；其余不到 0.05。
   - 理想网内合并：PR 0.68、tc 0.51、MM 0.40；其余不到 0.2。
2. **W = 256 下窗口不再是瓶颈**（窗口满的时间只占 0–20%，MM、npbcg、bfs 接近 0），所以"省窗口位"一类的机制空间很小：
   - hold 批能省 28–75% 的事务；
   - 在 owner 处释放窗口位等于把窗口放大 3–4 倍；

   但实测时间只变化 ±2%（只有 ar 有 +8%）。
3. **原型的最好结果：拐点 hub（自适应）+ hold（只在窗口半满以上时 hold）**，GMEAN 1.023（8 个 workload），单项最大：
   - ar 1.07、tc 1.05、bfs 1.04；
   - 没有一个变慢超过 0.5%（npbcg 1.000、sssp 0.996）。
   - 各部件单独的 GMEAN：拐点 hub 1.008（PR 1.06、bfs 1.045、tc 1.03；sssp 0.95、ar 0.985）；hold100o 1.017。
   - 区域 hub（q2，在途合并，相当于不带保留的 HMG 式区域 home）0.846：单个 hub 成为热点，加上绕路的代价。
4. **判断**：在新基线、384 GB/s、W = 256 下，RDMA 端的 wafer 机制只能再挤出约 2%，值不值得作为新的 M1 贡献要由用户决定。论文里可用的论点：
   - "按路由拐点合并"零绕路，并且在共享多的 workload 上真的省了 owner 的工作；PR 的 hub 合并率 0.43，tc 0.25。
   - 但代价是一次中转（实测约 7%），只有共享足够多时才划算，所以需要自适应。

### 3.1 拐点 hub 为什么在 PR、tc、bfs 上有用，在 sssp、ar 上有害

hub 实测的合并率（hub 收到的 line 里，接到另一请求方已在途表项上的比例，`mech_stats.csv`）：

| workload | 合并率 | 转发往返（hub→owner→hub） |
|---|---|---|
| PR | 0.43 | 1,317 ns |
| tc | 0.25 | 970 ns |
| MM | 0.21 | — |
| ar | 0.11 | — |
| npbcg | 0.06 | — |
| sssp | 0.05 | — |
| bfs | 0.03 | — |
| CFD | 0.00 | — |

- **合并率高**（PR、tc、MM）：合并的读不用再去 owner 了，角落 owner 的事务少了，排队也就短了。PR 的 hub 转发往返 1,317 ns，比直连的平均往返 2,839 ns 短，所以快了 6%。
- **合并率低**（sssp、ar、CFD）：只剩一次中转的代价，所以变慢 1–5%。graphtc 上关掉合并（hub 表只留 1 项）、只转发的诊断运行是 0.93×，说明中转本身大约多花 7%（请求和响应各多经过一次 hub RDMA 的流水线和队列）。
- **bfs 合并率只有 0.03，却快了 4.5%**（重复一次结果完全相同）。可能的原因是：经过 hub 以后，同一列的请求在 owner 行上的注入被串行化了，于是 owner 端的拥塞反而下降。这个原因没有核实。
- **区域 hub（q2）变慢**：
  - 绕路平均 1.4–2.1 跳；
  - 每个区域只有一个 hub，一个 GPM 要转发 12 个 GPM 的远读。CFD、ar 这种均匀流量的 workload 下，hub 成了热点，CFD 0.60×、ar 0.63×。
  - 只有 PR（1.064）这种几乎全部读同一个 owner 的 workload 能赚。

### 3.2 自适应

- 做法：请求方对每个 owner 有一个 4 位计数器。hub 的响应里带一位（或一个计数）"这次有 line 是合并来的"；有合并就加 8，没有就减 1，低于 8 时直连。直连期间每 16 个事务仍然走一次 hub，用来重新探测。
- 效果：消掉了 sssp（0.948→0.999）、ar（0.985→1.001）、CFD 的损失；但 PR 的收益也从 1.059 掉到 1.011，因为 PR 的直连比例变成 0.58。
- 原因：建表的第一个请求方永远看不到合并，所以计数器会被拉低。如果改为按 hub 的整体合并率来判断（比如由 hub 广播一个"本 hub 合并率高"的标志），可能更好，但没有做。

### 3.3 hold

- 省的是事务和窗口位，但 W = 256 时窗口本来就不缺：
  - tc：事务数 226K→146K，窗口满的时间比例 0.118→0.007，平均在途 77→48；
  - 时间只快了 1.8%。
- 只有 ar 明显快了（+9%）。ar 的流量是均匀的、每页多条 line，hold 让 owner 端的事务减少 63%，owner 也就不那么忙了。
- sssp 变慢 8%：窗口几乎是空的（在途 35 / 256），hold 只是平白增加了延迟。所以改成 `hold100o`：在途数不到窗口一半时不 hold。这样 sssp 0.92→0.996，MM 不再 hold（在途数只有 5），ar 仍然有 1.078，bfs 1.052。按距离 hold（holdrtt25，0.25 × RTT）比固定 100 ns 差：远处 hold 得更久，延迟增加得更多。

## 4. 开发过程中发现的问题（已修）

1. **hub 把单 line 也打成位图转发**（`c26d97e`）。owner 的位图路径要拆包，拆包期间整个入口都被挡住。结果 hub 转发的往返约 2.3 µs，而直连只要 1.5 µs：tc hubturn 0.76×，q2 0.84×，hubturn 的 GMEAN 0.94。修正：单 line 用普通的 line 读转发（`97fdca5`）。修正后 tc 是 1.03×，hubturn 的 GMEAN 1.008。`c26d97e` 的 hub 结果已作废，没有出现在上表里。
2. **hub 和 RDMA 共用 ToOutside 的 FIFO**：hub 的请求和转发回来的响应会排在 owner 请求后面（有队头阻塞）。改为 hub 用独立的端口 `M1WHub`（`bce2b0a`）。单独看只有 tc 从 123.8 µs 降到 121.3 µs，主要的问题是第 1 条。
3. **W = 256 时 baseline 走 T18 的独立请求方路径**，上限统计漏了这一路的钩子，旧二进制的 baseline 统计全是 0。已修（`859a6a1`）。
4. **上限统计里 path（理想网内合并）高估**：只检查了"发出时对方还在途"。已改成在对方完成时核实时间（`859a6a1`）。

## 5. 和相关工作的区别（详见 DESIGN 第 4 节）

- q2（区域 hub）加保留就是 HMG 的 GPU home，加上 Proxies / VH 那一类的区域代理；实测还更差（单点热点 + 绕路）。如果要用它，只能作为对照，并且要回应 Kurian HPCA'14：我们的数据正好说明区域大于 1 时，绕路和热点的代价超过了合并的好处，除非 hub 按地址交错（那就是 HMG）。
- 拐点 hub 的新意在于"合并点由路由决定"：
  - 零绕路；
  - 只合并在途的请求，不要目录，不缓存数据；
  - 用 Little 定律的说法：被合并的读少跑一次远往返，owner 的在途事务也少一个。

  实测效果只在共享集中的角落热点 workload 上明显（PR +6%、tc +3%），平均 +1%。

## 6. 没做的 / 局限

- 只跑了 8 个 workload、384 GB/s、W = 256。25 个 workload 的对照在 `~/akita-exp-test/pgcls/`（不是我跑的），没有用到。
- hub 表默认 1024 项；ar、tc 有 0.1–1.5 万条 line 因为表满没有跟踪（`untracked`）。没有扫描表的大小。
- 自适应只试了一种参数（+8 / −1，阈值 8，每 16 次探测一次）。
- hub 的保留（`-m1w-hub-retain-ns`）实现了，但没有跑：它就是区域缓存（HMG 式），和 M3 / A1 重叠。
- bfs 在 hub 下变快的原因没有核实。
- 8 个 workload 的上限统计用的是 `c26d97e`，那时 hub 还是有 bug 的版本。但上限统计只看 v4complete 和 baseline，和 hub 的实现无关，所以结果有效。
