# pgcls：每类访问模式的最佳搬运方式，以及值不值得针对它优化

Claude Code，2026-10-22。新基线 `c08698b`（二进制 `149dff0`），主配置 384 GB/s、W = 256，25 个 workload。数据、代码和校验见 `README.md`。表都由 `scripts/pgcls_aggregate.py` 生成。

- v4_complete 对 baseline：GMEAN **1.315×**（25 个，逐个见 README 表 1）。
- 占比：25 个 workload 的量加在一起算（`class_summary.csv`；逐 workload 的在 `class_traffic.csv`）。延迟 = RDMA 收到 L1 请求到回复 L1 的时间总和。"v4 已吃掉"按 baseline 的页类别对齐：1 − v4 的网络读 line（含预取）/ baseline 的远程读。
- oracle = 这一类页的 L1V 访问全部改走请求方自己的 L2 / DRAM，在 v4_complete 上做；只对占该 workload 远程读 ≥ 5% 的类跑。有效 = WG 数相同、指令数差 ≤ 1%、且没有 < 0.95× 的异常（§5）。逐 workload 的数在 `oracle.csv`（`*` = 无效）。

**建议**：
1. **热点广播是最大的一类**：占 baseline 远程读延迟的 2/3，v4 之后仍占剩余延迟的 1/3。v4 已经把它的读次数减到副本上限附近（78% vs 75%），再省读次数没用。剩下的是"每个 GPM 第一次读 + 每个 kernel 重读"仍然要去角落的 owner：做法是**热点小数据放到中间或复制几份**（dm 的 A4：4 份副本让最忙链路负载 ×0.15）加跨 kernel 保留（A1）。预期 PR、sssp、ivf、ar、tc 上 1.2–2.1×，GMEAN 上限约 1.25×。
2. **私有放错第二**：v4 只吃掉一半的读、19% 的延迟，迁移 / 按页放置能省 88% 的读。预期 KM、FW 约 2.4×，fft2d 1.3×，GMEAN 上限约 1.4×（7 个 workload）。和 pm/ 一致：**按类开迁移**（只迁私有放错页，不迁热点广播页）。
3. **流式**：搬运本身省不掉。MT 的页被多个 GPM 各读不同的 line（页级伪共享），按 512 B 子页放置能省 66% 的读；ar、PA、MoE 要靠更早发出（预取 / 批量拷贝），不在"放置"范围内。
4. **亲和、轮转广播、写共享、自己反复读**：每类只在 1–3 个 workload 上有 > 10% 的 oracle 收益，不值得各做一个机制；"自己反复读"可以由 A1 一起覆盖。
5. **按页分类有意义**：25 个里 13 个是混合的（最大类 < 80%：npbcg 78% 热点广播 + 21% 自己反复读，FW 24% 热点广播 + 76% 私有放错，CFD / MG 各 4 类）。见 §2。

## 1. 分类方法（每页一次，baseline 全运行的精确统计）

每页（4 KB 物理页）的读者 = 读过它的 GPM（含 owner 自己的本地 L1V miss）。按顺序判断：

1. **写共享**：≥ 20% 的读读到"同一个 kernel 内被另一个 GPM 写过的 line"。读到更早 kernel 别人写的 = 生产-消费，不算写共享（特征 `prod_cons`）。
2. **广播**：每条被读的 line 平均有 ≥ 8 个 GPM 读（line 级）。10 µs 窗口内平均 ≥ 4 个读者、且在 ≥ 3 个窗口里被读 → **热点广播**；否则（读者轮流来）→ **轮转广播**。
3. **私有**：主读者占这页 ≥ 90% 的读，或每条 line 平均 ≤ 1.2 个读者（页级伪共享）。主读者是 owner → owner 为主。否则看主读者（伪共享页看所有远程读者）：每条 line 平均读 < 2 次 → **流式**；重读里跨 kernel 的 ≥ 50% → **自己反复读**；否则 → **私有放错**。
4. 其余（2–8 个读者共享 line）：读者两两平均 ≤ 3 跳 → **亲和 / 区域**，否则 → **随机共享**（随机两个 GPM 4.7 跳）。

阈值在 `scripts/pgcls_page.py` 开头。修正过一次：第一版按页级读者数判断广播，把 MT 这种"很多 GPM 各读页里不同 line"的页算成了广播；改成 line 级后 MT 归为流式。oracle 页表在修正后重新生成（已经跑的 gups、lud 页表没变）。

各类特征见 `class_features.csv`（按远程读加权）：line 级读者数、主读者占比、读者两两跳数、10 µs 内并发读者、窗口间 Jaccard（固定伙伴）、被写比例、生产-消费比例、同 GPM 重读比例、子块读者不同的比例。

## 3. 上限：每页选最合适的做法 vs 每个 workload 只用一种（`bounds.csv`）

数字是 baseline 远程读剩下的比例（越小越好；纯离线，不含时序）。

- 单一做法（保留 / 放置 / 复制 / 子页放置里最好的一种）和"每页选最好的一种"差别大的：FW 0.18 → 0.07，npbis 0.30 → 0.14，bfs 0.55 → 0.34，embbag 0.61 → 0.46，MG 0.25 → 0.21，shocsort 0.14 → 0.09。其余由一种做法决定（热点广播 = 保留 / 复制，私有 = 放置）。
- "按类选做法"（`R_rule`）在 CFD、MG、BH、i2c 上比单一做法差：这些 workload 的随机共享 / 亲和页按规则"不动"，但保留（A1）对它们也有用。真正好的组合是"**保留（A1）对所有页 + 放置 / 迁移只对私有放错页**"（`R_place_retain`：MG 0.12、i2c 0.11、FW 0.04）。
- 热点广播：复制的上限和保留相同，v4 已经做到。

## 4. 子页放置（A3）的潜力（`a3_subpage.csv`）

- 页内各 512 B 子块的最优位置不同、且子页放置比整页放置省 ≥ 10% 读×跳的页，占远程读：MT 70%、embbag 48%、KM 43%、spmv 21%、MoE 20%、BH 18%、CFD 14%、FW 11%、fft2d 10%（shocsort 100%，但远程读很少）；其余 ≤ 8%。
- 读×跳（子页 / 整页放置）：KM 0.50、shocsort 0.59、embbag 0.75、MT 0.81、fft2d 0.85、CFD 0.90；其余 ≥ 0.93。
- A3 对"页级伪共享"的私有 / 流式数据（MT、KM、embbag）有用，对热点广播和随机共享没用。512 B 和 1 KB 差别不大，2 KB 明显变差（MT 0.70 → 0.34）。

## 5. oracle 运行的有效性

- 每个 oracle 和同配置不加 oracle 的运行比 WG 数和指令数（T15 规则：指令数差 ≤ 1%）。oracle 让多个 GPM 在各自 L2 里缓存同一页，被写的页会读到旧数据，可能改变控制流：
  - **bfs**：私有放错、流式、全部本地的 oracle 指令数 −8.3%（5.8–6.9×，不可信）；热点广播、随机共享的 oracle 有效（+0.4% / +0.6%）。
  - **ivf** 全部本地：指令数 +1.6%，标 `*`，不进全部本地的 GMEAN。
  - **npbis**：所有 oracle 要么崩溃（LDS 读越界，`aluds.go:85`，被写的数据读到旧值），要么 WG 数 −81%：**npbis 的 oracle 全部缺失**（热点广播 73%、流式 11% 两类没有结果）。
  - **shocsort 随机共享**：指令数一致，但慢 6.3×（0.159×）：写密集，本地 L2 里大量脏副本，是 oracle 自身的病态，不进 GMEAN。
  - FW 指令数差 0.02%，算有效。
- 没跑 oracle 的 (workload, 类)：占比 < 5% 的（如 MoE 亲和 3.5%、embbag 流式 4%、ivf 随机共享 3%）。
- **yss3 上 6 个 exit ≠ 0 的运行**全是 npbis：`npbis-or-hotb`、`npbis-or-strm`（v4）和 `npbis-or-all`（v4 / baseline）崩溃（上面的 LDS 越界）；另外 2 个是 `npbis-or-all-or-all`（下一条的重复运行）。
- **脚本 bug（已修，结果不受影响）**：`analyze_srv.sh` 把已完成的 `-or-all_mi200` 运行也当成 baseline 分析，`mkoracle.py` 于是又排了 `-or-all-or-all` 运行（两台共 70 个，等于 `-or-all` 重跑一遍，浪费机时）。这些运行和 json 没有用到（服务器上移到 `analysis_bad/`）。

## 6. 采样误差

分类和上限用的是精确聚合，不采样。原始 trace 按页哈希采 1/16 的页；只用采样页估计各类远程读占比的误差（`sampling_error.csv`）：93 个 (workload, 类) 里中位数 0.6 个百分点、90 分位 6 个百分点、最大 24 个百分点（FW：几个热页正好没被采到）。页数少、流量集中在少数热页的 workload（FW、atax、npbcg、npbis）误差大；以后用原始 trace 做时间相关分析时，这类 workload 要提高采样率或按流量加权采样。

## 7. 局限

- npbis 没有有效的 oracle；bfs 只有两类有效。
- oracle 是"本地 L2 / DRAM"，不是零代价：对热点广播相当于每个 GPM 一份副本，对私有放错相当于迁到读者。
- 新基线如果再改 benchmark，访问模式基本由算法决定，结论预计不变；需要时按 bfs、npbcg 和一个改过的 benchmark 抽查。
