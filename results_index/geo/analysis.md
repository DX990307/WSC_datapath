# geo-push / affinity-push 分析（10-21，分支 `isca27/geo-push` @ `106dc0d`；旧基线二进制，正式数字待新基线重跑）

> 由主会话根据 geo 会话的最终汇报落成。数据文件：`geo.csv`、`bound.csv`、`affinity_w256b384.csv`（rc = −15 的行是被停掉的，不要用）、`coread/`。

## 结论

- **不建议把"地理广播"本身作为新的 M2。** 收益来自少数热点在角落的 workload（PR、MM、graphtc），相当于把热点数据就近复制给几乎所有读者——热点本身是放置规则造成的，和 A4"热点放中间或复制"是一回事。
- **W 变大后缩水**：PR 的 geo1s 在 W = 64 是 1.14，在 W = 256（384 GB/s）只剩 1.025。
- 如果保留，只能写成"共享感知推送（shared 过滤）"，作为 M3 的补充（M3 管同一 GPM 的再读，推送管别的 GPM 的首次读）。只有 geo1s 在两个场景都不亏（384 GB/s、W = 64：1.074；48 GB/s、W = 256：1.033）。
- **affinity-push**：只有 CFD 有固定伙伴，CFD 的运行被停掉、没有结果；PR 上比 v4 慢 3–4%（PR 是广播型，没有固定伙伴）。
- 噪声：重复运行中只有 bfs 有 ±1.5% 的波动（来源是 benchmark 先 enqueue 再拷贝，新基线修复）。

## §5 新基线上建议重跑

- 配置：v4、geo1s、aff2s、aff1，加 geo1 作上界；同样 8 个 workload；场景 w256b384 和 w256b48m。
- CFD、allreduce 加 `-report-coread-matrix`，确认 affinity 学到的伙伴就是共读矩阵里的伙伴。
- 关键：CFD 上 affinity 能否把 0.017 的用到率提上去；W = 256 下热点 workload 的推送收益还剩多少。
