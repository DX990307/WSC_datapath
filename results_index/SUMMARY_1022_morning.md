## 2. 每类访问模式值不值得优化（`pgcls/analysis.md`）

| 类 | baseline 远程读 / 字节×跳 / 远程读延迟的占比 | v4 已去掉（读 / 延迟） | 最佳做法 | v4 + 该类变本地的 GMEAN 上限（有效数） |
|---|---|---|---|---|
| **热点广播** | 34% / 40% / **68%** | 78% / 82% | 每个读者一份副本（读数上 v4 已接近上限，剩的是延迟） | **1.25×**（12）：PR 2.12、sssp 1.63、IVF 1.51、allreduce 1.29 |
| **私有放错** | 20% / 17% / 9% | 55% / **19%** | 迁移到主读者（上限省 88%） | **1.39×**（7）：KM 2.48、FW 2.36、fft2d 1.33、MoE 1.11 |
| 流式 | 16% / 15% / 8% | 40% / 12% | 只能合并打包；MT 可子页放置 | 1.17×（4） |
| 随机共享 | 12% / 12% / 6% | 62% / 34% | = v4 | 1.09×（9） |
| 亲和 / 区域 | 7% / 6% / 3% | 71% / 32% | 放到伙伴中点 | 1.02×（6） |
| 自己反复读 | 5% / 4% / 3% | 58% / 30% | 跨 kernel 保留（A1） | 1.09×（3） |
| 轮转广播 | 3% / 3% / 1% | 55% / 16% | 产生后整块多播 | 1.09×（2） |
| 写共享 | 3%（只有 gups） | 17% / 10% | — | 1.70×（1） |

结论：**值得做的是热点广播（剩下的是延迟：第一次读和每个 kernel 的重读还要去角落 owner）和私有放错（v4 几乎没碰）**；其余类各自只影响 1–3 个 workload，不值得单独做机制。13/25 个 workload 是混合的，分类要按页。

## 3. A1 与 M3 规则修正（`a1/analysis.md`）

| 配置 | 对 v4 | 对 baseline |
|---|---|---|
| v4 + A1（跨 kernel 保留只读） | 1.005 | 1.322 |
| v4 + 首次触碰准入（ft2） | 1.017 | 1.337 |
| v4 + A1 + 边界清除"自己写过→不可缓存"标记（reset） | 1.021 | 1.343 |
| **v4 + A1 + reset + ft2** | **1.049** | **1.379** |

- A1 本身几乎没用：9 个 workload 在模拟窗口里只有 1 个 kernel；npbcg / MG 网络 line 大降但 W = 256 下不受窗口限制。
- 真正的 M3 问题是两条规则：**两次触碰才保留**（PR、MM、graphtc 等第二次取占网络 line 13–48%）和**本 GPM 写过的远程 line 永久不可缓存**（KM 100%、fft2d 79%、FW 64%、MG 53%、CFD 49%）。
- 全部合用：KM 1.65×、FW 1.27×、CFD 1.10×、graphtc 1.09×、bfs 1.07×、PR 1.05×；sssp −2.4%（ft2 造成，ft1 不变慢）、fft2d −1.3%。v4 + A1 + reset + ft1 正在补跑。
- KM 的 `-verify` 在所有配置（含 baseline）都失败，是 benchmark 自身问题。

## 4. M1 的 wafer 相关改进（`m1w/analysis.md`，8 个 workload）

| 配置（相对 v4） | GMEAN |
|---|---|
| **拐点合并（自适应）+ 条件延迟发批** | **1.023** |
| 条件延迟发批（在途过半才等 100 ns） | 1.017 |
| 路由拐点合并（自适应） | 1.009 |
| 一直延迟 100 ns | 1.007 |
| 区域汇聚点 q2（HMG 式） | 0.846 |

W = 256 下窗口满的时间只有 0–20%，省窗口位的机制没有空间；合并只在角落热点（PR、graphtc）上有空间。拐点合并不绕路、只合并在途，和 HMG / Proxies / HDPAT 不同，但收益只有约 2%。

## 5. 新基线是否可靠

- 原来挂住的 384 GB/s 运行在 `c08698b` 上都跑完：v3c384 MG M1+M2、W = 256 的 MG baseline / v3_complete（48 GB/s 的 shocsort、atax、LUD Complete 也已跑完）。修复前的二进制（`527d483`）上 bfs v4_complete 又挂了一次，新基线上没有。
- 确定性：bfs-s18e2 baseline 3 次都是 710.806589 µs，sssp 2 次都是 416.019 µs；pgcls 的开 / 关 / 原版逐位一致。
- fir：修复前 26.568 µs → 新基线 26.314 µs（IOMMU 移到中心）。

## 下一步建议

1. **Complete 的新组合**：v4 + M3 修正（reset + 首次触碰准入）≈ 1.38×；M1 拐点合并 + 条件延迟只多 2%，可作为小加分项。
2. **针对热点广播**：热点小数据放中间 / 复制，或者让第一次读和跨 kernel 重读不再去角落（上限 1.25×）。
3. **针对私有放错**：只对私有放错的页做访问计数迁移（上限 1.39×）；page migration 的新基线重跑（v4 + c4k）在跑，可以验证。
4. 还在跑的低优先级实验：page migration（c4k，50 个）、geo-push（16 个）、A1 + reset + ft1（25 个）。
