# 数据搬运方向的机会上限：字节×跳数、重复搬运与共享、压缩

Claude Code，2026-10-21。数据来源和文件说明见 `README.md`。这里只做离线分析：没有改代码，没有跑新的模拟。

## 场景和约定

- **主配置**：`w64b384`，W=64，每条链路 384 GB/s，25 个 workload。
- **网络紧张**：`w256b48m`（W=256，48 GB/s，MSHR 16）和 `w2048b48`（W=2048，48 GB/s），各 6 个 workload：pr-g24、npbcg-W、sssp-s18e4-r1、bfs-s18e2、ar-pc1、cfd-c172k-b128。两个网络紧张场景的结果几乎相同，下文给 `w256b48m` 的数，`w2048b48` 的数在 csv 里。
- **字节×跳数** = 在 168 条有向交换机链路上传输的字节总数，也就是 `mesh_bytes`，是精确值。读的部分按每次远程读每跳 112 B 估计（见 README 的字节模型）。baseline 下，不含写的 workload 用这个模型估出的读字节占实测 mesh 字节的 98%，说明模型对得上。
- **"上限"都是叠加在 Complete 之上的**，分母有两种：
  - Complete 实际发到网络的读 line 数，记作"网络 line"；
  - Complete 的 mesh 字节×跳数，记作"mesh"。
- 编号：统计里的 GPM 都是 tile id（x + 7y）。路由是**先 Y 后 X**。

## 1. 字节×跳数分解

### 1.1 远程读的距离：一半的字节×跳数来自 ≥6 跳的读

- 均匀访问的 workload（ar、sssp、bfs、cfd、ivf、gups、km、mt、spmv、embbag、npbis），远程读平均 4.0–4.9 跳。按跳数分，读的字节×跳数里：
  - ≤2 跳只占 6–12%；
  - 3–5 跳占 36–45%；
  - ≥6 跳占 47–59%。

  7×7 mesh 的平均跳数约 4.7，直径 12。越远的读在字节×跳数里的权重越大。
- 热点在角落的 workload，远程读平均 5.2–6.1 跳。PR、MM、shocsort 有 75% 的读字节×跳数来自 ≥6 跳的读。

### 1.2 热点 owner 都在角落

每个场景的数在 `bytehop_summary.csv` 和 `bytehop_by_ownerpos.csv`。下表是 baseline 的数；owner 份额对 Complete 是精确值，对 baseline 是按在途采样估的（见 1.5 节）。

| workload | 热点 owner（tile） | 位置 | 份额（baseline） | 份额（Complete） | 到请求方的平均跳数 |
|---|---|---|---|---|---|
| pr-g24 | 0 (0,0) | 角落 | 1.00 | 0.98 | 6.13 |
| mm-g12 | 0 | 角落 | 1.00 | 1.00 | 6.14 |
| npbcg-W | 0 | 角落 | 0.80 | 0.25 | 4.72 |
| tc-s12e16 | 48 (6,6) | 角落 | 0.60 | 0.61 | 5.90 |
| atax | 0 | 角落 | 0.35 | 0.04 | 5.79 |
| fw | 0 | 角落 | 0.31 | 0.06 | 6.06 |
| shocsort | 0 | 角落 | 约 0.6（写多，只能用在途估计） | 1.00 | 6.0 |
| sssp / bfs / ivf / gups | 48 或 0 | 角落 | 0.08–0.10 | 0.07–0.10 | 5.4–6.8 |
| ar、cfd、km、mt、spmv、embbag、pa | — | 均匀 | ≤ 0.05 | ≤ 0.05 | — |

- **原因是放置规则**：不到 48 页的 buffer 整个放在 GPM 0，也就是 tile 0，坐标 (0,0)；余数页放在最后一个 GPM，也就是 tile 48，坐标 (6,6)。两个都是角落。角落 owner 到其他 GPM 平均 6.13 跳，而中心旁边的 tile 17/23/25/31 只有 3.70 跳。
- **角落只有 2 条出链路，加上先 Y 后 X 的路由，热点流量几乎全压在一条链路上**：
  - tile 0 发出的数据先往下走，所以 0→7 这条链路承担了 PR 87%、npbcg 79%、MM 87%、atax 84% 的热点出流量；
  - tile 48 先往上走，48→41 承担了 tc 81–89%、sssp 63–66%、moe 92%。
- **实测链路负载**：

  | 场景 | 0→7 平均利用率 | 1 µs 窗口内的最大利用率 | 是否全网最忙 |
  |---|---|---|---|
  | PR baseline @384 | 0.36 | 0.45 | 是 |
  | PR baseline @48 | 0.87 | 1.0 | 是 |
  | PR Complete @48 | 0.67 | 1.0 | 是 |
  | npbcg baseline @48 | 0.76 | — | 是 |

  也就是说，48 GB/s 下 Complete 之后 PR 的瓶颈仍然是这一条角落链路。

### 1.3 链路负载：均匀流量压在中部，热点流量压在角落，中心 tile 闲着

数据来自 `links_class.csv`。

- **均匀流量**（ar、cfd、sssp、bfs）：
  - 行/列 2–4 之间的 56 条中部链路（占全部链路的 33%）承担 41–43% 的字节；
  - 角落的 16 条链路（10%）只承担 6–7%。
  - 48 GB/s、W=256 时，中部链路平均利用率 ar 0.30/0.36、cfd 0.46/0.43（baseline / Complete），角落只有 0.16–0.23；所有类别的 1 µs 窗口最大值都到 1.0。
- **热点流量**（PR、npbcg、tc、mm）：16 条角落链路承担 16–22% 的字节（npbcg baseline 20%），最忙的链路是角落 owner 的那条出链路。
- **中心 tile 24（driver/IOMMU）的 8 条链路**只承担 2–5% 的字节。中心不是 GPM，这些链路只有穿过的流量和地址翻译的流量。
- **384 GB/s 下所有链路都很闲**：平均利用率 1–7%，最大 0.36（PR 的 0→7），1 µs 窗口最大值 0.2–0.7。

### 1.5 方法的可信度

- **owner→requester 矩阵是估计的**，现有统计没有逐对的读数：
  1. 用 `_pairs.csv` 的在途均值除以按跳数的 (rtt + 等待)，再按每个请求方的实际读数归一化；
  2. 按列缩放：Complete 缩放到每个 owner 精确的 `t18_owner_reads`；baseline 在写不多时（写 ≤ 读的 20%）缩放到 owner 端的 `incoming_trans_count`，写多的 workload 不缩放。
- **验证**：
  - 把矩阵按先 Y 后 X 路由到链路上，和实测的每条链路字节比较，相关系数中位数 0.97。PR、npbcg、MM、atax 的 baseline 是 1.00，预测的最大链路利用率和实测的完全相同（PR 0.36 / 0.87，npbcg 0.26 / 0.76）。
  - 最差的是 shocsort Complete，0.29：读只占它流量的 2%，其余是写。
  - 按跳数的平均值和精确值差 ≤ 0.5 跳。fft2d 例外（估 5.5、实际 3.6），它的 owner 分解不可靠。

## 2. 重复搬运与共享的上限

### 2(a) 同一 GPM 重复取同一条 line

数据来自 `dup_same_gpm.csv`。

- **baseline 下的重复取**：在同一个写纪元内，同一 GPM 再次读同一条 line，占远程读的比例：PR 0.97、npbcg 0.95、KM 0.94、mm 0.91、bh 0.86、tc 0.83、fw 0.81、i2c 0.81、mg 0.75、sssp 0.71、npbis 0.70、cfd 0.67、bfs 0.45、ivf 0.35；ar、mt 为 0。
- **M3 之后剩下多少**：
  - 计算方法：Complete 的网络 line 数减去唯一的 (GPM, line, 写纪元) 数，再除以网络 line 数。这个值偏保守：有用的预取已经算在网络 line 里。
  - 结果：KM 0.93、npbcg 0.82、mg 0.62、cfd 0.60、fw 0.56、npbis 0.55、shocsort 0.52、sssp 0.43、i2c 0.40、PR 0.39、tc 0.39、bh 0.37、moe 0.25、bfs 0.21、ivf 0.16、embbag 0.13、lud 0.12；ar、mt、atax 为 0。
  - 网络紧张时：npbcg 0.79、cfd 0.57、sssp 0.42、PR 0.27、bfs 0.21。
- **为什么 M3 没把它们吃掉**：
  1. **kernel 边界整体作废**。多 kernel 的 workload 里，边界作废的 line 数约等于填入的 line 数。npbcg 有 186 个 kernel，141 万次填入里 135 万在边界被作废；cfd、mg、lud、bfs、fft2d 也一样。这些 workload 的 M3 填入有 63–97% 没用上就退休了（npbcg 63%、cfd 83%、lud 92%、ar 65%）。但 obs 的重用统计是按写纪元算的，被算作"重复"的读之间这条 line 并没有被写过。所以这些读在语义上可以继续在本地命中，只是被边界的整体作废丢掉了。
  2. **两次触碰过滤器抓不到长重用距离**。KM 的重复取 94%，但只有 0.8% 的重用间隔小于 10 µs；M3 只有 1980 个候选，`remote_seen_hits` 只有 10。
  3. **容量不是问题**：Complete 下 L2 空闲比例大多是 0.7–0.95，最低的 pa 是 0.43、atax 0.19。
- **改进 M3 的选择性保留**：只作废被写过的页或 line（例如用写纪元或页的写位图），跨 kernel 保留只读的远程 line；对长重用距离放宽两次触碰的条件。上限就是上面"剩下的比例"：网络 line 平均 31%、中位数 26%，有 15/25 个 workload ≥ 20%；按 mesh 平均 22%。

### 2(c) "按共享者主动推送"的上限

数据来自 `push_bound.csv`。

**假设**：
- owner 是 oracle：读的时候，把这条 line 多播给本窗口（T = 1 µs 或 10 µs）内会来读它的其他 GPM，最多 K 个；
- 推过去的数据在对方需要之前到达，并且一直留在对方 L2 里（L2 空闲 70–95%，容量不是约束）；
- 每次推送省掉对方一次"窗口内的首次读"，用一份请求加一棵多播树代替 s 次单播；字节×跳数按 m1 统计里的 owner 跳数和多播树链路数算；
- 省下的读数不超过 Complete 实际的网络 line 数。

**结果**（叠加在 Complete 之上，T = 10 µs，K = 4；括号里是 K = ∞）：

| workload | 省掉的远程读 / 全部逻辑读 | 省掉的字节×跳数 / Complete 的 mesh |
|---|---|---|
| sssp | 0.31（0.51） | 0.31（0.58） |
| ivf | 0.36（0.64） | 0.27（0.53） |
| bfs | 0.21（0.35） | 0.13（0.24） |
| ar | 0.17（0.44） | 0.12（0.32） |
| cfd | 0.12 | 0.10 |
| tc | 0.12（0.28） | 0.29（0.80） |
| PR | 0.02–0.05 | 0.25–0.56 |
| npbcg | T = 1 µs：0.07（0.26） | T = 1 µs：0.24（0.93） |
| mg | 0.09 | 0.08 |

- PR 的远程读本来就只剩 5%，但剩下的几乎都是"别的 GPM 已经取过"的首次读，所以字节能省一半以上。
- 网络紧张（w256b48m，K = 4）：sssp 0.32/0.32、bfs 0.22/0.13、ar 0.24/0.14、cfd 0.08/0.07、npbcg 0.12/0.39、PR 0.04/0.54。

**无用推送的比例**（预测器的真实准确率现有统计算不出来，给出两个界）：
- 乐观：只有本窗口里确实被共享的 line 才有读者历史，无用 = K 个读者里本窗口没读的那些。K = 1 时为 0；K = 4 时，sssp 0.27、ivf 0.26、tc 0.14、ar 0.13、bfs 0.37、cfd 0.74、mg 0.75。
- 悲观：每条 line 都推给 K 个读者。K = 4 时，sssp 0.55、ivf 0.44、tc 0.31、PR 0.31、bfs 0.87、ar 0.92、cfd 0.96、npbcg 0.99。

**结论**：sssp、ivf、tc 的共享者数稳定在 3–6 个，在 K = 2–4 时，"有用的推送"和"无用的推送"量级相当，值得做；bfs、ar、cfd、npbcg 需要一个准确的预测器，否则推送的字节多于省下的字节。这一项的上限和 2(a) 的跨 kernel 保留**有重叠**（同一条 line 被同一个 GPM 再次读，在边界作废之后也会被算作窗口内的首次读），两者不能直接相加。

### 2(d) owner 端等待 100 / 200 / 500 ns 再多播

数据来自 `owner_wait.csv`。

**假设**：
- f(τ) 是"owner 收到读的时候，前 τ 时间内另一个 GPM 读过同一条 line"的比例；
- 在两个实测点之间按 log τ 线性插值：owner 驻留时间 τ_o（排队 + 服务 + 等待发送）对应 owner 并发比例，L1V 驻留时间 τ_r（端到端延迟）对应 L1V 端其他 GPM 在途比例；
- 合并以后响应改成多播，每次合并省下的跳数按 1 µs 窗口里两个共享者的 "owner 跳数之和 − 多播树链路数" 算；
- 用 baseline 的点。

**结果**：

| workload（w64b384） | τ_o / τ_r | 多合并（占 owner 读）100 / 200 / 500 ns | 字节×跳数 @200 ns | τ = 200 ns 占 RTT 的比例 |
|---|---|---|---|---|
| sssp | 48 ns / 2.1 µs | 0.11 / 0.22 / 0.36 | 5% | 0.50 |
| ivf | 58 ns / 2.2 µs | 0.08 / 0.18 / 0.32 | 5% | 0.45 |
| bfs | 54 ns / 1.5 µs | 0.05 / 0.11 / 0.19 | 2.5% | 0.55 |
| ar | 145 ns / 3.5 µs | 0 / 0.04 / 0.15 | 1.2% | 0.36 |
| cfd | 53 ns / 2.7 µs | 0.01 / 0.03 / 0.05 | 1.6% | 0.51 |
| mg | 52 ns / 2.1 µs | 0.01 / 0.01 / 0.02 | 0.7% | 0.64 |
| PR / npbcg / tc / mm | 350–570 ns | 0（热点 owner 本来就在排队） | 0 | — |

- 网络紧张（w256b48m）：sssp 0.08/0.15/0.25、bfs 0.03/0.08/0.13、ar 0/0.07/0.16、npbcg 0.09/0.17/0.29、PR 0.11/0.21/0.34。最后两个是因为 48 GB/s 下热点 owner 的驻留时间降到了 45–50 ns。字节×跳数只省 1–7%。
- **代价**：如果每个读都多等 τ，在 W=64 受窗口限制的区域，吞吐大约按 RTT 成比例下降，而 200 ns 是 RTT 的 0.36–0.64 倍，净效果是负的。只有"只在 owner 已知有别的读者将要到达时才等"（需要预测器），或者链路饱和（48 GB/s）的时候才可能为正。上限很低：字节省 < 7%，L2 读省 < 36%。

## 3. 压缩率

### 3.1 现有 trace 没有记录数据内容

已经确认：
- `akita/mem/trace/*.go`、`runner/obsstats.go`、`gpmtracer.go`、`p12tracer.go`、`page_sharing_trace.go` 里都不读 `Data`；
- obs 的 hook（`ObsOwnerSend` / `ObsReqArrive`）只传 ID、地址和时间；
- `metrics.csv` 里没有数据相关的计数器。

所以现有结果算不出可压缩性。timing 模式下响应带有真实数据：`mem.DataReadyRsp.Data`、T18 owner 的 `e.data`、位图响应的 `LineData`，在不做 verify 时也一样。只要加一个只读统计就能测。

### 3.2 只读统计的提案（未实现）

- **开关**：`-report-obs-compress`，默认关，不并入 `-report-obs-all`，以免改变已有运行的输出。它不发消息、不调度事件，不改变时序。
- **入口函数**：在 `akita/mem/trace/obsstats.go` 加 `ObsRspData(ownerName, requesterName string, addr uint64, data []byte, dests int)`，在所有 owner 发响应的地方调用。这四处和现有的 `ObsOwnerSend` 一一对应：
  1. baseline 路径：`mgpusim/timing/rdma/comp.go:755`，`rsp.(*mem.DataReadyRsp).Data`；
  2. 位图响应：`remote_owner.go:157` 的循环，`batch.readyData[line]`；
  3. T18 多播：`t18_owner.go:273`，`e.data`，`dests = len(e.reqs)`；
  4. T18 单播：`t18_owner.go:298`。

  远程写的数据也可以在请求方 RDMA 发写请求的地方（`comp.go` 克隆 `WriteReq` 的路径）用同一个函数统计，带上 `DirtyMask`。
- **每条 64 B line 在线计算**（只累加计数，不存数据）：
  - 全 0；全部 8 B / 4 B 字相同；
  - BDI：base 8 B，delta 1/2/4 B；base 4 B，delta 1/2 B；base 2 B，delta 1 B；并带一个隐含的 0 base；取最小的编码；
  - FPC：每个 32 位字分成 0 / 符号扩展 4/8/16 位 / 半字补零 / 字节重复 / 不压缩，算总位数；
  - 跨 line 的值局部性：64 B 内容的 64 位哈希放进一个 4K 项的近期表，统计"刚刚发过一模一样的 line"的比例；
  - 每种方案的压缩后字节数，换算成 flit（`ceil(1.25 × (bytes + 4) / 16)`），和原来的 6 flit 比较。
- **输出** `_compress.csv`：
  - 按方案统计：line 数、压缩后字节数之和、flit 数之和、flit × 跳数之和（跳数用 `manhattanHops(owner, requester)`，多播按树计）；
  - 再按 owner tile 和按"热点 owner / 其他"各分一份；
  - 一个压缩后字节数的直方图（以 8 B 为一档）。
- **开销**：每个响应扫一遍 64 B，做一次哈希，在模拟机上约 50–100 ns。每个运行 10⁶–10⁷ 个响应，所以总共不到 1 秒（运行本身要几十分钟）。内存是常数（几个计数器加一个 4K 项的表）。
- **验证**：开关打开后，`total_time` 和所有现有统计应该逐位一致。

### 3.3 不知道数据时能给的界

- **按假设的压缩率**（`ranking.csv` 的 `compress*_mesh_assumed`）：
  - 1.5× 压缩：响应从 6 flit 降到 4 flit，按 mesh 平均省 20%；
  - 2× 压缩：降到 3 flit，平均省 30%（最多 42%）。
  - 写多的 workload（i2c、fft2d、gups、mt、shocsort）还要看写数据能不能压缩。
- **性能上的上限要分两种情况**：
  - **384 GB/s**：链路平均利用率 1–7%，瓶颈是窗口位和 owner 排队。压缩只省串行化时间：每跳 6 flit 在 24 flit/ns 下只要 0.25 ns，6 跳一共约 1–2 ns，相对 300–900 ns 的 RTT 可以忽略。**压缩在主配置下几乎没有性能上限。**
  - **48 GB/s**：所有类别的链路在 1 µs 窗口里都会饱和；cfd 中部链路平均 0.43–0.46，PR 的角落链路 0.67–0.87。字节省 30% 可以直接减少饱和链路的忙时，上限大约是"链路受限时间 × 0.3"。
- **推测（未验证）**：图类（sssp 的距离、bfs 的层号、CSR 下标）大多是窄整数和重复的初始值（INF / −1），BDI/FPC 通常能到 1.5–2×；PR 的 rank、cfd 的通量这类 float 数组通常只有 1.1–1.3×。需要 3.2 节的统计来确认。

## 4. 汇总：各方向的上限排序

叠加在 Complete 之上。数据来自 `ranking.csv`、`hotspot_whatif.csv` 和第 2 节。"网络 line" 和 "mesh" 的含义见开头的约定。

| 方向 | 主配置 @384：网络 line（均值 / 中位数） | 主配置 @384：mesh（均值 / 中位数） | 网络紧张 @48：mesh（均值） | 能不能解决主配置的瓶颈（窗口位、owner 排队） |
|---|---|---|---|---|
| **改进 M3 的选择性保留**（跨 kernel 保留只读 line；长重用距离） | **0.32 / 0.26**；KM 0.93、npbcg 0.82、mg 0.62、cfd 0.60、npbis 0.55、sssp 0.43、PR 0.39 | 0.22 / 0.15 | 0.29 | **能**：少一次往返就少占一个窗口位 |
| **主动推送**（oracle，K = 4） | 0.31 / 0.23；sssp 0.66、ivf 0.46、tc 1.0、PR 1.0、bfs 0.30 | 0.16 / 0.10 | 0.26 | 能，但要靠预测器；无用推送 0.13–0.99 |
| **压缩**（假设 1.5–2×） | 0（不减少往返次数） | 0.20–0.30（按假设） | 0.23–0.34 | **不能**：384 GB/s 下链路利用率只有 1–7% |
| **热点小数据放中间 / 复制** | 只影响热点 workload | 0.11 / 0.04；MM 0.77、PR 0.56、tc 0.48、npbcg 0.18 | 0.13；PR 0.50 | 部分能：4 份副本让热点 owner 的服务带宽 ×4，最忙链路的负载 ×0.15 |
| **owner 自适应等待**（200 ns） | 0.05 / 0.01（多合并的 owner 读） | 0.01 / 0.001 | 0.03 | **不能**，而且每个读多出 0.36–0.64 倍 RTT 的延迟 |

### 热点 owner 搬家或复制的效果

数据来自 `hotspot_whatif.csv`：把估计的读矩阵按先 Y 后 X 路由，最大链路负载的预测值和实测值吻合。

| workload | 搬到最优 tile：读的字节×跳数 | 搬到最优 tile：最忙链路负载 | 4 份副本（tile 8/12/36/40）：读的字节×跳数 | 4 份副本：最忙链路负载 |
|---|---|---|---|---|
| PR（31 号 tile） | ×0.58 | ×0.63 | ×0.27 | ×0.15 |
| npbcg（baseline） | ×0.66 | ×0.56 | ×0.48 | ×0.25 |
| tc | ×0.72 | ×0.65 | ×0.52 | ×0.18 |
| MM | ×0.58 | ×0.52 | ×0.28 | ×0.15 |

- 只搬到中间，最忙链路的负载只降 35–45%。先 Y 后 X 的路由仍然把流量集中在中心 tile 的上下两条链路上，而且 owner 的服务带宽不变。复制才能同时解决链路和 owner 两个问题。
- PR @48 Complete 的 0→7 链路忙时占 0.67T。做 4 份副本后，最忙链路的负载降到原来的 0.15，这是这一项在网络紧张场景下唯一明显的性能上限。

### 最值得实现：M3 的选择性保留（跨 kernel 保留只读 line）

1. **在主配置下它是唯一直接打到瓶颈上的方向**。384 GB/s 下，瓶颈是请求方的 64 个窗口位和热点 owner 的排队，不是链路字节。少一次远程往返，就同时省下一个窗口位、一次 owner 服务和全部字节；只省字节的方向（压缩、M2 多播、owner 等待）在这里没有效果，这和 abl3c384 里 M2 的 0.998 一致。
2. **上限大，而且分布在多个 workload 上**：Complete 剩下的网络 line 有 31% 是同一 GPM 的重复取（15/25 个 workload ≥ 20%），而 L2 有 70–95% 是空的。
3. **实现简单，风险低**：现有 M3 在 kernel 边界整体作废；改成只作废被写过的页（写位图或写纪元），或者只读页不作废。再对长重用距离（KM）放宽两次触碰的条件。正确性只依赖"作废所有被写过的 line"，现在的边界作废已经有这套机制。
4. **和推送是互补的**：保留解决"同一 GPM 再读"，推送解决"别的 GPM 首次读"。推送的上限（sssp、ivf、tc）次之，但要先有一个准确的读者预测器；建议先加 2(c) 的在线评估统计（每条 line 记最近 K 个读者，读的时候统计"如果推了，是否在 T 内被用到"），确认无用推送 < 0.3 再实现。

**热点放置/复制**放在论文里作为放置问题单独交代，和 abl3c384 的 P6 一致。它对 PR、MM、tc、npbcg 的字节和角落链路效果很大，但 M3 已经在每个 GPM 的 L2 里复制了热点数据（PR 96% 的本地命中），所以叠加在 Complete 上的性能收益主要出现在 48 GB/s 下。

**压缩**在主配置下没有性能上限，在 48 GB/s 下有约 20–30% 的字节上限，但要先用 3.2 节的统计测出真实的压缩率。**owner 自适应等待**排在最后。

### 和 wafer 特性的关系

- **对分带宽 ∝ √N，平均跳数 ∝ √N**：
  - 7×7 的对分带宽只有 7 条链路，平均跳数 4.7。均匀流量的读，一半的字节×跳数来自 ≥6 跳的读，中部 56 条链路承担了 41–43% 的字节；48 GB/s 下最先饱和的是中部链路。
  - 网格变大时，每个 GPM 分到的对分带宽按 1/√N 下降，平均跳数按 √N 上升。所以"按字节×跳数省"的方向（压缩、多播树、复制、推送）的价值随 √N 增长。
  - "按往返次数省"的方向（保留、推送、合并）同时省掉一个往返的延迟，而这个延迟也随直径增长。按 Little 定律，固定窗口 W 下的吞吐 = W ÷ RTT，所以在大 wafer 上，减少往返比减少字节更重要。这也是 W=64 下打包和 M3 有用、M2 没用的原因。
- **直径**：7×7 的直径是 12 跳。中心的 tile 不是 GPM，所以离所有 GPM 最近的位置（17/23/25/31，平均 3.70 跳）只有 4 个。角落到其他 GPM 平均 6.13 跳，是中心旁边的 1.66 倍。
- **角落链路少**：角落只有 2 条出链路，内部有 4 条。先 Y 后 X 的路由让一个角落 owner 的出流量 79–92% 走同一条链路，等于一个角落 owner 只有 1 条有效的出链路，是内部 owner 的 1/4。当前放置规则恰好把小 buffer 和余数页放在两个角落（tile 0、48），这是 PR、npbcg、tc、MM 热点的根本原因。
- **中心 tile 的链路几乎闲着**：只承担 2–5% 的字节。如果中心 tile 换成 GPM，或者用于存放复制的热点数据，可以把这部分对分带宽用起来。这是以后讨论 wafer 布局时的一个选项，这里没有评估。
