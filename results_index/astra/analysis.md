# ASTRA-sim 交叉验证：结论（P18，2026-10-21）

一句话：**MGPUSim 的网络结论被独立的模拟器复现了。** 两边输入同样的流量和 W，网络受限的场景里往返时间差 0–12%，热点链路利用率差 0–3%。两边不一致的地方只有一处：384 GB/s、W = 64 时的热点 owner。差异来自 akita 里 owner 端的处理排队，ASTRA-sim 不建这一部分，不是 akita 网络模型的问题。

建模方式、补丁、版本见 `README.md`。下面的"akita"指 MGPUSim/akita 的已有结果（二进制 `4235991`）。

## 0. 校准（`calibration_hops.csv`）

零负载单程延迟（ns）：

| 跳数 | ASTRA 请求 @384 | akita 请求 | ASTRA 响应 @384 | akita 响应 | ASTRA 响应 @48 |
|---|---|---|---|---|---|
| 1 | 45.67 | 45.74 | 46.29 | 45.81 | 51.54 |
| 6 | 225.67 | 226.06 | 227.33 | 226.10 | 241.33 |
| 12 | 441.67 | 442.47 | 444.58 | 442.20 | 469.08 |

- 384 GB/s：差 ≤ 0.8 ns（请求）、≤ 2.4 ns（响应）。
- 48 GB/s：ASTRA 的响应在 12 跳时多 27 ns。原因是 ASTRA 逐跳存储转发（6 flit 的包每条链路串行化 2 ns），akita 是 flit 级流水，只付一次。akita 在 48 GB/s 下没有零负载的测量，这一项只有模型上的解释。
- akita 的每跳 35.96 ns = 32 周期交换机流水 + 约 4 个周期的 route / forward / 链路级。T14 的指针追逐（`platform_mi200/hopmatrix.csv`，768 GB/s）每跳往返 72 ns，和这里的 2 × 36 一致。

## 1. 第 1、2 条："384 GB/s 下网络不是瓶颈，瓶颈是 W × RTT"——复现

E1 闭环（所有请求方一直保持 W 个在途），384 GB/s，非热点流量（`compare_E1_closed.csv`）：

| 流量 | RTT（ns）W = 64 / 256 / 448 | akita RTT | 每 GPM 吞吐（B/ns） | 最忙链路 @W448 | 链路平均 @W448 |
|---|---|---|---|---|---|
| sssp | 384 / 391 / 404 | 401 / 405 / 408 | 10.5 / 38.3 / 65.4 | 0.44 | 0.22 |
| bfs | 360 / 369 / 381 | 363 / 369 / 373 | 11.3 / 41.8 / 68.4 | 0.44 | 0.21 |
| ar | 433 / 440 / 442 | 552 / 598 / 656 | 9.3 / 35.2 / 61.3 | 0.32 | 0.23 |
| cfd | 386 / 392 / 394 | 391 / 409 / 471 | 10.5 / 39.4 / 69.0 | 0.42 | 0.24 |
| 均匀 all-to-all | 400 / 407 / 410 | — | 10.1 / 38.0 / 65.7 | 0.33 | 0.24 |

- W 放大 7 倍，往返时间只涨 1–5%，吞吐几乎按 W 线性增长；吞吐 = W × 64 B ÷ RTT，误差 ≤ 10%（ASTRA 也是窗口受限）。
- W = 448（akita 被 L1V MSHR 封顶的值）时，mesh 最忙的链路才 32–44%，平均 21–24%，填不满。这和 akita 的"对分带宽只用到 20–32%"一致。
- akita 的 W 放大收益比 ASTRA 小（sssp 的总时间 W 64 → 256 只快 1.56 倍，ASTRA 的远程读吞吐快 3.6 倍），因为 akita 的请求方并不总是被窗口卡住（`frac_time_full` 0.35），还有计算和 kernel 边界。网络本身允许的上限比 akita 实际用到的高。

## 2. 第 3 条："48 GB/s 下回程排队到 µs 级"——复现

热点 workload 闭环，ASTRA / akita：

| 流量 | 带宽、W | RTT ASTRA / akita | 0→7 链路 ASTRA / akita | tile 0 注入口（ASTRA） |
|---|---|---|---|---|
| PR | 48，64 | 5.91 / 5.82 µs（+1.6%） | 0.868 / 0.868 | 0.995 |
| PR | 48，256 | 23.7 / 23.5 µs（+0.8%） | 0.871 / 0.871 | 0.998 |
| PR | 48，448 | 41.4 / 41.0 µs（+1.0%） | 0.871 / 0.871 | 0.999 |
| PR | 384，256 | 2.96 / 2.91 µs（+1.7%） | 0.844 / 0.823 | 0.968 |
| PR | 384，448 | 5.17 / 5.16 µs（+0.3%） | 0.863 / 0.830 | 0.990 |
| npbcg | 48，64 | 3.08 / 2.94 µs（+4.9%） | 0.781 / 0.753 | 0.975 |
| npbcg | 48，256 | 12.3 / 11.8 µs（+4.2%） | 0.799 / 0.760 | 0.997 |
| npbcg | 384，448 | 2.72 / 2.43 µs（+12%） | 0.773 / 0.576 | 0.965 |

- 非热点 workload 在 48 GB/s 下也到 µs 级：W = 256 时 ASTRA 1.0–1.2 µs，akita 0.7–1.6 µs。这时 ASTRA 的请求方一直是饱和的，akita 不是，所以只对得上数量级。
- **同负载开环（E2a）**：按 akita 整个运行的平均速率注入，ASTRA 的回程排队只有 0.2–0.6 µs（akita 是 0.4–23 µs），但平均链路利用率和最忙链路的利用率都和 akita 一致（PR @48：0.878 / 0.871）。这说明 akita 的 µs 级排队是闭环饱和的结果：47 × W 个在途读堆在瓶颈队列里，往返时间 ≈ 在途数 ÷ 吞吐。它不是平均负载造成的，也不是 akita 网络模型多算出来的。另外 akita 1 µs 窗口的峰值利用率（0.2–1.0）比泊松开环（0.05–0.9）高，akita 的流量是阵发的。

## 3. 第 4 条："热点在角落、87% 的出流量走 0→7"——复现，并修正一点

- ASTRA 和 akita 的最热链路都是 0→7，利用率一样（见上表）。按先 Y 后 X 路由重建流量，就能预测出 0→7 的 flit 数（`traffic_link_check.csv`：PR 1.70 亿 vs 1.69 亿）。
- **修正**：真正的瓶颈是 **tile 0 自己的注入口**（GPM→交换机，带宽和一条链路相同），它在饱和时到 0.97–1.0。0→7 只分走其中 87%，所以停在 0.87，到不了 1.0。合成的"47 个 GPM 读 tile 0"也是同一个数（0.87 / 0.999）。换路由（比如先 X 后 Y，或者自适应）只能改变 87% 是怎么分到 0→1 和 0→7 上的，提高不了热点 owner 的上限。要提高上限，只能减少 owner 发出的字节（合并、多播、M3），或者把数据挪走（page migration）。
- 开环扫描（`compare_E2b_sweep.csv`）：每个流量的最热链路利用率和按路由预测的 ρ 完全一致。非热点流量的往返时间在 ρ ≤ 0.9 之前基本不变，过了 1 才失稳。热点流量在 ρ = 0.9 时已经开始排队（注入口 = 0.9 / 0.87 > 1）。

## 4. 唯一的不一致：384 GB/s、W = 64 的热点 owner

| | ASTRA RTT | akita RTT | akita owner 排队 |
|---|---|---|---|
| PR | 740 ns | 1554 ns | 532 ns |
| npbcg | 385 ns | 804 ns | 372 ns |

- ASTRA 只建网络加固定的 owner 服务时间；akita 里 tile 0 的 RDMA / L2 处理能力有限（每周期 8 个、10 周期流水，加上 L2 带宽），请求在 owner 端排队。
- 所以主配置下 PR 和 npbcg 卡在 **owner 端的处理**，不在网络：ASTRA 的 tile 0 注入口只到 0.70 / 0.53。W ≥ 256 或 48 GB/s 时，网络（注入口）先饱和，两边又对上了。
- 这和"384 GB/s 下网络不是瓶颈"不矛盾，反而补了一句：热点 owner 在主配置下的瓶颈是 owner 的服务能力。

## 5. 第 5 条："带宽大概率不是瓶颈，和 wafer 相关的是 hop"

- 384 GB/s 下支持：非热点流量的往返时间 ≈ 零负载值（hop 决定），W 放大 7 倍链路也用不到一半。
- 48 GB/s 下带宽确实会成为瓶颈（往返时间到 µs 级），而且热点 owner 的上限由注入带宽决定，和 hop 无关。
- LLM 试验（第 7 节）也是同一个规律：384 GB/s 下放置方式只影响 8%，48 GB/s 下影响 35%。

## 6. 选项 A：CuPath 机制的网络层评估（`compare_E3_mechanisms.csv`）

用 akita Complete 运行自己的流量（M3 命中和请求方合并不进网络、按实测直方图打包、实测的目的地分布），和 baseline 流量在同样的 W、带宽下闭环比较"每 ns 完成的逻辑远程读"：

| workload | ASTRA 网络层提升（6 组条件） | akita 端到端加速比 |
|---|---|---|
| PR | 20.0–22.8× | 7.2–17.6× |
| npbcg | 6.8–15.7× | 2.7–8.7× |
| sssp | 2.0–2.7× | 1.42–1.69× |
| cfd | 1.24–1.97× | 1.06–1.88× |
| ar | 1.05–1.91× | 1.02–1.86× |
| bfs | 1.41–1.63× | 1.04–1.11× |

- 36 组里 35 组 ASTRA ≥ akita，排序一致（Spearman 0.88），中位数 ASTRA / akita = 1.40。ASTRA 是"只看远程读"的上限：akita 的端到端时间里还有计算、本地访存和不饱和的时段（Amdahl）。唯一 ASTRA < akita 的是 ar @48 GB/s、W = 256（1.08 对 1.25）。
- **收益从哪来**：384 GB/s 下，sssp / bfs / cfd / ar 的 Complete 往返时间和 baseline 差不多（±8%），网络层提升 ≈ 每个包承载的逻辑读数（sssp 2.16，cfd 2.31，ar 1.94）。也就是说，在 W × RTT 的上限下，机制的作用是**让同一个窗口位置承载更多逻辑读**（M3 命中、合并、打包），不是降低延迟。PR 每个包承载 29.6 个逻辑读（几乎全靠 M3），所以提升 20 倍，但 tile 0 的注入口在 Complete 下仍然饱和（0.96–1.0）。
- 局限：owner 合并 + mesh 内多播没有建，结果偏保守（akita 被合并的 owner 读 ≤ 7%）；合并和打包的比例取自 akita，不是 ASTRA 动态算出来的。**这一节是"同样的流量削减在独立的网络模型里值多少"，不是 CuPath 端到端加速比的独立复现**，端到端以 MGPUSim 为准。

## 7. LLM 试验：Llama-7B 推理（`llm/llama7b_tp8pp6.csv`）

6 条序列，各 512 token 的 prefill 加 8 个解码 token；TP 8 × PP 6；每 GPM 24 TFLOPS、240 GB/s，roofline；TP all-reduce 用 ASTRA 的 ring；stage 之间点对点传激活。

| 放置 | 384 GB/s | 48 GB/s |
|---|---|---|
| 相邻（蛇形） | 148.3 ms | 216.9 ms |
| 随机 | 161.8 ms | 293.1 ms |

- 每个配置 5–9 s 墙钟。计算时间（每 GPM 92–102 ms）和手算一致。
- 384 GB/s 下放置只差 9%、带宽降到 1/8 只差 46%（相邻放置）；48 GB/s 下随机放置差 35%，带宽和 hop 叠加。
- 这只是趋势：计算和通信不重叠、ring all-reduce、中心 tile 不参与。它看不到 kernel 内细粒度的远程读，所以不能用来评估 CuPath 本身。

## 8. ASTRA-sim 的速度

- 每次远程读约 4,000–5,400 次/秒（闭环 14.1 万次读 26 s；100 万次读开环 4 分钟，约 5 GB 内存），生成 100 万次读的 ET 约 80 s。akita 全 GPU 模拟约 1,300 次远程读/秒，但它同时模拟了整个 GPU。
- 原版的事件队列是平方级的（见 README 补丁 3），不修的话大一点的运行跑不完。
- ASTRA-sim 适合 MB 级的集合通信（LLM 试验每个配置几秒）；64 B 粒度、几百万条的读不是它的强项。

## 没做的 / 需要用户决定的

- 48 GB/s 下 akita 的零负载跳数延迟没有直接测量，只做了模型上的解释（第 0 节）。如果要放进论文，建议在服务器上用当前二进制跑一次 T14 跳数矩阵（`-bandwidth=3 -switch-buffer-flits=16`，baseline，只开统计）。
- 多播（M2）没有在 ASTRA 里实现；按 akita 的比例，它最多影响 7% 的响应。
- 现在的 ASTRA 补丁和结果只在本机和 yss3，没有推送 ASTRA-sim 的仓库。
