# v3 机制在 384 GB/s 下为什么有用 / 没用，以及改进提案

Claude Code，2026-10-21。数据：`abl3c384.csv`（每个运行一行）、`mechanism_stats.csv`（每个 workload 一行：Complete 的 M1/M2/M3 统计，加上 baseline 和 Complete 的 obs 统计）、`obs_raw/{yss2,yss3}/*.csv`（`akkalat/obs_collect.py` 对 baseline 和 Complete 运行的输出）。加速比和损失的表在 `README.md`。

**统计口径**
- 二进制都是 `baseline_4235991`，网络是 `-bandwidth=24 -switch-buffer-flits=16`，每条链路单向 384 B/ns。
- 统计是 48 个 GPM 求和；"平均占用"类统计是 48 个 GPM 的平均。
- 链路利用率 = 字节数 ÷（时间 × 384 B/ns）。"窗口最大值"是 1 µs 窗口里的最大利用率。
- 延迟分段来自 obs：`wait_rrt` 是请求在请求方门口等表项或窗口位的时间，`rtt` 是网络往返时间（含 owner 端），`total` 是 L1V 看到的端到端时间。
- 下文的"损失"都是 T_变体 / T_Complete，大于 1 说明去掉（或者换掉）的那个部件有用。

## 0. 先看瓶颈在哪：384 GB/s 下链路很闲，瓶颈在请求方的 64 个窗口位

- **baseline 的链路很闲**：所有 workload 的平均链路利用率是 0–5%，p99 不超过 0.30。1 µs 窗口里的最大值大多在 0.1–0.5，只有 PR、shocsort、KM 有 0.66–0.70 的短时突发。
- **baseline 的远程读，延迟大部分花在请求方等表项**：
  - atax：等 3,152 ns，端到端 3,965 ns；
  - MM：等 3,585 ns，端到端 5,108 ns；
  - PR：等 9,329 ns，端到端 10,893 ns；
  - graphtc：等 4,167 ns，端到端 5,085 ns；
  - npbcg：等 4,592 ns，端到端 5,406 ns；
  - gups：等 2,402 ns，端到端 2,823 ns。

  网络往返本身只有 310–900 ns（PR、MM、shocsort 例外，有 1.5 µs，原因是热点 owner，见下一条）。64 项表处于满状态的时间比例是 0.2–0.8。
- **热点 owner**：有 8 个 workload 的远程读集中在一个 GPM 上（"最常访问的目的 GPM"拿到的份额）：PR 1.00（GPM 0）、MM 0.98、graphtc 0.78、atax 0.66、FW 0.66、shocsort 0.62、npbcg 0.61、PA 0.57。原因是放置规则：不到 48 页（192 KB）的 buffer 整个放在 GPM 0，余数页也堆在最后一个 GPM。论文里要说明这一点，否则 PR 的 13.3× 会被质疑。
- **Complete 以后**，下面几个 workload 等表项的时间仍然占端到端的一半以上，而且 64 项表满的时间比例仍有 0.3–0.7：
  - gups：2,203 / 2,622 ns；
  - allreduce：1,070 / 1,643 ns；
  - CFD：958 / 1,268 ns；
  - PA：1,122 / 1,527 ns；
  - npbis：997 / 1,254 ns；
  - sssp：910 / 1,048 ns。

  128 项的组合表也常常是满的。表满停顿（不重复计数的请求数）：MoE 496 万、MG 234 万、PA 140 万、npbcg 133 万、allreduce 115 万、CFD 98 万、IVF 88 万、gups 79 万。
- **结论**：在 384 GB/s、64 项窗口下，凡是能让"每个窗口位、每个表项带更多有用的 line"，或者让"请求根本不用发出去"的部件就有用（打包、请求方合并、M3）；只节省链路字节、或者只调整窗口位怎么分配的部件（M2、分配方式）就没用。

## 1. M1 合并

| | 数据 |
|---|---|
| 平均损失（−merge） | GMEAN 1.111（25 个 workload） |
| 损失大的 | MM 1.611、atax 1.383、FW 1.350、PR 1.257、npbcg 1.218、IVF 1.197、shocsort 1.178、graphtc 1.166、fft2d 1.147、allreduce 1.132、MoE 1.116 |
| 没作用的（≤ 1.01） | gups、SPMV、MT、embbag、BH、KM；sssp 0.954 和 bfs 0.981，去掉以后反而更快 |

**为什么有用：几乎全部来自请求方合并，owner 合并很少**
- **请求方合并的比例**（合并的读 / 远程读）：shocsort 0.86、MM 0.52、atax 0.38、FW 0.36、fft2d 0.36、IVF 0.27、LUD 0.25、npbcg 0.18、bfs 0.17；gups、MT、SPMV ≤ 0.01。
- 合并直接减少发出去的 line。去掉合并后发出的 line 数（括号里是 Complete）：MM 51.6 万（8.1 万，6.4 倍）、shocsort 17.6 万（2.6 万）、FW 80 万（45 万）、atax 241 万（145 万）、fft2d 225 万（157 万）。每少发一条 line，就少占一个窗口位、一个表项一整个往返时间，所以在窗口受限的时候，这就是吞吐。
- **合并到的表项，大多还在排队、没发出去**（挂到排队项 / 挂到已发出项）：atax 57.4 万 / 20.1 万，fft2d 50.9 万 / 22.0 万，PA 16.8 万 / 17.8 万。也就是说，正因为表项要排很久的队，后来的同 line 读才来得及挂上去。合并和"窗口满"是互相成就的：窗口越挤，合并越多。
- **owner 合并**（owner 合并数 / owner 收到的整行读）只有 0–9%：MM 0.18、LUD 0.09、PR 0.09、shocsort 0.07、npbis 0.06、graphtc 0.06，其余 ≤ 0.03。原因：
  1. 同一 GPM 内的重复先被请求方合并或 M3 吃掉了。baseline 下同 GPM 的重复读占比：MM 0.84、shocsort 0.86、I2C 0.53、npbcg 0.51、FW 0.50。
  2. 跨 GPM 的共享在时间上分散。1 µs 窗口内被多个 GPM 读的 line 占远程读的比例：MM 0.96、npbcg 0.75、PR 0.74、graphtc 0.61、npbis 0.59、sssp 0.46。但在 owner 端同时在途的同 line 读只有 0.05–0.34（baseline）。owner 服务一个读只要 10–20 ns（owner 排队 10–15 ns，热点 owner 除外），所以别的 GPM 的读几乎总是在前一个读已经离开 owner 以后才到。

**为什么在 sssp / bfs 上去掉合并反而略快（0.954 / 0.981）**
- 这两个的请求方合并比例很低（0.02 / 0.17），合并的好处很小。
- 合并以后，一个读要等它挂上的那个表项。这个表项可能还在排队等窗口位，合并等待（merge_wait）的平均值是 sssp 201 ns、bfs 172 ns。也就是说，挂上去不一定比自己单独发更快。
- 这两个的分配方式实验也有 ±5% 的波动（sssp：shared 0.941，near 1.041），说明这类不规则 workload 对发送顺序敏感，±5% 以内不要过度解读。

## 2. M1 打包（同页位图包 + 预取捎带）

| | 数据 |
|---|---|
| 平均损失（−pack） | GMEAN 1.222，是 M1 三个部件里最大的 |
| 损失大的 | allreduce 1.826、MoE 1.740、CFD 1.661、PA 1.656、IVF 1.637、atax 1.493、MG 1.343、npbcg 1.303、graphtc 1.295、KM 1.291、fft2d 1.214、npbis 1.202、PR 1.177 |
| 没作用的 | MM 1.005（每包 1.00 条 line）、shocsort 1.000、SPMV、MT、embbag、gups、BH、I2C、sssp |

**为什么有用：不是因为省了字节，而是一个窗口位能带多条 line**
- 去掉打包，发出去的 line 数几乎不变（allreduce：去掉打包 202 万，Complete 204 万；CFD 225 万对 225 万），链路利用率本来也只有几个百分点。
- 打包把同一页的多条 line 放进一个位图包，一个包只占 1 个窗口位，最多带 8 条 line。有效的在途 line 数大约是 64 × 每包 line 数。每包 line 数：KM 2.09、CFD 2.00、fft2d 1.96、allreduce 1.95、PA 1.83、IVF 1.87、MG 1.79、atax 1.78、npbcg 1.67。多 line 包占包数的 40–61%。
- 所以损失和"窗口满的程度 × 每包 line 数"一致：
  - allreduce：窗口满 0.72，每包 1.95 条，损失 1.83；
  - CFD：0.64，2.00 条，1.66；
  - PA：0.40，1.83 条，1.66；
  - IVF：0.31，1.87 条，1.64；
  - 反例 gups：窗口满 0.70，但每包只有 1.06 条（随机访问，同页比例为 0），损失 1.02。
- **还有余量**：baseline 下 16 个周期内的同页比例 allreduce 0.76、embbag 0.83、KM 0.79、MT 0.75、IVF 0.70、atax 0.64，但实际每包平均不到 2 条，离上限 8 条很远。
  - 代码里（`m1ProcessRemoteBatches`），批在等窗口位的时候其实一直开着，同页的新 line 会继续并进来；
  - 窗口一有空位，就按批的先后顺序发最老的批，不管它有几条 line（统计里的 work-conserving flush，atax 80.8 万次，满 8 条才发的只有 1.1 万次）；
  - 另外，128 项的 line 表一满，同页的新 line 根本进不了表，也就并不进批（表满停顿见第 0 节）。

  所以每包 line 数低，是"先发最老的批"加上"line 表满"两个原因造成的，见提案 P1、P2。
- **预取捎带**：被用上的比例大多 0.82–1.00（MG 0.73、MoE 0.67），能省掉 0–21% 的远程请求（atax 0.21、IVF 0.18、allreduce 0.13、fft2d 0.13、PA 0.12）。MT 是反例：捎带了 28.6 万条，用上 0 条。MT 的链路很闲，这些多余的 line 没造成时间损失（MT 各配置都是 1.00）；但到了低带宽网络上就是浪费。

## 3. M1 分配（rtt / shared / near）

| | 数据 |
|---|---|
| shared 对 rtt | GMEAN 0.998。25 个 workload 里，除 sssp（0.941，shared 更快）以外，都在 ±1% 以内 |
| near 对 rtt | GMEAN 1.056，平均更慢 |
| near 更差的 | FW 1.238、fft2d 1.181、npbis 1.179、gups 1.177、I2C 1.170、shocsort 1.140、MG 1.136、CFD 1.083、LUD 1.075 |
| near 更好的 | graphtc 0.934、PR 0.978 |

**为什么 rtt 和 shared 一样：保底份额基本都是借来的**
- 在 rtt 下，Complete 发出的事务里用借来的位发出的比例：MG 1.00、FW 1.00、I2C 0.99、LUD 0.99、PA 0.99、npbcg 0.99、MoE 0.99、allreduce 0.97、fft2d 0.97，最低的 SPMV 也有 0.11。保底份额几乎从来没起过约束作用，所以 rtt 的行为就是共享池。
- 真正的约束是 128 项组合表和 64 个窗口位的总量，不是它们在目的地之间怎么分（见第 0 节）。

**为什么 near 更差：近区的 16 项大多空着**
- 近区 16 项的平均占用只有 0.5–7.1 项。近区满的时间比例 ≤ 0.25。近的请求在近区满了以后借用其余 48 项的次数很多（MG 161 万次、fft2d 89 万、LUD 86 万、FW 54 万）。
- 结果是远处的请求能用的位变少了。从 rtt 换成 near，远程组的平均在途数：allreduce 17.6 → 13.3、shocsort 15.1 → 11.5、PR 17.2 → 12.8、graphtc 14.3 → 11.4、gups 18.3 → 15.3。
- "近的请求排在远的后面"这件事在数据里并不明显。Complete（rtt）下，"表满时有请求在等"的时间比例，近组和远组差不多：allreduce 0.17 / 0.23、CFD 0.28 / 0.18、graphtc 0.19 / 0.23、gups 0.29 / 0.27。Complete 下的平均等待时间，近组和远组只差 1–2 倍（MM 15 / 14 ns，IVF 553 / 521 ns）。所以"给近的留位"解决的是一个不存在的问题，反而浪费了位。
- graphtc 和 PR 上 near 稍好，是因为它们的热点 owner（GPM 0）离不少请求方在 3 跳以内。这属于放置效应，不是一般规律。

## 4. M2 网内多播

| | 数据 |
|---|---|
| −M2（= M1+M3 对 Complete） | GMEAN 0.998；最大收益 1.016（fft2d、FW） |
| M2 是负的 | sssp 0.947、bfs 0.967 |
| M1 → M1+M2 | GMEAN 1.439 → 1.427（24 个 workload；MG 的 M1+M2 挂住，不计）；sssp 1.10 → 0.97，bfs 1.05 → 0.98 |

**为什么几乎没有作用：能多播的东西少，而且多播省的是不缺的资源**
1. **多播包少**：多播包只在 owner 合并之后才有，而 owner 合并只占 owner 读的 0–9%（见第 1 节）。
2. **扇出小**：每个多播包平均只发给 2.0–2.6 个目的地（FW 2.61、KM 2.53、MM 2.37、BH 2.36、PA 2.35、atax 2.29），平均每个包只少发 1–1.6 个响应。少发的响应占全部响应不到 1%（atax：1.6 万 / 145 万）。
3. **省下的是链路字节，而链路平均只用了 1–5%**：节省的链路量最多是全部响应的 0–43%（MM 0.43、FW 0.29、npbcg 0.27）（这是 baseline 统计按理想多播树算的上限，不是 Complete 里实际省下的）。但链路不是瓶颈，省了也不改变时间。
4. **请求方的窗口位不会因为多播提前释放**：每个请求方还是要等到自己那份数据到了，才释放窗口位和表项。所以多播对真正的瓶颈（第 0 节）没有作用。

**为什么在 sssp / bfs 上是负的（还没完全查清）**
- sssp 的 M1 → M1+M2：多播包 7.68 万个，代替了 8.01 万个"合并后逐个单播"的包；远程读的平均延迟没变（1,713 → 1,702 ns），但总时间多了 13%（608 → 689 µs）。加上 M3 以后，多播包降到 1.92 万，负作用缩小到 5%。
- 平均延迟不变而总时间变长，说明慢的是尾部（某些 kernel 的最后几个 WG），不是平均值。可能的原因：
  - 多播在交换机里要等所有分支的出口都有空位才能前进，16 flit 的缓冲区会造成队头阻塞；
  - 多播改变了响应的到达顺序。

  这一次的 M1+M2 运行只开了廉价统计（没有 obs 和 gpm trace），没法区分。要确认，需要在 sssp 的 M1 / M1+M2 上开 `-report-obs-latency -report-gpm-trace` 再跑一对，按 kernel 看尾延迟。

## 5. M3 请求方 L2 保留

| | 数据 |
|---|---|
| −M3（= M1+M2 对 Complete） | GMEAN 1.213（24 个 workload，MG 的 M1+M2 挂住，不计），是三个机制里第二大的（−M1 是 1.358） |
| 损失大的 | PR 6.664、npbcg 1.993、graphtc 1.959、sssp 1.641、MM 1.196、BH 1.160、bfs 1.140、FW 1.127、I2C 1.104、IVF 1.095、CFD 1.084、npbis 1.065 |
| M3 是负的 | allreduce 0.969、PA 0.985（还有 MoE 0.997、LUD 0.996、shocsort 1.000） |
| 只开 M3 | GMEAN 1.278（24 个 workload，和 T2 同一组）；PR 8.27、npbcg 2.87、graphtc 2.37、MM 1.54、sssp 1.52、atax 1.33；shocsort 0.98 |

**为什么有用：远程 line 在一个 GPM 内被反复读，而 L2 有空闲**
- Complete 下，远程读命中请求方 L2 的比例：PR 0.89、graphtc 0.61、BH 0.60、npbcg 0.59、I2C 0.54、sssp 0.47、MM 0.40、npbis 0.29、MG 0.29、embbag 0.29、FW 0.22。
- 这和 baseline 下"远程 line 在数据回来之后又被同一 GPM 读"的比例一致：PR 0.90、npbcg 0.82、graphtc 0.75、BH 0.69、sssp 0.69、I2C 0.64。
- baseline 下 L2 的空闲比例（无效 + 死行）是 0.33–0.99，大多 > 0.7，放得下这些副本。
- M3 的收益大，基本都发生在热点 owner 的 workload 上：PR、MM、graphtc、npbcg、atax 的热点份额是 0.61–1.00。M3 把对热点 owner 的反复读变成本地命中，所以等表项的时间也随之下降（PR 9,329 → 2,070 ns），并且把窗口位让给别的读。PR 的 mesh 总字节从 2.27 GB 降到 0.14 GB。

**L2 污染：按 DRAM 读次数看，没有污染**
- Complete 和 M1+M2 的 DRAM 读次数之比都是 1.000（embbag 1.050 例外）。本地 L2 的缺失率在两者之间也几乎相同。
- 原因是"保护本地干净行"的规则：M3 的填充不替换本地的干净行，它丢掉的填充很多（atax 41.4 万次、MoE 38.3 万次、allreduce 5.7 万次、sssp 10.5 万次）。

**M3 在 allreduce / PA 上略负（−3% / −1.5%）的原因：填充几乎没用，却占了 L2 写带宽，还多了一次探测**
- 被再次读到的填充 / 实际装进去的填充：allreduce 0.02（5,080 / 22.2 万）、fft2d 0.01、CFD 0.17、PA 0.13、gups 0.10、MoE 0.09；对比 PR 0.98、I2C 0.83、MM 0.77、graphtc 0.75、BH 0.72。
- 填充没有造成额外的 DRAM 读，但每次填充要占 L2 的写端口和 typed filter 的更新。命中路径上还多一次探测，平均 13–86 ns（atax 86 ns）。

## 6. 小结：每个部件起作用的条件

| 部件 | 起作用的条件 | 在本次 25 个 workload 里 |
|---|---|---|
| M1 打包 | 窗口满 + 同页的 line 在短时间内一起到 | 最大贡献者 11 个；GMEAN 损失 1.222 |
| M3 | 同一 GPM 反复读远程 line（热点 owner 时尤其明显） | 最大贡献者 7 个；GMEAN 损失 1.213 |
| M1 合并 | 同一 GPM 内同 line 读多，并且表项要排队 | 最大贡献者 3 个（MM、FW、shocsort）；GMEAN 损失 1.111 |
| M1 分配 | 理论上是近、远争抢窗口位；实际上保底份额 70–100% 是借来的 | rtt ≈ shared；near 平均慢 5.6% |
| M2 | 链路是瓶颈，并且同一时刻有多个 GPM 读同一 line | 384 GB/s 下两个条件都不成立；GMEAN 0.998 |

所有部件都贡献很小（< 2%）的 workload：gups、MT、SPMV、embbag。原因各不相同：
- MT、SPMV：等表项的时间只有 14–17 ns，本来就不受远程访问的限制；
- gups：随机单 line 访问，没有同页、没有重复、没有复用，唯一的限制是 64 个窗口位乘往返时间；
- embbag：等表项的时间只有 117 ns，远程延迟主要在往返本身。

## 7. 改进机制的提案（只是提案，没有实现）

每条都给出依据、预期收益和实现代价。收益是按本次统计粗估的，没有跑过。

### P1（M1 打包 + 表）：按页组织的请求方表——一个表项跟踪一页的位图，而不是一条 line
- **依据**：
  - Complete 下 128 项组合表经常是满的（第 0 节：MoE 496 万、MG 234 万、PA 140 万、npbcg 133 万、allreduce 115 万、CFD 98 万次停顿）；
  - 同页的 line 很多（同页比例 0.33–0.83）；
  - 现在每条 line 占一个表项。
- **做法**：表项 = (owner, 页号, 64 位 line 位图, 每条 line 的等待链)。容量仍然是 128 项。窗口位的规则不变，一个位图包占 1 位。
- **预期**：同页比例高、表满停顿多的 workload，表项的有效容量可以变成 1.5–2 倍（按每包 1.8–2.1 条 line 估），包括 allreduce、CFD、PA、IVF、MG、npbcg、MoE。表满停顿会大幅减少。这些 workload 的 Complete 还有 30–60% 的时间在等表项，按这个比例估，可以再快 5–15%。gups、MT、SPMV 不变。
- **代价**：中等。
  - 硬件上：每项多 64 位位图和每条 line 的等待链头，表的存储增加约 1.5 倍；cuckoo 的键从 line 换成页。
  - 模拟器上：改 `m1m2_compose.go` 的索引（`m1IndexLine` 按页建索引）和 `remoteLines` 的分配点。
  - 不改 64 项窗口和表项数，符合用户"表保持 64 项"的要求。

### P2（M1 打包）：按批的大小决定发送顺序，代替先来先发
- **依据**：
  - 每包平均 1.0–2.1 条 line，上限是 8；
  - 16 个周期内的同页比例是 0.64–0.83（allreduce、embbag、KM、MT、IVF、atax）；
  - 现在窗口一有空位就发最老的批，几乎全是这种情况（atax：80.8 万次这样发出，满 8 条才发的只有 1.1 万次）；
  - 打包的收益和"窗口满的程度 × 每包 line 数"一致（第 2 节）。
- **做法**：
  - 窗口满时，空出来的位优先给 line 数最多的批；
  - line 数相同，给最老的；
  - 为了不饿死单 line 的批，等待超过 T（比如 1 个往返时间，约 400 ns）的批优先。
  - 窗口不满时行为不变，所以不增加空载延迟。
- **预期**：窗口满 ≥ 0.3 的 workload（allreduce、CFD、PA、IVF、MG、fft2d、npbis、sssp、graphtc、PR），每包 line 数从约 1.8 提高到 2.2–2.8。按 P1 同样的口径，大约再快 3–8%。和 P1 叠加时收益不简单相加，因为两者都是在扩大有效容量。
- **代价**：小。只改 `m1ProcessRemoteBatches` 选批的顺序，加一个按 line 数的优先级比较，不增加存储。
### P3（M3）：按复用预测决定是否填充（M3 admission / bypass）
- **依据**：
  - 被再次读到的填充 / 装进去的填充，allreduce 0.02、fft2d 0.01、gups 0.10、PA 0.13、CFD 0.17、MoE 0.09，而 PR、I2C、MM、graphtc、BH 是 0.72–0.98；
  - M3 在 allreduce（−3%）和 PA（−1.5%）上是负的；
  - 没有 DRAM 污染（DRAM 读之比都是 1.000），所以问题只在 L2 写带宽和探测延迟。
- **做法**：
  - 每个请求方 GPM 按 kernel 统计"填充以后被再次读到的比例"（已有 `remote_useful_two_touch_fills` / `remote_l2_two_touch_installed_fills` 的计数）；
  - 低于阈值（比如 0.2）时，本 kernel 后面的远程 line 不填、不探测；
  - 下一个 kernel 开始时重新试一段。
- **预期**：allreduce、PA 回到不开 M3 的水平（+1.5–3%），MoE、fft2d、gups、CFD 不变或略好。复用多的 workload 不受影响。平均收益约 0.5–1%，作用主要是让 M3 "不会变慢"，方便回应审稿人。
- **代价**：小。每 GPM 两个计数器加一个比较器，复用已有的 kernel 边界钩子。

### P4（M1 分配）：去掉按距离分份额，用共享池
- **依据**：
  - rtt 和 shared 在 25 个 workload 上的差别都在 ±1% 以内（sssp 除外，−6%），因为 70–100% 的事务是借位发出的；
  - near 平均慢 5.6%，而且近区 16 项大多空着；
  - "近的请求排在远的后面"在数据里不明显（第 3 节）。
- **做法**：分配方式就用 shared（硬件上最简单）。窗口位给谁，交给 P2 的"按批大小排序"决定。
- **预期**：
  - 时间基本不变，省掉每个目的地的份额寄存器和借用逻辑（48 个目的地 × 计数器）；
  - 论文里可以把"按距离分配"写成"做过、没用"的负面结果，用第 3 节的统计说明原因，回应"堆技术"的质疑。
- **代价**：没有（删掉逻辑）。
### P5（M2）：不再把 M2 作为 384 GB/s 下的贡献，只在低带宽网络上评估；配合 owner 端短暂停留
- **依据**：
  - 384 GB/s 下 −M2 的 GMEAN 是 0.998；
  - 链路平均利用率 1–5%；
  - owner 合并只占 owner 读的 0–9%，每个多播包的扇出 2.0–2.6；
  - baseline 下 1 µs 窗口内的跨 GPM 共享比例却很高：MM 0.96、npbcg 0.75、PR 0.74、graphtc 0.61、npbis 0.59、sssp 0.46。owner 端同时在途的同 line 只有 0.05–0.34。也就是说，共享存在，但到达 owner 的时间错开了。
- **做法（两步）**：
  1. 先在 48 GB/s（`-bandwidth=3`，之前停掉的 v3net 配置）重跑 M1 对 M1+M2。那里链路会成为瓶颈，看 M2 有没有用。
  2. 如果有用，再加 owner 端短暂停留：owner 收到一条已知被多个 GPM 共享的 line 的读（用 typed filter 标记），先挂在 owner 合并表里 T 纳秒（比如 100–200 ns，约等于跨 GPM 读之间的间隔）再发出，攒更多读一起多播。只对被标记的共享 line 做，避免给所有读都加延迟。
- **预期**：
  - 384 GB/s 下，停留只会增加延迟，预期没有收益，甚至更慢（停留的时间直接加到请求方的窗口占用上）；
  - 48 GB/s 下，如果链路成为瓶颈，MM、npbcg、PR、graphtc 这类共享多的 workload 可能有 10% 量级的收益。这需要实验确认，现在没有数据支持具体数字。
- **代价**：第一步只是跑实验。第二步中等：owner 合并表加一个定时器和共享标记查询。
- **另外**：sssp / bfs 上 M2 是负的（−5% / −3%），原因还没查清（第 4 节），建议先补一对带 obs 的运行。

### P6（放置，不是机制）：小 buffer 按页分散，或者把"热点 owner"单独作为一种场景报告
- **依据**：PR、MM、graphtc、npbcg、atax、FW、shocsort、PA 的远程读，57–100% 集中在一个 GPM 上。Complete 的大加速（PR 13.3×、npbcg 4.4×、graphtc 3.7×、atax 2.7×、MM 2.7×）基本都在这些 workload 上，靠的主要是 M3 和合并来缓解热点。
- **建议**：这不是要实现的机制，而是论文里怎么报告的问题。
  - 要么另做一组"小 buffer 按页轮转放置"的 baseline 作为敏感性分析（这是配置偏离，要用户确认）；
  - 要么在论文里把它明确写成"不到 192 KB 的 buffer 默认放在 GPM 0 的 wafer 运行时"的现实场景。
- **代价**：按页轮转放置需要改 driver 的放置函数，要另起一组运行。
