## 动机（已有数据）

- 远程访问受端点窗口限制：RDMA 只放行 64 个在途请求，单对带宽 = 64 × 64 B ÷ 往返时间（1 跳 26.4、6 跳 8.0 B/周期，T14 诊断 A），链路利用率 < 3%。
- T17：每个 GPM 同时有 270–400 个远程读在途，请求堵在 RDMA 门口；排队占远程延迟 80% 以上（闭环模型）。按模型，窗口放大后吞吐最多约 7 倍（T17 的 O2b 还没跑，P12 验证）。
- incast：k 个 GPM 读同一 owner 时总带宽封顶约 113 B/周期，相同 line 的请求不合并（T14）。
- 负载下远程延迟随距离增长：同一请求方内约 180–360 ns/跳（空载 72）。

## 设计（草案）

**A. 请求方（取代现有 m2 的实现，沿用 typed filter 的硬件和 CACTI 数据）**
- **在途表**：cuckoo 表，key = 远程 line 地址，项内容 = 指纹 + 目的 GPM + 等待者链表指针。新请求命中 → 挂到已有请求上（合并），不再发出；响应返回 → 唤醒等待者并**删除**该项（需要删除，所以用 cuckoo 而不是 Bloom）。
- **正确性**：指纹只做快速筛选；合并前必须用完整地址核对（或每项存完整 tag，即 cuckoo 哈希表）。假阳性如果直接合并，会返回错误数据。
- **窗口**：总在途上限 W（扫描 64 / 256 / 1024 / 4096，各自给面积）；按目的地的往返时间分配 credit（credit_d ∝ RTT_d，按 Little 定律让每个目的地都能用满），空闲 credit 可以借用。
- 响应和请求按表的索引匹配，不用全相联 CAM。

**B. owner 端**
- 表项 = 指纹 + 48 位请求者位图 + 状态。同一条 line 只读一次 L2/HBM，返回时沿 mesh 的 XY 树多播给位图里的所有 GPM；表满、超时或只有一个请求者时退化为单播。
- 写请求：对同一 line 的读写顺序要保证（写到达时，已合并的读先完成或按顺序处理），设计时写清楚。

**C. 和 HPCA 版 m2 的关系**：保留“请求方聚合 / 去重”的说法和 typed filter 的面积数据；新增 owner 端合并多播和按距离分配窗口，这两点是 wafer 特有的、也是回应“机制太通用”的关键。

## 需要的统计
