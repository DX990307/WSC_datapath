## 设计思路（提案）

- 把 7×7 mesh 划成多个**区域**（先试 3×3，边缘区域可以更小，区域大小可配置）。
- 每个远程 page 在每个区域里有一个固定的**代理 GPM**，用页地址哈希在区域内选出来，思路类似 R-NUCA 的 rotational interleaving。
- **读路径**：requester 的 L2 miss，而且目标是远程 page 时：
  - 如果 home 的距离超过阈值（可配置，默认等于区域直径），先把请求发给代理（1–2 跳）
  - 代理的 L2 命中，就直接返回
  - 代理的 L2 没命中，由代理向 home 取数据，返回后用代理 L2 中**空闲或已死**的 way 缓存一份（**不挤掉本地数据**，沿用原 CuPath 的规则），同时回复 requester
  - 代理会合并同一区域内多个 GPM 发来的同 line 请求（区域级的合并）
- **近处的 home 直接访问**，不走代理。
- **写路径**：写请求仍然直接发给 home。代理上的副本在 kernel 边界失效（由机制 2 / T8 决定失效哪些）。
- 每个区域对每个 page 只存一份副本，容量效率比“每个 requester 各存一份”高。

## 为什么这样设计（对应审稿意见）

- 把闲置的 L2 变成分布式的远程缓存，同时坚持“不新增 cache 层级”（回应 E 的“这个说法只有在和加了 cache 层级的设计比较时才有意义”）
- GPM 内部的合并升级为跨 GPM 的合并（比 AdCoalescer、MSHR 合并更进一步）
- 和 MCM-GPU L1.5、SAC、selective replication 的区别：那些都是按模块或按 requester 设计的，不考虑距离

## 主要风险

- **HMG（Ren et al., HPCA'20）是最接近的工作**：它在 GPU 层级为 GPM 之间的远程数据设了一个 home。区分点：HMG 的层级由封装边界固定；wafer 上没有封装边界，区域按距离划分，是否走代理也随距离自适应。
- 代理没命中时要多走 1–2 跳，所以要用距离阈值来控制。
- 如果 M1 的区域共享占比太低，这个机制就不成立。
