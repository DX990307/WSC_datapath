## 设计思路（提案）

- 每个 owner GPM 在一个 kernel 执行期间，把**被写过的 page** 加入一个 Bloom 签名。签名大小可配置，先试 2 KB。
- 到了 kernel 边界，把所有 owner 的签名做 OR 合并，然后广播出去（经由中心 CPU tile，或者沿 mesh 树形广播；广播的延迟和字节数都要建模）。
- 各个 GPM（以及 T7 中的代理）**只失效命中签名的远程副本**，其余副本跨 kernel 保留。
- **正确性由结构本身保证**：Bloom filter 不会有假阴性，所以被写过的 page 一定会被失效；假阳性只会让一些没被写过的行也被失效，影响的是性能，不影响正确性。
- 这样就把“为什么用近似结构”讲清楚了：只在出错方向安全的地方用近似结构，其他地方一律用精确结构（D6：In-Flight 改用精确 CAM）。

## 为什么这样设计（对应审稿意见）

- A：只读的权重和图结构可以跨 kernel 保留
- B：一致性语义明确。在 GPU 的 scoped consistency 下，跨 GPM 的可见性本来就只在 kernel 边界和同步点保证，签名就在这两种时刻生效
- C 和 E：近似结构的出错方向是安全的

## 需要处理的细节

- **kernel 内部的同步点**（比如 grid sync 或 system-scope 的 fence）：先按“全部失效”处理，作为保守的回退方案，并统计这种情况出现的频率。
- **atomic**：原子操作总是直接发给 home，不在副本上执行。
- **签名的 false positive rate**：报告它随签名大小的变化。
- **广播开销**：kernel 边界多出来的延迟和字节数。

## 主要风险

- Bulk（ISCA'06）等工作已经用过签名，要讲清楚应用场景的区别：这里是 GPU 的 kernel 边界，配合区域副本使用。
- 如果 M2 的跨 kernel 复用很低，这个机制就没有收益。
