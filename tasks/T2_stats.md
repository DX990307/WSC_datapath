# T2 新增统计（W1 的核心）

> 🔒 **执行前必做**：按 `../CONFIG.md` 第 3 节做配置确认（检查文件有没有变 → 打印完整参数 → 列出和论文配置的差异 → **等用户确认**）。论文配置不可修改（用户 10-13）。

**状态**：`[已定]` · **周次**：W1 · **依赖**：T0 · **被依赖**：go/no-go 关口、T6、论文的特征分析部分

> **项目背景（重复）**：CuPath（HPCA 2027 #1329 被拒）改投 ISCA 2027。审稿人认为原设计（用 typed Cuckoo Filter 串起三个机制）新颖性不足。现在提出的新主线 `[提案]` 是**利用 wafer-scale 特有的问题**：
> - 机制 1（T7）：按距离分区域做远程数据复制。每个区域里为每个远程 page 设一个代理 GPM，这个区域内的请求都先发给代理。
> - 机制 2（T8）：用写签名做选择性失效，让只读副本跨 kernel 保留。
>
> 平台：48 GPM，7×7 mesh，中心是 CPU tile；远程距离 3.0–6.6 跳，延迟 465–7,787 周期。
> 索引：`../README.md` · 背景：`../00_background.md` · 进度写入：`../STATUS.md`

## 为什么做

1. **决定新主线能不能走。** 机制 1 成立的前提是：同一区域内有多个 GPM 读同一条远程 line（M1）。机制 2 成立的前提是：远程数据在 kernel 之间被再次读取，而且这期间没有被写过（M2）。如果这两个比例很低，新主线就不成立，要退回原方案。
2. **回应审稿人 C**：C 说动机测量和机制实际能用到的机会对不上，要报告实际能捕获的比例，以及实际访问的 footprint。
3. **回应审稿人 A、B、C**：他们要网络层的数据（packet 数、字节数）。
4. **证明 cache 和 HBM 确实被压满了**：模拟只截断跑了开头一部分，要证明已经到达稳态。

## 要做什么

先读代码，找到 NI、L2、HBM controller 和 mesh 里合适的位置插统计点。**所有统计都按 kernel 分段输出**（kernel 编号作为一个维度），文件放在 `results/<exp_id>/stats/`。

| 编号 | 统计 | 定义 | 输出 |
|---|---|---|---|
| **M1** | 跨 GPM 共享度 | 每个 kernel 内，每条远程 line（按 64B 对齐）被多少个不同的 requester GPM 读过 | (a) 共享者数量的分布，按 1 / 2 / 3–4 / 5–8 / >8 分桶，**按远程读次数加权**；(b) 按“请求者到 home 的跳数”分桶的共享度；(c) **区域共享占比**：给定区域划分（默认把 7×7 切成 3×3 的块，边缘不够 3 的就用小块；区域大小作为参数），统计“同一区域内至少 2 个 GPM 读了同一行”的远程读占所有远程读的比例 |
| **M2** | 跨 kernel 复用 | kernel k 读过的远程 line，在 k+1 及之后被①同一 GPM、②同一区域再次读取的比例；以及这些 line 所在的 page 在 kernel k 中**被写过**的比例 | 每对相邻 kernel 输出一行，外加汇总 |
| **M3** | 远程读的跳数分布 | 每次远程读的跳数（曼哈顿距离），以及每个跳数下的平均端到端延迟 | 直方图 |
| **F** | 实际访问的 footprint | 去重后的 line 数 × 64B，同时按 page 去重统计 | 每个 kernel 一行，外加总计 |
| **W** | 按时间窗口的指标 | 窗口默认 10k 周期（可配置）：本地 L2 命中率、HBM 带宽利用率（相对峰值）、NI 请求表占用率、mesh 链路利用率（平均值和最大值） | 时间序列 CSV |
| **N** | 网络层 | 请求 packet 数、响应 packet 数、总字节数，同时按“同 line 合并”和“同 page 打包”分别计数（如果原 CuPath 开着） | 汇总 |

以上统计的汇总值写进 `summary.csv` 的对应字段，字段定义见 T0。

## 注意

- M1 和 M2 需要记录每条 line 的访问者集合，内存开销可能很大。可以用按 kernel 清空的 map，或者用一个 48-bit 的 bitmap 表示访问过的 GPM 集合。
- 区域的划分方式要做成参数，后面 T7 会扫描不同的区域大小。
- **这个任务只做统计，不改变任何模拟行为。**


## T11 发现的现成统计（10-13，Cowork 侧补充）

fork 里已经有 `-report-l2-source`（`akkalat/baseline/runner/flag.go:207`），输出 `<metric>_l2_source_*.csv`：
- `_data_source.csv` 的 `source` 列能区分 `local_/remote_` × `l2_cache / l2_mshr / dram / write_allocate`，每行带 requester GPM、provider GPM 和跳数。
- `_remote_matrix.csv` 给出每对 GPM 的远程访问次数、字节数、平均延迟和跳数。

**M3（跳数分布）基本可以直接从这些统计算出来**；M1 和 M2 可以在同一个 tracer 上扩展：加上 cache line 地址和 kernel 编号，按 kernel 统计每条 line 的访问者集合。不要另外写一套追踪逻辑。

注意 GPM 有两套编号：driver ID 是 1–48；组件名 `GPU[t]` 里的 t = x + 7y，中心格 t = 24 留给 driver。ID ≤ 24 时 t = ID − 1，ID ≥ 25 时 t = ID。区域划分要用 t 计算坐标。
