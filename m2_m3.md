# M2/M3 Implementation Spec

## Requester-Side RDMA Bitmap Batching + Owner-Side Fair Service Queue

This document is written for an implementation agent. It describes **what to implement**, **where to insert it conceptually**, **what state and counters to add**, and **how to validate the result**.

The two mechanisms are:

```text
M2: Requester-side RDMA bitmap batching
M3: Owner-side per-requester fair service queue
```

They are designed for a wafer-scale GPU / WSG-style system where a requester GPU may access cachelines owned by another GPU.

---

## 0. High-Level Story

Enhanced L1/L1V exposes many outstanding remote cacheline requests. If every remote miss is sent immediately as a standalone RDMA/NoC packet, the system creates many small packets, high flit-hop traffic, and high owner endpoint injection pressure.

M2 batches compatible remote cacheline requests at the **requester side**:

```text
same requester
same owner
same address space / PID
same physical page
same access type
```

into one bitmap RDMA request.

M3 schedules batched requests at the **owner side** so one requester cannot monopolize the owner just because its batches are large or frequent.

The full path is:

```text
Requester GPU
  L1 / L1V miss
      |
      v
  remote-owner lookup
      |
      v
  M2 requester-side RDMA batch queue
      |
      v
  NoC / RDMA bitmap request
      |
      v
Owner GPU
  M3 per-requester fair service queue
      |
      v
  owner L2 / owner DRAM service
      |
      v
  batched response / per-line responses
      |
      v
Requester GPU
  demultiplex response to original waiting requests
```

---

## 1. Non-Goals

Do not implement these in the first version:

```text
page migration
page replication
coherence protocol redesign
store batching
atomic batching
owner-side data placement
global cross-requester batching
ML-based scheduling
```

First version should support:

```text
remote read-only cacheline requests
same-page bitmap batching
bounded waiting
owner-side requester fairness
basic response demultiplexing
metrics/counters
```

Stores, atomics, fences, and unknown operations should bypass M2 and can also force conflicting pending read batches to flush.

---

## 2. Terminology

```text
requester GPU:
  GPU tile that issues the original L1/L1V miss.

owner GPU:
  GPU tile that owns the target physical cacheline/page and serves the remote request.

remote request:
  requester_gpm != owner_gpm.

cacheline:
  assumed 64B unless simulator config says otherwise.

page:
  assumed 4KB unless simulator config says otherwise.

bitmap RDMA request:
  one network request for a page plus a line bitmap selecting requested cachelines.

batch:
  a group of compatible remote read requests represented by one bitmap packet.
```

Default constants:

```text
CACHELINE_BYTES = 64
PAGE_BYTES = 4096
LINES_PER_PAGE = 64
BITMAP_BITS = 64
```

If simulator constants differ, use simulator values and report them in the output metrics.

## 3. Required Request Fields

The implementation needs access to these fields for each remote miss:

```text
requester_gpm
owner_gpm
pid
physical_address
page_paddr
cacheline_addr
access_type
arrival_time
original transaction / callback / request object
```

Derived fields:

```text
line_offset = (cacheline_addr - page_paddr) / CACHELINE_BYTES
```

Requirements:

```text
0 <= line_offset < LINES_PER_PAGE
page_paddr must be aligned to PAGE_BYTES
cacheline_addr must be aligned to CACHELINE_BYTES
```

If alignment is uncertain, add assertions or debug warnings.

## 4. M2: Requester-Side RDMA Bitmap Batch Queue

### 4.1 M2 Placement

Insert M2 after the requester knows the request is remote and knows the owner GPU:

```text
L1/L1V miss
  -> local/remote decision
  -> owner_gpm resolved
  -> M2 batch queue
  -> NoC/RDMA send
```

Do not place M2 before owner resolution. The batch key requires `owner_gpm`.

Do not place M2 at owner side. Owner-side arbitration is M3.

### 4.2 M2 Batch Key

Two remote read requests can be batched only if this key is identical:

```text
requester_gpm
owner_gpm
pid
page_paddr
access_type
```

In code:

```go
type M2BatchKey struct {
    RequesterGPM int
    OwnerGPM     int
    PID          int
    PagePAddr    uint64
    AccessType   AccessType
}
```

If the simulator has address spaces beyond PID, include address-space ID as well.

### 4.3 M2 Batch State

Each active batch should store:

```go
type M2Batch struct {
    Key              M2BatchKey
    LineBitmap       uint64
    LineCount        int
    OldestArrival    sim.VTimeInSec
    NewestArrival    sim.VTimeInSec
    Requests         []*RemoteRequestOrTransaction
    PerLineRequests  map[int][]*RemoteRequestOrTransaction
    FlushReason      M2FlushReason
}
```

Notes:

```text
Requests:
  all original requests in this batch.

PerLineRequests:
  maps line_offset -> original requests waiting for that line.
  This is needed to wake duplicate reads to the same line.

LineBitmap:
  one bit per cacheline in the page.

LineCount:
  popcount(LineBitmap), not len(Requests).
```

Duplicate line reads:

```text
If two requests ask for the same cacheline, do not set a new bitmap bit.
Keep both original waiters in PerLineRequests[line_offset].
```

### 4.4 M2 Config Knobs

Add simulator flags or config fields:

```text
-m2-rdma-batch-enable
-m2-max-batch-lines
-m2-max-wait-ns
-m2-batch-table-entries
-m2-max-packet-bytes
-m2-bypass-stores
-m2-bypass-atomics
```

Initial defaults:

```text
m2-rdma-batch-enable = false
m2-max-batch-lines = 8
m2-max-wait-ns = 50
m2-batch-table-entries = 64
m2-max-packet-bytes = unlimited for first prototype
m2-bypass-stores = true
m2-bypass-atomics = true
```

### 4.5 M2 Add Request Algorithm

Pseudocode:

```text
on remote request arrival at requester:
  if M2 disabled:
      send normal remote cacheline request
      return

  if request is not batchable:
      flush conflicting batches if needed
      send normal remote cacheline request
      record bypass counter
      return

  key = batch_key(request)

  flush expired batches for this requester

  if key not in batch_table and batch_table is full:
      flush oldest batch

  batch = batch_table[key] or new batch
  add request to batch

  if batch.line_count >= max_batch_lines:
      flush batch with reason FULL
```

Batchable request condition:

```text
is_remote == true
access_type == read
line_offset in [0, LINES_PER_PAGE)
owner_gpm is valid
page_paddr is valid
```

Non-batchable requests:

```text
local request:
  not handled by M2

store/atomic/fence:
  flush conflicting read batch if it targets same key/page
  bypass M2

unknown access:
  bypass M2
```

### 4.6 M2 Flush Conditions

Flush a batch when any of these happens:

```text
line_count >= max_batch_lines
oldest request age >= max_wait_ns
batch table full and a new key needs insertion
packet size exceeds max_packet_bytes
store/atomic/fence conflicts with the batch
simulation is ending / drain event
```

Flush reasons:

```go
type M2FlushReason int

const (
    M2FlushFull M2FlushReason = iota
    M2FlushTimeout
    M2FlushCapacity
    M2FlushConflict
    M2FlushDrain
)
```

### 4.7 Timeout Implementation

There are two acceptable first implementations.

Option A: lazy timeout check:

```text
On every new request arrival, scan active batches for this requester.
Flush batches whose oldest_age >= max_wait_ns.
```

Pros:

```text
simple
good enough for first implementation
```

Cons:

```text
if no new requests arrive, a batch may sit too long unless drain logic exists
```

Option B: scheduled timeout event:

```text
When creating a new batch, schedule a flush event at oldest_arrival + max_wait_ns.
If the batch already flushed before the event, ignore event.
```

Pros:

```text
more accurate
better for timing simulator
```

Cons:

```text
more integration work
```

Recommended path:

```text
Start with lazy timeout + explicit drain.
Move to scheduled timeout if timing artifacts appear.
```

### 4.8 M2 Packet Construction

When flushing a batch, create one RDMA bitmap request:

```go
type M2BitmapRDMARequest struct {
    RequesterGPM int
    OwnerGPM     int
    PID          int
    PagePAddr    uint64
    AccessType   AccessType
    LineBitmap   uint64
    LineCount    int
    OriginalReqs []*RemoteRequestOrTransaction
}
```

The packet destination is `owner_gpm`.

The owner should receive the bitmap request and know:

```text
which page to access
which lines to return
which requester to respond to
```

### 4.9 M2 Response Demultiplexing

The response must wake every original request.

First prototype response model:

```text
owner returns one batched response containing all requested cachelines
requester demultiplexes lines by bitmap offset
each original request receives its cacheline data
```

Implementation state needed:

```text
line_offset -> list of original request waiters
```

If the simulator does not model actual data payload:

```text
use the batched response as a timing/completion event
complete each original request when the response arrives
```

If the simulator does model data:

```text
ensure each original request receives only its requested cacheline
not the full page
```

## 5. M3: Owner-Side Fair Service Queue

### 5.1 M3 Placement

Place M3 at the owner GPU after RDMA/NoC request arrival and before owner L2/DRAM service:

```text
NoC/RDMA packet arrives at owner
    |
    v
M3 per-requester fair service queue
    |
    v
owner L2 / owner DRAM service
```

M3 handles both:

```text
normal remote cacheline requests
M2 bitmap batched requests
```

### 5.2 Why M3 Is Needed

M2 can create larger and more efficient batches. However, if one requester has many batchable requests to the same owner, the owner may repeatedly serve that requester while others wait.

M3 prevents:

```text
owner monopolization
requester starvation
p95/p99 wait blowup
unfair owner endpoint service
```

M3 should preserve most batching/locality benefit while bounding unfairness.

### 5.3 M3 State

Per owner GPU:

```go
type M3OwnerFairQueue struct {
    OwnerGPM int
    Queues map[int]*M3RequesterQueue  // requester_gpm -> queue
    Deficit map[int]int               // requester_gpm -> credits
    LastServedRequester int
    ConsecutiveServes int
}
```

Per requester queue:

```go
type M3RequesterQueue struct {
    RequesterGPM int
    Items []*OwnerServiceRequest
    OldestArrival sim.VTimeInSec
}
```

Service request:

```go
type OwnerServiceRequest struct {
    RequesterGPM int
    OwnerGPM int
    IsBatched bool
    LineCount int
    LineBitmap uint64
    PagePAddr uint64
    ArrivalAtOwner sim.VTimeInSec
    OriginalPacket interface{}
}
```

### 5.4 M3 Config Knobs

Add flags/config:

```text
-m3-owner-fair-enable
-m3-fair-quantum-lines
-m3-max-consecutive-batches
-m3-age-boost-ns
-m3-hard-age-limit-ns
```

Initial defaults:

```text
m3-owner-fair-enable = false
m3-fair-quantum-lines = 8
m3-max-consecutive-batches = 2
m3-age-boost-ns = 100
m3-hard-age-limit-ns = 500
```

### 5.5 M3 Scheduling Policy

Use a simple hybrid:

```text
Deficit Round Robin + consecutive-service cap + age escape
```

Why:

```text
M2 packets have different line_count.
Serving a 16-line batch should cost more than serving a 1-line request.
DRR handles variable-size packets better than naive round-robin.
Consecutive cap prevents one requester from repeatedly winning.
Age escape prevents starvation.
```

### 5.6 M3 Request Cost

Cost can be defined as:

```text
cost = max(1, line_count)
```

For non-batched request:

```text
line_count = 1
cost = 1
```

For batched request:

```text
line_count = popcount(line_bitmap)
cost = line_count
```

Later, a flit-based cost can be used:

```text
cost = request_flits + response_flits
```

Start with line-based cost.

### 5.7 M3 Select Algorithm

Pseudocode:

```text
on owner ready to serve next remote request:
  if M3 disabled:
      serve FIFO arrival order
      return

  if any request age >= hard_age_limit_ns:
      serve oldest request globally
      return

  for each active requester:
      deficit[requester] += fair_quantum_lines

  candidates = requesters with non-empty queue

  skip requester if:
      requester == last_served_requester
      consecutive_serves >= max_consecutive_batches
      other requesters have pending work

  choose first requester whose deficit >= cost(front_request)

  if no requester has enough deficit:
      add another quantum or choose oldest requester

  serve front request
  deficit[requester] -= cost(request)
  update last_served_requester and consecutive_serves
```

Age boost:

```text
If front request age >= age_boost_ns:
    reduce effective cost or increase requester priority.
```

Simple first version:

```text
hard-age oldest-first escape is enough.
Add age boost later if needed.
```

### 5.8 M3 Response Path

M3 decides service order only. It should not change the semantics of a request.

For a normal request:

```text
serve one cacheline and send normal response
```

For an M2 batched request:

```text
serve all requested bitmap lines
send batched response to requester
requester demuxes response to original waits
```

M3 can optionally split a very large batched request in a later version. Do not implement splitting in the first version unless needed.

## 6. M2 + M3 Interaction

M2 reduces packets. M3 prevents the reduced packets from becoming unfair service bursts.

Important:

```text
M2 is requester-local.
M3 is owner-local.
They should be independently enableable.
```

Experiment matrix should include:

```text
baseline
M2 only
M3 only
M2 + M3
```

Expected behavior:

```text
M2 only:
  best packet/flit reduction
  may increase owner monopolization

M3 only:
  improves fairness
  limited packet reduction

M2 + M3:
  most packet reduction
  bounded owner fairness/tail latency
```

## 8. Correctness Checks

### 8.1 M2 Correctness

Add assertions:

```text
all requests in a batch have same key
line_offset is within bitmap range
LineCount == popcount(LineBitmap)
each original request completes exactly once
no store/atomic is batched with reads
batch never crosses page boundary
batch never crosses owner boundary
```

Debug mode:

```text
record every batch:
  key
  bitmap
  line_count
  original request IDs
  flush reason
```

### 8.2 M3 Correctness

Add assertions:

```text
every owner-side packet is eventually served
no requester queue loses packets
deficit never underflows unexpectedly
hard-age request is served when limit is reached
non-batched packets still complete correctly
batched packets still complete all original lines
```

### 8.3 Determinism

Tie-breakers should be deterministic:

```text
arrival time
sequence number
requester_gpm
page_paddr
cacheline_addr
```

Avoid random scheduling in the first implementation.

## 11. Expected Workload Behavior

Likely positive workloads:

```text
im2col
stencil2d
spmv
matrixmultiplication variants
LLM-like remote-heavy kernels
```

Likely weak or negative-control workloads:

```text
pagerank
highly irregular graph workloads
workloads with low remote ratio
workloads with same owner but low same-page locality
```

Do not force M2 to look good on all workloads. A good policy should naturally produce small batches and low wait on weak-locality workloads.

## 12. Success Criteria

M2 success:

```text
remote request packet reduction >= 20% on several remote-heavy workloads
flit-hop reduction >= 15-20%
avg batch size >= 1.5 on useful workloads
p90 batch size >= 4 on some workloads
p95 wait <= 50-100 ns for practical configs
```

M3 success:

```text
owner max consecutive service decreases significantly
Jain fairness index improves
p95/p99 owner wait decreases or is bounded
M3 loses only modest M2 packet/flit benefit
```

Full M2+M3 success:

```text
preserves most M2 packet reduction
reduces owner monopolization
improves or preserves end-to-end runtime on remote-heavy workloads
does not harm negative-control workloads badly
```

## 14. Paper Wording

M2 wording:

```text
M2 is a requester-side RDMA bitmap batch queue. It converts fragmented remote cacheline misses targeting the same owner and page into compact bitmap requests, reducing packet count and flit-hop pressure with bounded wait.
```

M3 wording:

```text
M3 is an owner-side fair service queue. It prevents requester monopolization caused by aggressive batching by scheduling per-requester queues with bounded fairness and age-based escape.
```

Combined wording:

```text
M2 improves network efficiency, while M3 preserves fairness and tail latency at the owner endpoint.
```

Avoid saying:

```text
M2 solves coherence.
M2 migrates data.
M3 improves batching.
M3 is a global network scheduler.
```

## 16. Detailed Code Search Guide for the Implementer

The codebase may name the remote path differently. Search for these concepts, not just exact names:

```text
remote
owner
gpm
rdma
network
route
hops
l1v
l2 source
remote fill
cacheline
ReadReq
WriteReq
```

The M2 insertion point must satisfy all of these:

```text
1. The request is already classified as remote.
2. The requester GPU ID is known.
3. The owner GPU ID is known.
4. The physical/cacheline address is known.
5. The original request can still be held/delayed safely.
6. The code path has not yet sent the NoC/RDMA request.
```

If multiple candidate insertion points exist, prefer this order:

```text
best:
  immediately before constructing/sending the remote RDMA/NoC request

acceptable:
  immediately after owner lookup but before network port send

risky:
  inside L1/L1V before owner lookup

wrong:
  at the owner side
  inside DRAM controller
  after the response has already returned
```

The M3 insertion point must satisfy:

```text
1. A remote request or bitmap RDMA request has arrived at owner GPU.
2. The requester GPU ID is known.
3. The owner has not yet issued service to owner L2/DRAM.
4. The request can be queued by requester.
5. The selected request can be forwarded to the existing owner service path unchanged.
```

If owner service path is not centralized, implement M3 at the earliest common owner-side endpoint that sees remote requests before cache/DRAM access.

## 17. Detailed M2 State Machine

M2 should be implemented as a small state machine per requester GPU.

### 17.1 States

```text
Idle:
  no active batch for a key.

Collecting:
  at least one active batch exists and is waiting for more lines or timeout.

Flushing:
  batch is converted into a bitmap RDMA request and removed from table.

WaitingForResponse:
  original requests in a flushed batch are waiting for owner response.

Completed:
  all original requests have been woken by the response.
```

A single requester can have many active batches at the same time:

```text
key A: owner 3, page 0x1000
key B: owner 7, page 0x9000
key C: owner 3, page 0x2000
```

### 17.2 Event: Remote Read Arrives

```text
input:
  original remote read transaction

steps:
  1. compute key
  2. compute line_offset
  3. flush expired batches
  4. find/create batch
  5. attach original transaction to batch
  6. update bitmap
  7. flush if full

output:
  either no packet yet, or one bitmap packet if flushed
```

Important:

```text
Do not complete original transaction when adding to batch.
Original transaction completes only when owner response returns.
```

### 17.3 Event: Non-Batchable Remote Request Arrives

For store/atomic/fence/unknown:

```text
1. identify conflicting pending batches
2. flush those batches before sending non-batchable request
3. send non-batchable request using normal baseline path
```

Conservative conflict rule for first version:

```text
same requester_gpm
same owner_gpm
same pid
same page_paddr
```

This may flush more than necessary, but it is easier to reason about.

### 17.4 Event: Batch Timeout

If using lazy timeout:

```text
1. on every new arrival, scan batch table
2. if now - OldestArrival >= max_wait_ns, flush
```

If using scheduled timeout:

```text
1. batch creation schedules timeout event
2. timeout event checks whether batch still exists
3. if exists and still old enough, flush
```

Always record timeout flushes:

```text
m2_timeout_flushes += 1
```

### 17.5 Event: Bitmap Response Arrives

```text
1. locate the response's original batch context
2. for each line_offset in response bitmap:
     get all original requests waiting for that line
     complete those requests
3. assert every original request in batch has completed exactly once
4. remove response tracking state
```

If response does not carry original batch ID, include one:

```go
type M2BatchID uint64
```

Add to request and response:

```go
BatchID M2BatchID
```

Batch ID is useful for debugging even if the simulator can route by object pointer.

## 19. Detailed M2 Flush Semantics

When a batch flushes, it should do exactly one of these:

```text
if LineCount == 1 and policy says no singleton bitmap:
  send normal single-line remote request
else:
  send bitmap RDMA request
```

Two policy options:

```text
Option A: always bitmap
  even one-line batches use bitmap request
  simpler but may add metadata overhead

Option B: singleton fallback
  one-line batches use baseline request format
  more realistic and avoids overhead for weak-locality workloads
```

Recommended:

```text
Implement Option B after the first prototype.
Prototype can start with Option A if packet format work is easier.
```

Flush must record per-request wait:

```text
for each original request in batch:
  wait = flush_time - request_arrival
  record wait sample
```

Flush must remove batch from active table before sending packet, to avoid reentrant callbacks adding into a flushed batch.

## 21. Detailed M3 State Machine

M3 is a per-owner queueing scheduler.

### 21.1 States

```text
Idle:
  no remote packets waiting at owner.

Enqueue:
  incoming packet assigned to requester queue.

Select:
  scheduler chooses a requester queue.

Serve:
  selected packet forwarded to existing owner service path.

Update:
  deficit/consecutive/age stats updated.
```

### 21.2 Event: Packet Arrives at Owner

```text
1. extract requester_gpm
2. compute service cost
3. create OwnerServiceRequest
4. append to Queues[requester_gpm]
5. update owner received counters
6. if owner service pipeline is idle, trigger scheduler
```

### 21.3 Event: Owner Ready

```text
1. call SelectNext()
2. if nil, remain idle
3. forward selected request to owner L2/DRAM path
4. update stats
```

### 21.4 Event: Service Completes

```text
1. send response using existing response path
2. mark owner pipeline ready
3. trigger scheduler if queues non-empty
```

M3 should not directly complete requester-side original transactions. It only controls owner service order.

## 22. Detailed M3 Scheduler Design

### 22.1 Requester Queue Ordering

Inside each requester queue, keep FIFO order:

```text
do not reorder packets within same requester in first version
```

This keeps M3 simple:

```text
M2 controls batching at requester.
M3 controls inter-requester fairness at owner.
```

### 22.2 Active Requester List

Keep a deterministic list of active requesters:

```go
ActiveRequesters []int
RoundRobinIndex int
```

When a requester queue becomes non-empty:

```text
add requester_gpm to ActiveRequesters if absent
```

When it becomes empty:

```text
remove requester_gpm or skip it until cleanup
```

### 22.3 DRR Selection Pseudocode

```go
func (q *M3OwnerFairQueue) Select(now sim.VTimeInSec) *OwnerServiceRequest {
    if req := q.FindHardAgeRequest(now); req != nil {
        q.Stats.HardAgeEscapes++
        return q.PopSpecific(req)
    }

    n := len(q.ActiveRequesters)
    if n == 0 {
        return nil
    }

    for rounds := 0; rounds < 2*n; rounds++ {
        requester := q.ActiveRequesters[q.RoundRobinIndex]
        q.RoundRobinIndex = (q.RoundRobinIndex + 1) % n

        rq := q.Queues[requester]
        if rq == nil || len(rq.Items) == 0 {
            continue
        }

        q.Deficit[requester] += q.FairQuantumLines

        item := rq.Items[0]
        cost := serviceCost(item)

        if q.ShouldSkipForConsecutiveCap(requester) {
            q.Stats.ConsecutiveCapHits++
            continue
        }

        if q.Deficit[requester] >= cost {
            q.Deficit[requester] -= cost
            return q.PopFront(requester)
        }
    }

    // Fallback: avoid deadlock if all costs exceed deficits.
    requester := q.OldestRequester()
    q.Stats.FallbackOldest++
    return q.PopFront(requester)
}
```

### 22.4 Consecutive Cap

The consecutive cap should apply only when other requesters are waiting:

```text
if only one requester has pending work:
  allow it to continue

if multiple requesters have pending work:
  prevent same requester from exceeding max_consecutive_batches
```

This avoids artificial stalls when there is no competition.

### 22.5 Hard Age Escape

Hard age escape should override fairness:

```text
if any request waits too long:
  serve oldest request globally
```

This prevents starvation even if deficit logic has a bug or a very large batch cannot accumulate enough credits.

## 23. M2/M3 Edge Cases

### 23.1 Duplicate Reads to Same Cacheline

Example:

```text
line 5 requested by three wavefronts
```

M2 behavior:

```text
LineBitmap has bit 5 set once.
PerLineRequests[5] has three original requests.
One returned cacheline completes all three.
```

Counter:

```text
m2_duplicate_line_reads += 2
```

### 23.2 Batch Table Full

When table is full:

```text
flush oldest batch by OldestArrival
insert new batch
record capacity flush
```

Do not drop the incoming request.

### 23.3 Timeout With Singleton Batch

If a batch times out with one line:

```text
either send singleton bitmap packet
or fallback to normal request
```

For realistic evaluation, singleton fallback is better.

### 23.4 Response Arrives Before All Local State Is Updated

Avoid this by:

```text
registering batch response state before sending packet
removing active batch before send
```

### 23.5 Owner Receives Mixed Baseline and Bitmap Requests

M3 should normalize both into `OwnerServiceRequest`:

```text
baseline request:
  IsBatched = false
  LineCount = 1

bitmap request:
  IsBatched = true
  LineCount = popcount(bitmap)
```

### 23.6 Local Requests

M2 should ignore local requests entirely.

M3 should only handle remote arrivals at owner endpoint. Do not accidentally route local owner L2 requests through M3 unless explicitly intended.

### 23.7 Stores and Atomics

First version:

```text
bypass M2
optionally flush same-page pending read batch first
do not batch stores/atomics
```

If correctness is unclear:

```text
disable M2 for workloads with remote writes/atomics
or count bypasses and report read-only coverage
```

## 26. Minimum Viable Implementation Order

Follow this order exactly if possible.

### Step A: M2 Counters Without Batching

Add only counters:

```text
count remote requests
count batchable remote reads
count bypass requests
```

Run one workload and verify counters match existing remote request metrics.

### Step B: M2 Batch Table Without Network Format Change

Implement batch table and flush decisions, but when flushing:

```text
send the original individual requests
```

This verifies batching opportunity and wait accounting without changing network semantics.

Expected:

```text
counters show would-be batch sizes
runtime should be close to baseline
```

### Step C: Bitmap Request Format

Replace individual flush send with one bitmap request.

Expected:

```text
remote packet count decreases
all original requests still complete
```

### Step D: Response Demux

Implement robust demux and duplicate-line completion.

Expected:

```text
no deadlocks
all request completion counts match baseline
```

### Step E: M3 FIFO Wrapper

Before fairness, route owner remote arrivals through an owner queue that simply serves FIFO.

Expected:

```text
M3 FIFO wrapper matches baseline/M2-only behavior except small queue timing differences
```

### Step F: M3 DRR Fairness

Replace FIFO select with DRR + consecutive cap + hard age.

Expected:

```text
fairness counters improve
packet reduction from M2 mostly preserved
```

This staged plan isolates bugs. Do not implement bitmap batching and DRR fairness simultaneously.

## 27. Common Failure Modes

### 27.1 Deadlock Because Singleton Batch Never Flushes

Symptom:

```text
simulation hangs
active M2 batches remain forever
```

Fix:

```text
ensure timeout or drain flush runs even without new arrivals
```

### 27.2 Lost Original Requests

Symptom:

```text
fewer completions than baseline
workgroups never finish
```

Fix:

```text
verify every original request is stored in PerLineRequests
verify response demux completes every waiter
```

### 27.3 Cross-Page Bitmap Error

Symptom:

```text
line_offset negative or >= 64
wrong data line returned
```

Fix:

```text
assert page_paddr matches cacheline_addr page
never batch across page_paddr
```

### 27.4 Packet Reduction But Runtime Regression

Possible causes:

```text
max_wait_ns too high
large response serialization cost
owner monopolization
head-of-line blocking in requester batch table
weak locality workload
```

Debug:

```text
look at p95 wait
timeout_flush_ratio
owner wait
M3 fairness counters
```

### 27.5 M3 Fairness Destroys M2 Benefit

Symptom:

```text
packet count remains low, but runtime worsens
owner service becomes too round-robin and loses locality
```

Fix:

```text
increase fair_quantum_lines
increase max_consecutive_batches
make hard_age_limit less aggressive
```

## 29. Paper-Level Claims to Enable

The implementation should produce enough evidence for these claims:

### Claim 1: Remote request streams are batchable.

Evidence:

```text
same requester-owner-page line groups occur frequently
avg/p90 batch size > 1
oracle window batching shows upper bound
```

### Claim 2: M2 reduces network pressure.

Evidence:

```text
fewer request packets
fewer flit-hops
fewer owner endpoint arrivals
bounded requester wait
```

### Claim 3: M2 alone can create unfair owner service.

Evidence:

```text
M2-only increases max consecutive owner service for some requesters
M2-only worsens p95/p99 owner wait in some cases
```

If this does not happen in data, do not force the claim. Then M3 becomes a safety mechanism rather than a performance-critical mechanism.

### Claim 4: M3 bounds unfairness with modest cost.

Evidence:

```text
Jain fairness improves
max consecutive service decreases
p95/p99 owner wait improves or is bounded
packet reduction mostly preserved
runtime does not regress badly
```

## 30. Final Sanity Checklist Before Reporting Results

Before trusting any M2/M3 result:

```text
1. Baseline and mechanism runs complete same amount of work.
2. Total original request completion count matches baseline.
3. M2 is disabled by default.
4. M3 is disabled by default.
5. M2-only changes packetization but not requested cacheline set.
6. M3-only changes owner service order but not packet contents.
7. M2+M3 does not batch stores/atomics.
8. Packet reduction is not computed using all requests; use remote batchable reads as denominator and also report all-remote denominator.
9. Wait time includes time spent collecting batch before send.
10. Owner wait includes time spent in M3 queue before owner service starts.
```
