前提：HDPAT 之后是数据访问

HDPAT（HPCA 2026）

中心 IOMMU 的页表遍历是瓶颈 → 把 PTE 缓存在离请求方近的 GPM 上，用 cuckoo filter 快速判断“本地有没有”。解决地址转换。

CuPath（ISCA 2027）

地址转换解决之后，远程数据访问成为瓶颈：端点窗口只放行 64 个请求、排队占远程延迟 80% 以上、owner 端不合并相同 line。

baseline 已定（用户 10-19）：mi200 原样，地址转换不变。依据是 T17 的远程 TLB 缺失只占远程读的 1.3–1.6%、远程延迟的 0.3–0.5%，地址转换不是瓶颈。动机图可以用：原始 baseline → + CuPath（T18）→ O1（数据全部本地）。

这篇的机制（T18）：跟踪表规模化 + owner 端合并多播

10-20 核查：(1) MGPUSim 的 RDMA 引擎在这里统称 GPM 的网络接口，它最多能同时挂的远程请求数叫请求跟踪表项数。(2) 上游 MGPUSim 没有这个上限，64 是我们 fork 在 7 月（a185a7e）和 CuPath 机制一起加的；HPCA 稿引用的是数据中心 RDMA 网卡的论文，不能支撑它。(3) HPCA 版 m2 已经有请求方 cuckoo filter 的在途记录、同 line 合并、同页打包，所以这些不再算新贡献。

64 项从哪来、为什么不够

在途上限在途字节填满自己链路需要（带宽 × 往返）
PCIe Gen4 x16（约 32 GB/s，往返约 1 µs）768 个 tag × 最多 512 B约 384 KB约 32 KB：tag 富余
MI250X 两个 GCD 之间（200 GB/s）厂商未公开—实测 kernel 直接读写 153 GB/s（77%），每 CU 约 1.4 GB/s（Pearson 2023）
我们一个 GPM（链路 768 GB/s，往返 155–945 ns）64 × 64 B4 KB约 120–730 KB：差 30–180 倍

定位：64 项给出的每 CU 远程带宽（约 1.6 GB/s）和 MI250X 实测相当，即“沿用今天多芯片 GPU 的端点设计”。真实接口是按能填满自己那条链路来配置的；wafer 的链路宽 4 倍、距离远好几倍，按 Little 定律需要的在途数大 10–100 倍，用全相联 CAM 做不下去。这就是 T18 的出发点，也是它对 wafer 独特的原因。实验上把 64 作为敏感性参数扫 64 / 256 / 1024 / 4096。

T18 的组成

部分HPCA 版 m2T18 新增为什么只对 wafer 成立
请求方：在途记录 + 同 line 合并 + 同页打包已有（cuckoo filter 的 RDMA-In-Flight 类型、页内位图包）——
请求跟踪表规模化64 项，全精确表几百到几千项：cuckoo 结构做索引、完整地址放旁路阵列、按索引匹配响应，不用 CAM（实现：12 位指纹 + 完整地址，表 = 2W）需要的项数 = 带宽 × 往返时间；wafer 比 MCM 大一个数量级
owner 端跨 GPM 合并 + 多播只解开同一请求方的页内位图，逐条服务表项 = 指纹 + 48 位请求者位图；同一 line 只读一次，沿路由树多播；多播响应只带地址，请求方用跟踪表认领同一条 line 最多 47 个读者（MCM 最多 3 个）；链路富余，多送副本可以接受
（候选，未实现）owner 故意攒批—对预测为多读者的 line 等 100–300 ns 攒齐再服务排队占 80%，端点工作量降到 1/k 的收益大于等待；先用微基准验证
（降级）按距离分 credit—已实现为开关 -t18-dist-credits（按 84 + 71.4 ns × 跳数分）；W ≥ 1024 时和共享池逐位相同通用的队头阻塞问题，只在 W = 64 / 256 评估，作为设计细节

证明“对 wafer 独特”的实验：同样的 workload 和机制，在 2×2（相当于 4 个 GPM 的 MCM）、4×4、7×7 的 mesh 上跑，画出 baseline 的排队占比和 T18 的加速比随 GPM 数的变化。收益随规模变大，才能说是 wafer 独特；如果 2×2 上一样大，就要重新考虑。

数据支持：远程带宽 = 64 × 64 B ÷ 往返时间（1 跳 26.4、6 跳 8.0 B/周期），链路利用率 < 3%；T17 每个 GPM 有 270–400 个远程读在途，堵在网络接口门口；按闭环模型，跟踪表放大后吞吐最多约 7 倍（T17 的 O2b 正在跑）。

实现和冒烟结果（Claude Code，10-20）

T18 已经实现（分支 isca27/t18-merge @ ca8b831，默认关闭，全部开关关闭时 fir、MM、旧 m2 逐位一致）。请求方 cuckoo 跟踪表；-t18-window 限制网络在途数；owner 端在该 line 的 L2 读完成前合并；返回时在 switch 里按 YX 树复制（网内多播）；表满退回单播。正确性：FW -verify 多种配置都通过，R-GAT 0 个不一致。

  • 合并和放大跟踪表要一起才有效（FW）：只放大到 1024、不合并 2.26×；只请求方合并 48.5 µs；只 owner 端 87.8 µs（几乎没用）；全开 8.56×，约是 O1 上限（11.1×）的 77%。不合并时 owner 端 incast 让往返时间停在 3–4 µs，owner 合并 + 多播消掉 incast 后，大窗口才用得上。
  • PagedAttention 几乎没有可合并的，3.34× 全部来自跟踪表放大；W=1024 和 4096 相同，说明这些 workload 用不到几千项（W ≥ 1024 时每 GPM 在途 40–75 个，Claude Code 报告，统计口径待核对）。
  • W=64 时 T18 比旧 m2 慢（FW 2.13× 对 2.51×）：旧 m2 还有同页打包，T18 只合并整行读。
  • FW 是截断运行，各配置完成的指令数可能不同，正式评估按 T15 的规则核对。
  • 正式评估在跑：mi200 下 141 个运行（10 个配置 + 只放大窗口的对照）；HPCA 规模（hpca 配置、-max-wg 78600）下和 HPCA baseline / Complete 比较 28 个。

用户 10-20：如果 T18 效果很好且相对复杂，考虑拆成两个机制（合并 + 多播消 incast；大跟踪表）。
