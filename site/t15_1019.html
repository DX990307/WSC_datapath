T15 oracle 上限实验：wafer 层最多还能快多少

T15 用 oracle 实验量出 wafer 层的优化空间：每一组把远程路径的一部分变成“免费”，看程序能快多少。14 个 workload × 6 组，mi200 冻结版，短片段。

要回答的问题

背景：用户担心现在的数据放置让大部分访存发生在本地，wafer 层（远程路径）可能没有足够的优化空间；如果先把本地做好，空间会更小。与其争论，不如直接量出来：把远程路径的某一部分“变成免费”，看程序能快多少。这类实验叫 oracle，它们都是有意偏离真实配置的分析实验，不代表能实现的设计。

  1. 每个 workload 在 wafer 层最多还能快多少？（上限）
  2. 这个上限里，多少来自端点窗口（同时在途的请求数被卡住），多少来自距离（每跳的延迟）？
  3. 现有 CuPath 的 m2、Complete 拿到了上限的百分之多少？
  4. 远程访问占访问个数的多少、占访存时间的多少？

方法问题：截断运行的有效性

口径O1O2aO2bO2O3m2Complete

截断运行在全局完成 32,768 个 WG 的那一刻退出。O1 等组跑得快慢不同，退出时各个 GPM 正在执行的 WG 进度不同，完成的指令数也就不同；远程多的 workload 指令数差得多（im2col −39%），于是被严格规则判为无效，严格口径的 GMEAN 几乎都是 1.0。这不一定说明 oracle 本身有问题，而是截断口径的问题。

  • 改成按“每条指令的时间”或“每个 WG 的时间”比较；
  • 远程多的 workload 改为完整跑完（kmeans 完整跑要十几个小时）；
  • 论文里两种口径都给出。

待决定：截断运行的有效性规则。T16 已经说明截断运行看不到 kernel 尾部，T17 的新 workload 都是完整运行，以后的 oracle 也应该在完整运行上做。
