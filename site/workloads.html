Workload 与实验

测量定义、workload 讨论和已有的实验结果。

T11 探针结果（10-13）

P1、P2 是功能性结论，仍然有效。P3、P4 用的是 baseline 二进制的默认参数（16 GB/s、20 周期交换延迟），不是论文配置，性能数字作废，要用新配置重跑。

实验结论说明
P1通过数据和 kernel 在同一个 GPM 上时，远程事务数为 0
P2通过只有目标 GPM 的 32 个 CU 执行了指令
P3路径通过远程读写都经过远端 L2（第 1 遍 miss、第 2 遍 hit）；延迟数字作废
P4通过48 个 GPM 能并发运行；耗时数字作废

其他发现：fork 是 mgpusim v3；CuPath 的远程通路在 RDMA 内部；可以复用 -report-l2-source 统计；SPMD 骨架在 probe/spmd.go；GPM 有两套编号（driver ID 1–48 和 GPU[t]）。

T10 自写通信套件（提案）

数据按 GPM 分片，加上显式的通信阶段；通信用 kernel 直接 load/store 对端缓冲区（和 NCCL、NVSHMEM 的做法一样）。T11 已经确认这种写法可行。

W1 测量定义

在 MGPUSim 里加统计点。阈值是建议值，可以按实际数据调整。

编号测什么怎么统计用来判断
M1跨 GPM 共享度每个 kernel 内，对每条远程 line 统计访问它的不同 requester GPM 数，按 home 距离分桶，再按远程读流量加权。同时统计“同一候选区域内 ≥2 个 GPM 读同一行”的远程读占比机制 1 是否成立。建议：后者在主要负载上要明显超过 10–15%
M2跨 kernel 复用kernel k 读过的远程 line，在 k+1 及之后被同一 GPM 或同区域再读的比例；以及这些 line 所在 page 在 kernel k 内被写过的比例机制 2 能保留多少数据
M3远程读按距离分布远程读的跳数直方图，加上各跳数下的平均延迟（在 Fig 4 的基础上细化）按距离决定是否走代理时的阈值
B1–B4强 baselineB1 远程数据总进 L2（可以挤掉本地数据）；B2 128B 取数；B3 MCM-GPU L1.5；B4 精确 NI 合并原 CuPath 的收益还剩多少（尤其 MM 上的 5.45×）

Workload 讨论

10-12 开始讨论，下面全部是提案。现有 workload 有三个问题：WG 数量受模拟器限制、page placement 太理想导致远程通信少、benchmark suite 太旧（2010–2017）。

问题应对（提案）
模拟预算有限：benchmark 太大跑不完，每个 CU 只能执行前约 5 个 WG（10-12 澄清）（已撤回 persistent kernel 的建议：每个 WG 变重之后同样跑不完。）新提案：A. 按模拟预算来定输入规模，让 kernel 真正跑完，用“实际访问到的 footprint”代替“分配的 footprint”，目标是明显超过全 wafer 的 L2 总量 192 MB；优先选访存密集的负载。B. 保留 7×7 mesh，但把每个 GPM 的 CU 数从 32 减到 8，L2、HBM、NI、链路带宽按比例缩小，这样每个 CU 能执行的 WG 数约是原来的 4 倍；再用一部分负载在 32 CU 配置上验证趋势一致。C. Photon 采样（10-12 放弃：移植难度太大）。D. 用小输入做验证：同一负载跑完整版和截断版，对比两者的指标
page placement 太好，远程通信少不要为了制造远程流量去刻意选差的 placement。正确做法是两种策略都报：local-aware，以及按 page 交错（MI300X 的 NPS1 模式就是把数据交错到全部 8 个 HBM stack 上，有真实依据）。同时选择本身就有不规则、全局共享访问的 workload，这类访问任何静态 placement 都无法消除
benchmark 太旧主评估换成 2020 年后的负载（LLM、MoE、GNN、推荐系统、带标准输入的图计算）。旧 benchmark 保留少数几个作为“经典 kernel”对照
批次类别Workload 和输入共享 / 远程特征对应机制估计 footprint工作量
第一批LLM 推理共享前缀的批量 decode：1B 级配置（hidden 2048，32 个 Q 头，8 个 KV 头，FFN 8192，fp32），batch 16–32，共享 system prompt 2K token，每个请求私有 512 token。kernel 包括 RMSNorm、QKV/O GEMV、attention、SwiGLU FFN，跑 1–2 层共享前缀的 KV 被所有请求读（vLLM prefix caching 的真实场景）；GQA 下一个 KV 头被 4 个 Q 头共享；FFN 的 GEMV 是纯流式访问，充当无优化机会的对照机制 1；FFN 部分作对照每层权重约 243 MB，KV 约 70 MB4–6 天
第一批图学习2 层 GCN，ogbn-arxiv 全图（16.9 万点、117 万边、128 维特征）。kernel：CSR SpMM 聚合、GEMM、ReLU幂律分布下热点顶点的特征被很多 GPM 读；CSR 跨层只读机制 1 + 机制 2特征约 87 MB，CSR 约 10 MB3–4 天
第一批推荐系统DLRM embedding bag：前向 gather-sum，反向 scatter-add。索引用 Meta 公开的 lookup trace，或参数明确的 zipf 分布热门行被所有 GPM 读；反向是带 atomic 的写，正好回应 B 要的读写混合机制 1；机制 2 的写路径每批实际访问约 100–200 MB2–3 天
第一批数据库Star Schema Benchmark 的 hash join 查询（参考 Crystal，SIGMOD'20），SF 1–2：build 阶段写哈希表，probe 阶段读维度表的哈希表很小，被所有 GPM 读；从 build 到 probe 跨越 kernel 边界机制 1 + 机制 2 的正确性约 100–200 MB3–4 天
第二批LLM 推理MoE 层（Mixtral 风格 8 选 2，或 DeepSeek 风格 64 选 6）：gating、token permute、grouped GEMM、combine热门 expert 的权重被很多 GPM 读；permute 是 all-to-all 的 scatter机制 1、aggregation按 expert 规模调整在 LLM 基础上 +2–3 天
第二批图计算BFS 和 PR（pull 方式），输入用 GAP/Graph500 的 Kronecker 图，scale 20访问不规则；每轮迭代一个 kernel，图结构只读机制 2、aggregationcol_idx 约 128 MB3 天
可选HPC3D Jacobi 7 点 stencil，256³，3 轮迭代只和相邻 GPM 交换 halo，属于近距离远程作对照，检验按距离决定是否走代理的阈值约 128 MB1–2 天
保留经典 kernelMM、FWS、KM、SPMVMM 和 FWS 是原来收益最大的；SPMV 作为无优化机会的对照—沿用现有设置0

注意事项：(1) GCN3 没有矩阵核心，所有 kernel 用 fp32 写。这会低估访存瓶颈，所以测出的收益是偏保守的，论文里要写明。(2) 所有 workload 都要报 M1 共享度，包括没有优化机会的负载，避免被说挑 workload。(3) 第一天先检查 MGPUSim 的 GCN3 模拟器对 atomic 和各种 load/store 宽度的支持，用一个小 kernel 在 emulation 模式下跑通，免得移植到一半才发现缺指令。(4) 如果采用方案 B（每 GPM 8 个 CU），全 wafer 的 L2 总量会降到 48 MB，上面这些 footprint 都足以给 cache 施压。
