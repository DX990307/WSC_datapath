I3多 line 远程事务：同一 page 的几条 line 只占一个在途槽位带宽和往返延迟成反比，窗口按事务计数（1 跳 26、6 跳 8 B/周期）
I4用数据给 T7 定量：距离直接换带宽；本地副本 / 区域代理 / home 三层，自适应选择延迟 = 198 ns + 72 ns/跳；代理按延迟算的盈亏平衡命中率约 55%
I5远程地址转换是一阶开销（作为特征分析；作为机制和 HDPAT 重合）远程 TLB miss 多付 732 ns，和距离无关

用 thread placement 利用 wafer 特性（10-16，提案）

完整内容在 ideas_from_T14.md。上限由 T15 的 O1（全部本地）和 O3（距离几乎免费）给出。

wafer 特有的角度和已有工作（Milic MICRO'17、Khairy MICRO'20、CODA）的区别
二维拓扑映射：共享数据的 WG 组放在物理相邻的 tile 上已有工作面对的是 4 个左右、距离差不多的模块；wafer 上 1 跳和 12 跳差 4 倍多
避开热点 owner：分散读同一个 owner 的 WG，或分散热点数据瓶颈在端点（owner 约 113 B/周期封顶），不只是距离
搬计算而不是搬数据：下一个 kernel 的 WG 跟着上一个 kernel 写出的数据走wafer 上 kernel 边界约 1 µs，跨 wafer 搬数据又慢又占窗口

补充（10-16）：AES、BT 这类几乎全在本地的负载，placement 帮不上；只有远程占比高的负载（pagerank、I2C、MT、SPMV、mi200 下的 KM）可能受益。只缩短距离的话 198 ns 的固定开销还在，距离减半大约带来 1.5–2×；量级上的收益只来自把访问变成本地。建议把 placement 做成强 baseline，不当主贡献，以此回应“收益来自弱 baseline”的质疑。新增 O4 放置 oracle：离线按 WG→页 的统计，在负载均衡的约束下把每个 WG 放到加权跳数最小的 GPM 上。

placement 以外的路依据最近的已有工作
a. 用带宽换延迟：owner 端合并、多行事务、批量推送（I2、I3）链路 97% 空闲；远程路径受窗口限制GPS（MICRO'21）
b. 远程翻译（I5）远程 TLB miss 多 555–732 ns，和到中心 IOMMU 的距离有关Trans-FW（HPCA'23）
c. 空间/流水线执行：分区跑不同 kernel，邻居间流式传数据最有 wafer 特色；需要驱动支持多 kernel 并发，工程量大—（3.5 周内风险高）

新机制提案

两项都还在提案阶段。区域大小、代理选择规则等细节见“待决问题”。

机制 1 · 按距离分区域的远程数据复制

  • 把 7×7 mesh 划成若干小区域，每个远程 page 在请求者所在区域内有一个固定的代理 GPM（用页地址哈希选）
  • 读请求先去代理（1–2 跳）。代理命中就直接返回；不命中由代理去 home 取，再用自己空闲或已死的 way 缓存
  • 只在 home 足够远时走代理，近的直接访问 home
  • 代理顺带合并同区域内多个 GPM 的重复请求

好处：闲置 L2 变成分布式远程缓存，仍然不新增 cache 层级；GPM 内的合并升级为跨 GPM 合并；每个区域只存一份副本。

机制 2 · 基于写签名的选择性失效

  • 每个 owner GPM 在一个 kernel 内把被写过的 page 记进 Bloom 签名
  • kernel 边界广播签名，各 GPM 只失效命中签名的副本
  • 其余只读副本跨 kernel 保留，比如权重、迭代算法中的输入数据

Bloom filter 不会有假阴性，假阳性只会多失效一些行，所以正确性由结构本身保证。这同时回答了“为什么要用近似结构”。

工作有多接近区分点
HMG（Ren et al., HPCA'20）最接近HMG 的层级由封装固定；wafer 上没有封装边界，区域按距离划分，是否走代理也随距离自适应

CARVE（MICRO'18）、HALCONE、MGPU-TSMmulti-GPU 的远程缓存和一致性没有考虑距离；失效是全量的，或基于时间戳
