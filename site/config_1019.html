配置文件化，以及 hpca、mi300x、mi200 三套配置的对比

把所有模拟参数从命令行搬进 JSON 配置文件，每次运行记录实际生效的值和与基准的差异；在此基础上增加了 GPM 预设，先试 1/8 MI300X，最后换成 1/4 MI250X GCD（mi200）并冻结。这一页列出做了什么、三套配置逐项怎么不同、实测出来是什么样。

配置文件化：做了什么

  1. 问题：以前每个实验在命令行写十几个参数（来自 runall2_constants.py）。10-13 的 T11 第一轮漏了，用的是二进制默认值（-bandwidth=1 即 16 GB/s、-switch-latency=20、没有 magic copy），得出“远程带宽只有本地 1/18”的错误结论，P3/P4 的性能数字全部作废。
  2. 配置文件（akkalat/baseline/runner/config_file.go，提交 1b1e829）：-config a.json,b.json，键就是参数名；后面的文件覆盖前面的；"extends" 继承另一个文件；_ 开头的键是注释；参数名写错直接报错退出；命令行显式写的参数覆盖所有文件，并打印出来。二进制的默认值没有改。
  3. 记录实际生效的值：-config-out 写出每个参数的实际值和来源（默认值 / 哪个文件 / 命令行）。每个结果目录都保存这份 config_used.json，它本身也能直接当配置文件用。
  4. 运行脚本：isca27_run.sh <exp_id> <commit> <task> <配置名> [benchmark 参数]。meta.json 里自动写 config_deviation：和基准配置的逐项差异。冻结之后基准是 configs/mi200.json（字段 deviation_base）；benchmark 参数和统计开关单独标注，不算配置修改。
  5. 测试：test_isca27_configs.py 检查 hpca.json 和论文的 BASE_COMMON_FLAGS 逐项相同、预设和配置文件一致、所有配置都保留 -magic-memory-copy；config_file_test.go 检查继承、循环检测、仓库里的配置只用已有参数。
  6. 冻结：10-16 在 67f1c03 打标签 isca27-mi200-v1，说明写在 akkalat/configs/MI200_V1.md。之后改任何预设数值都要用户批准，并打新标签（v2）。
  • 不再用 -disable-servers：核实它只关掉两个后台网页服务（Go pprof、akita 监控页），都监听随机端口，多个实验同时跑不冲突，也不影响结果（上表第一行）。
  • CuPath 机制开关不在配置文件里：-remote-data-path-enable 默认 false，Remote Aggregation / Reuse 的子开关只在它打开时起作用；Local Pairing、filter、prefetch 等默认都关。所以用配置文件跑出来的就是 baseline。消融和 oracle 实验在配置之上用 --extra-benchmark-flags 叠加，差异会写进 config_deviation。
  • 敏感性实验：配置文件可以叠加，例如 mi200,l2_8mb，只需要写一个只含差异的小文件。

configs/mi300x_eighth.json

{
  "extends": "hpca.json",
  "gpm-preset": "mi300x-eighth",
  "num-memory-banks": 16
}

configs/mi200.json（冻结版，注释已简写）

{
  "extends": "hpca.json",
  // 28 CU、8 个 256 KB slice、HBM2e
  "gpm-preset": "mi200",
  // 8 个 slice = 8 个 HBM2e channel
  "num-memory-banks": 8,
  // 每 GCD 8 MB ÷ 4
  "l2-cache-size-mb": 2
  // 另有 7 条 "_deviation-*" 注释：
  // CU 取整、时钟换算、64 B 行、
  // MSHR 32、DRAM 时序和建模选择
}

三份文件只在 3 个参数上不同：gpm-preset、num-memory-banks、l2-cache-size-mb。GPM 内部的其余参数由预设决定（akkalat/baseline/runner/gpm_preset.go）；预设检查这两个参数，填错直接报错。wafer 层（网络、网络接口、MMU、L1 MSHR）三套完全相同。

实测和理论峰值

实测峰值占理论峰值的比例

理论值：HBM 按控制器数 × 每次访问字节 ÷ burst 时间；L2 按分区数 × 每周期请求数 × 64 B。三套配置的 L2 都远低于理论值；hpca 和 mi300x 的理论值差 2 倍，实测峰值却几乎一样（622 vs 631），说明瓶颈在 L2 之前（L1V 一侧），不在 L2 本身。

HBM 读为什么只有 31%

10-15 诊断（临时构建，HBM 读，28 个 WG）B/周期
按冻结配置74
每 slice 128 个 MSHR111
关掉刷新129
两者都改135
去掉“同一请求行保持”52
  • MSHR 不够：每 slice 32 个，覆盖不了约 200 ns 的 HBM 延迟（按 Little 定律约需 94 个）。
  • 每条 line 开一次行：close page，相邻 line 在不同 bank，速率被 tRRD_S 限制在每 pseudo channel 一次激活，约 138 B/周期。
  • 刷新被放大：一个 pseudo channel 刷新时占满共享的 MSHR，另一个 pseudo channel 也停下来，代价从约 12% 放大到约 40%。刷新模型本身是对的。
  • 用户 10-16 决定保持 32 个 MSHR 并冻结（改的话已完成的 mi200 结果都要重跑，约一天）。

为什么从 mi300x-eighth 换成 mi200

时间事件
10-13实现 -gpm-preset，第一个新预设是 1/8 MI300X；同时用同一套微基准实测旧配置
10-13校准：HBM 读 243 B/周期（目标 315，−23%），L2 读约 630（目标 2,048，−69%），偏差超过 10% 按规则停下
10-13 – 10-14用户先按实测值跑全量（阶段 4）；遇到内存泄漏、结果不确定、服务器硬件故障，阶段 4 中止
10-14内存控制器审查：Local Pairing 的收益来自旧配置 128 B 的 DRAM 访问单位；用户决定改用 1/4 MI250X GCD（mi200）
10-15mi200 实现并验证（7 项清单）；HBM 读只有 31%，诊断后决定保持
10-16冻结：标签 isca27-mi200-v1（67f1c03），之后所有新实验都以它为 baseline
