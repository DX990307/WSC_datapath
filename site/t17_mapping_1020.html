共同的规则

  • 执行模型：整片 wafer 作为一个 unified GPU，每个 kernel 一次 launch 覆盖 48 个 GPM。
  • WG 分配：静态连续切分。按 driver ID 1–48（行优先对应 tile），每个 GPM 拿 28 × ⌈N/1344⌉ 个连续的 WG。N < 1344 的 kernel 只用到前 ⌈N/28⌉ 个 GPM。
  • 数据放置：每个 buffer 按页平均切成 48 段，第 i 段放在第 i 个 GPM。
  • 写法：OpenCL C 编译到 gfx803；fp32；不用 atomic（模拟器不支持），统一 pull（每个 WG 自己读所需数据、只写自己的输出）；块表、路由排列、采样子图这些索引结构在 host 端生成。
  • 正确性：不跑 verify；用极小输入在 emu 模式下和 host 端的参考实现对照过输出。

R-GAT
MLPerf Inference v5.0 的 RGAT 任务，按比例缩小：IGBH-tiny（55.8 万点、410 万条边；完整 IGBH 有 5.47 亿点），320 个种子，fanout (10, 5)，hidden 128，单头（MLPerf 是 4 头 × 512 维）		 每层、每种关系两个 kernel：rgat_proj（每个 WG = 32 个采样源点 × 64 列，gather 特征并投影）、rgat_agg（每个目标点一个 WG，算 attention、邻居 softmax、加权求和）；两层共 30 个 kernel。采样在 host 端做（仿 DGL） proj 类 kernel 只有 26–340 个 WG → ≤ 13 个 GPM，占了 85% 的时间；最大的聚合 kernel 1,344 个 WG → 48 个 每种节点类型一张完整的特征表（1024 维），切成 48 段。footprint 约 140 MB（实际访问到的） 采样到的点是随机的，gather 分散到所有 GPM；一个 owner 占 16%（原因待查）

wafer 的 L2 总量是 96 MB，三个 workload 的 footprint 都超过它；HBM 总量 384 GB，它们不到 1%。WG 和 GPM 数来自每个 GPM 的 trace；footprint 来自 benchmark 的报告；PagedAttention 的分配量是估算（KV 池按需要的 2 倍分配），R-GAT 的特征表整张分配但只拷了用到的行。

放置真的帮不上吗？ R-GAT 的随机 gather 基本是。PagedAttention 如果块分配器知道序列会在哪个 GPM 计算，理论上可以把块放在本地；但 continuous batching 下这个对应关系每步都在变，而块在 prefill 时就分配了，需要用 O4 放置 oracle 量化。MoE 现在的 95% 远程主要来自权重和计算没对齐；真实系统用 expert parallel，把 expert 的计算放到权重所在的 GPM，只有 token 的 dispatch/combine 是远程。下一轮应该改成这种映射。
