工作总览 · 第 9 项 T16

T16：GPM 的位置会不会造成负载不均

T16 检验一个 wafer 特有的假设（W1）：GPM 在 mesh 上的位置不同，导致远程延迟不同，kernel 被角落的 GPM 拖慢。阶段 1 只测量，不改任何时序：加一个每个 GPM 的统计 tracer，跑 6 个微基准和 7 个真实 workload 的小输入，全部跑完整个 kernel。

1.224all-to-all 尾部比（ρ = 0.95）
1.248 / 1.237kmeans / pagerank 小输入的尾部比
2 / 3满足 W1 条件的真实 workload（需要 3 个）
≤ 1.05remotefrac 扫描的尾部比（预期之外）

假设和出发点

W1 假设：48 个 GPM 在 7×7 mesh 上的位置不同。角落的 GPM 到其他 GPM 平均 6.1 跳（远程约 639 ns），中心附近只有 3.7 跳（约 465 ns）。对远程访问多的负载，角落 GPM 的每个 WG 跑得更慢（按延迟模型约 1.37 倍），而 kernel 要等最慢的 GPM 结束。4 个模块的 MCM 距离都差不多，没有这种系统性的位置差，所以这是 wafer 特有的问题。如果成立，可以做按位置加权的 WG 切分、向邻居偷 WG 等机制。

远程 TLB 缺失的代价和这个距离有关（T14 诊断 B）。

为什么要新做实验：之前所有真实 workload 的运行都是截断的。-max-wg 是全局计数，所有 GPM 合计完成 N 个 WG 就退出，慢的 GPM 只是少完成几个 WG，不会拖住别人，kernel 尾部的等待根本看不到。所以 W1 只能在跑完整个 kernel 的运行里测。

测什么：per-GPM tracer

统计项（每个 kernel、每个 GPM 一行）用途
分到 / 开始 / 完成的 WG 数检查切分（空 GPM、余数）
GPM 的 kernel 启动时间、第一个 WG 开始、最后一个 WG 结束、GPM 报告结束的时间忙碌时间 = 结束 − 启动
WG 平均耗时每个 WG 的速率
L1V 读：本地 / 远程次数、各自平均延迟；写同样远程比例、远程延迟
L2 TLB 缺失：本地 / 远程次数、远程总延迟远程地址转换的代价
坐标 (x, y)、到中心跳数、到其他 GPM 的平均跳数和位置做相关

开关 -report-gpm-trace，只做统计。回归：mi200 下 fir、MM 开 / 关 tracer，total_time（26.568 / 345.433 µs）和全部统计逐项一致。

实验设计

部分内容为什么
1c-①all-to-all，每对 16 KB（T14 的通信模式，mi200 补跑）已知在 hpca 上 1.23 / 1.43 / ρ 0.93，确认 mi200 上一样
1c-②远程比例扫描 -plat-test=remotefrac：每个 GPM 一个 1 MB 本地分片，224 个 WG，12 次迭代；每个 WG 的读有比例 f 是均匀的 all-to-all 远程读，其余读本地。f = 0 / 0.1 / 0.25 / 0.5 / 1得到“尾部比随远程比例怎么变”的曲线，用来估计真实 workload 的位置差
1d7 个真实 workload 的小输入，能完整跑完一个 kernel（下表）真实程序里有计算和本地访存，看位置效应会不会被冲淡
1b（没跑）在截断运行里看各 GPM 的 WG 速率截断时同时有 2.8–5.8 万个 WG 在执行，速率只反映 kernel 开头，意义有限；用户决定不跑

尾部比和位置的关系

落在 W1 区域的：T16 的 all-to-all、kmeans、pagerank，T17 的 MoE router

方块是 T17 的主要 kernel（10-17 第一轮）：尾部比都很高（1.2–1.8），但和位置几乎无关，来自数据（序列长度、expert 的 token 数）。MoE router 只用 10 个 GPM、占 MoE 时间的 19%。

remotefrac 扫描

remotefrac：尾部比 vs 远程比例

预期随 f 增大到 all-to-all 的 1.22，实际一直 ≤ 1.05。

remotefrac：kernel 时间 vs 远程比例

f = 1 时 1,520 µs，是 f = 0 的 30 倍：远程读本身很慢，但每个 GPM 慢得差不多。

这和 T16 子代理之前用 64 KB 分片做的冒烟测试（尾部比 1.29、ρ 0.97）不一致。可能的解释：每 GPM 1 MB 时远程读分散到全部 48 个 owner，瓶颈在 跟踪表窗口和 owner 端的服务能力，而不是距离；按闭环模型，排队时间对所有 GPM 都差不多，距离只影响往返时间的一小部分。原因还要查。

结论

问题回答
(i) 位置差是否存在、有多大存在，但只在一部分负载上明显：远程为主、访问对象均匀分布、跑完整个 kernel 时，角落比中心慢 1.4–1.5 倍，尾部比 1.22–1.25（all-to-all、kmeans、pagerank），和平均跳数强相关（ρ 0.74–0.99）。
(ii) 和位置无关的不均两个大例子：MM（GPM 1 热点，最慢 / 最快 2.84）、im2col（随编号变化，1.81 / 5.03）；matrixtranspose 最后一个 GPM 分得少。这些是 baseline 的放置和切分问题，不算进 W1。
(iii) W1 是否成立微基准满足；真实 workload 只有 kmeans、pagerank 两个，差一个。T17 的新 workload 也没有补上（不均来自数据，不是位置）。结论：W1 不作为主线。

还没查清的：remotefrac 和冒烟测试的不一致；im2col 小输入的编号梯度；f = 1 的对角渐变是否来自 GPM 的启动顺序。
