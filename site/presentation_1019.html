背景 · CuPath 是什么

48 个 GPM 的 wafer GPU 上，优化远程访存的数据通路

平台（MGPUSim v3 + akita v3）

  • 7×7 mesh，48 个 GPM，中心 tile 是 CPU / IOMMU
  • 整片 wafer 当成一个 GPU：WG 按 GPM 连续切分，页按 48 等分连续放置
  • 远程读的路径：
L1V→本地网络接口→mesh（每跳一个交换机）→远端网络接口→远端 L2→远端 DRAM

baseline 里远程数据不进请求方 L2（真实 MI200 会以 NC 方式缓存）。

CuPath（HPCA 投稿版）

  • m1 Local Pairing：本地 miss 成对提前发出，掩盖 HBM 延迟
  • m2 Remote Aggregation：远程请求进网络前去重、按页打包
  • m3 Remote Reuse：值得复用的远程 line 留在请求方 L2
  • 三者共用一个 typed Cuckoo Filter（在途、L2 驻留、复用信息）
  • 论文结果：14 个 workload 平均 1.47×

7×7 mesh：GPM 编号（driver ID）和一条远程读路径

编号逐行递增、跳过中心。WG 和页都按这个顺序连续切成 48 段。示例：左下角 GPM 42 读 GPM 13 的数据，走 10 跳（先 Y 后 X），往返约 198 + 72×10 ≈ 920 ns。

② 改了什么

评估平台与方法的修订：baseline 配置、模拟器正确性与机制取舍

Baseline 配置：改用 MI200 级 GPM 并冻结

  • 每个 GPM：28 CU、2 MB L2（8 × 256 KB，每 slice 32 MSHR）、HBM2e（8 channel × 2 pseudo channel，峰值 241 B/周期）
  • 没用 MI300X：它的新架构（Infinity Cache 等）模拟器实现不了
  • 已知的局限：HBM 读只到峰值 31%；kernel 之间不失效 L1（baseline 偏快）

模拟器正确性修复

  • v_mad_u64_u32 解码成 32 位；补了 6 条新 workload 用到的指令
  • 所有修复都做了回归：fir、MM、gemm 修复前后统计逐项一致

撤除 Local Pairing 机制

内存控制器审查发现：hpca 配置的 DRAM 每次访问 128 B，相邻两条 64 B line 本来就一起取回，m1 的“配对”收益来自这里。换到 64 B 访问的 mi200 后：

评估方法的调整

  • 用 oracle 先量上限，再看机制拿到了多少
  • workload 换成“page placement 帮不上忙”的现代负载，每个实验控制在 3–5 小时、kernel 完整跑完
  • 发现 -max-wg 截断是全局计数，截断运行看不到 kernel 尾部，新实验不再用截断
  • 新增每个 GPM 的统计（结束时间、远程延迟、TLB miss）

换到 mi200 后，Local Pairing 的收益消失

灰点是 hpca（128 B DRAM 访问），蓝点是 mi200（64 B 访问）。m2、m3 基本不变，m1 从 1.165 降到 1.028，Complete 随之下降。

③ 新结果 · 1 平台特征（T14）

平台测量：远程访问卡在 RDMA 两端各 64 项的表，不在链路

T14 用微基准（platbench，跑完整个 kernel、不截断）把 wafer 平台本身测清楚，不开任何 CuPath 机制。mi200 为主，hpca 和 1/8 MI300X 也测了：wafer 层的数字三套几乎一样，因为 GPM 之间的参数没变。带宽按 1 GHz 算，1 B/周期 = 1 GB/s。

发现的瓶颈

  • 请求方：RDMA 的请求表只有 64 项，一项从请求发出占到响应回来。单对远程带宽 = 64 × 64 B ÷ 往返时间：1 跳 26.4、6 跳 8.0 B/周期（发现 2）
  • owner 端：多个 GPM 读同一个 owner 时封顶约 113 B/周期，同一条 line 的请求不合并（发现 3）
  • 距离：往返时间随跳数线性增长，最远是最近的 6 倍，远的请求占表项更久（发现 1、4）
  • 不是瓶颈：链路（768 B/周期）最多只用到 2.8%（发现 2、4）

发现 1 · 远程延迟只取决于跳数，往返时间最多差 6 倍

→ M1 分配
做法
跳数矩阵：远端 L2 命中的单线程指针追逐，GPM 1 → 全部、全部 → GPM 1、另外 5 个起点 → 全部，共 329 对
结果
远程读延迟 = 198.1 + 71.8 ns × 跳数（RMS 残差 2.3 ns）。同一跳数下最慢和最快只差 7–10 ns，中心的 CPU tile 没有让路由绕路
换算
减去 L1V 自己的 115 ns，网络接口往返 ≈ 84 + 71.4 ns × 跳数：1 跳 155 ns、6 跳 514 ns、12 跳 945 ns
瓶颈
请求表的一项从请求发出占到响应回来。跳数越多，一项占得越久：最远的一项占用时间是最近的 6 倍（2×2 MCM 只差 1.5 倍）。远近请求共享 64 项时，远的会占掉大部分
对设计
64 项要按距离分，近的有保底，远的不能把表占满

远程延迟和跳数（329 对 GPM）

每个点是一对 GPM 的实测值，虚线是线性拟合。

发现 2 · 单对远程带宽只有链路的 1–3%，卡在请求方的 64 项表

→ M1 合并、打包、分配
做法
GPM 1 读 1 跳 / 6 跳外一个 GPM 的数据（远端 L2 1 MB、远端 HBM 16 MB），WG 数从 1 扫到 256
结果
8 个 WG 就饱和：1 跳 26.4 B/周期、6 跳 8.0 B/周期（远端 HBM 18.6 / 7.3）。链路是 768 B/周期，只用到 3.4% 和 1.0%
诊断
① L1V 在途数改成 16 / 32 / 64，带宽不变，不是 L1V 的问题。② 把请求表从 64 改到 128、256（只做诊断），1 跳带宽 26.4 → 50.3 → 92.2，6 跳 8.0 → 15.7 → 30.5，几乎成正比，到 256 还没饱和。③ 按 Little 定律反推在途数 = 带宽 × 往返 ÷ 64 B，1 跳和 6 跳都正好是 64
瓶颈
请求方 RDMA 的 64 项请求表：远程带宽 = 64 × 64 B ÷ 往返时间，和距离成反比。真实 workload 里也一样：T17 每个 GPM 有 270–400 个远程读在途，堵在网络接口门口，排队占远程延迟的 80–86%（闭环模型）
对设计
表不放大（当作硬件约束），就让每一项带更多内容：同 line 只占一项（合并）、同页的 line 打成一个包（打包）

单对远程带宽（1 跳）和 RDMA 请求表项数成正比

64 项是基线；128、256 只是诊断，用来确认瓶颈是这张表，机制里表不放大。

发现 3 · 多个 GPM 读同一个 owner 时，owner 端封顶，而且不合并同一条 line

→ M1 owner 合并 + M2 多播
做法
incast：k = 1–47 个 GPM 同时读 owner（driver 25）上的 1 MB。共享读 = 都读同一份；不相交读 = 各读一段
结果
共享读，k = 1 / 2 / 4 / 8 / 16 / 47：25.4 / 50.6 / 70.5 / 108.2 / 111.8 / 113.5 B/周期，k ≥ 8 卡在约 113。不相交读也在 92–97 封顶。共享读没有任何好处：总时间随 k 线性增长（k = 47 是 k = 1 的 10.5 倍）
瓶颈
owner 端 RDMA：同一条 line 的请求各占 owner 表一项、各读一次 L2、各发一份响应。一个热点 owner 最多同时服务约 4 个全速读者（113 ÷ 26.4）。wafer 上一条 line 最多 47 个读者，2×2 MCM 最多 3 个
对设计
owner 端把同一条 line 的请求并成一项、只读一次 L2（M1 合并）；合并后只发一份响应，在 switch 里复制给每个读者（M2 多播）

多个 GPM 读同一个 owner（incast）

所有 GPM 读的是同一份 1 MB 数据，owner 端仍在约 113 B/周期封顶。

发现 4 · 48 个 GPM 同时通信时，链路最多只用到 2.8%

→ M2 多播 · M1 分配
做法
48 个 GPM 同时做 all-to-all（每对 16 KB）、邻居交换、转置、按编号的环、蛇形环
结果
聚合带宽 338 / 847 / 148 / 171 / 171 B/周期，每个 GPM 只有 3.1–17.6 B/周期；按 YX 路由推算，最忙的链路只用到 0.5–2.8%（模拟器没有链路统计，是推算值）
瓶颈
端点，不是 mesh 链路。all-to-all 里角落的 GPM 比中心慢约 1.4 倍（109 vs 78 µs），和到其他 GPM 的平均跳数的相关系数 0.95：远的请求占表项更久
对设计
链路有富余，多播多送几份副本代价很小；位置效应说明表项要按距离分

发现 5 · 远程读是本地 L2 命中的 2–8 倍

→ M3 保留
做法
本地延迟阶梯：单线程指针追逐，数据集 4 KB–1 GB
结果
本地 L1V 115 ns、L2 129 ns、HBM 约 198 ns；远程（远端 L2 命中）1 跳 270 ns、12 跳 1,060 ns
瓶颈
每次远程读都要走一遍 mesh、占一项请求表；同一个 GPM 再读同一条远程 line 时还要再走一遍
对设计
会被再读的远程数据留在请求方 L2（M3）。注意 L2 命中只比 L1V 多 14 ns，比真实芯片快，M3 的收益可能偏高

本地延迟阶梯（mi200，指针追逐）

L2 拐点在 2–3 MB（每 GPM 2 MB L2）。

对应到三个机制

瓶颈表不放大时的办法机制
请求表 64 项限制带宽（发现 2）同 line 只占一项；同页的 line 打成一个包，一项带多条M1 合并、打包
远的请求占表项更久（发现 1、4）64 项按距离分，近的有保底，远的不能占满M1 分配
owner 端封顶、同 line 不合并（发现 3）owner 端同一条 line 只占一项、只读一次 L2；只发一份响应，在 switch 里复制M1 合并（owner 端）+ M2 多播
远程比本地贵（发现 5）会被再读的远程数据留在本地，不再占表项M3 保留

其他发现（不在这篇的范围，或需要说明）

  • 远程 TLB 缺失多 555–818 ns，取决于发起方到中心 IOMMU 的距离，和数据在哪无关：这是地址转换的问题，这篇以 HDPAT 为前提
  • kernel 边界约 1 µs（mi200，48 个 GPM 统一调度 1,280 ns）：对 T17 里 15–1,700 µs 的 kernel 影响很小
  • mi200 的 HBM 读只到峰值的 31%（MSHR、close page、刷新叠加）；L2 带宽在 16 个 WG 见顶后下降 25–33%，原因还没查清
  • 术语：MGPUSim 的 RDMA 引擎就是每个 GPM 的网络接口；中间每跳只过 switch，不碰 RDMA。64 项当作硬件约束：和 MI250X 两个 GCD 之间的实测相当（每 CU 约 1.4 GB/s，Pearson 2023），也和 AMD NoC2 的 NMU 上限（64 个在途读）一致；上游 MGPUSim 没有这个上限，是我们 fork 加的

W2 的观察

  • 和 T17 一样远程主导：远程读占 66–98%，远程延迟占总延迟 97–100%
  • 覆盖 12 类通信模式：图、稀疏求解、推荐、向量检索、随机读改写、集合通信、排序、FFT 转置、稠密线代、树遍历、非结构网格、多重网格
  • 数据量都偏小（2–267 MB，多数小于整片 wafer 的 L2 96 MB），机制收益可能偏高
  • 小输入下有几个只用到 10–37 个 GPM（WG 太少）；P16 的消融要求每个都用到全部 48 个 GPM

W2 的问题（要先处理）

  • graphtc 崩溃：LDS 归约数组越界读 4 字节，三个配置都在约 1030 s 崩溃；npbis 2 次迭代时 baseline 也崩溃（表里用 1 次迭代）。要修 kernel 或模拟器
  • 地址转换：每 GPM 的 L2 TLB 只覆盖 2 MB；gups、embbag、ivfflat 的正式规模远超这个范围，测到的会是 TLB 而不是数据访问。论文以 HDPAT 为前提，这几个要用理想地址转换或 HDPAT，等决定
  • 移植时发现几个模拟器指令 bug（如 v_cndmask_b32_e64、v_lshlrev_b64），都在 kernel 侧绕开，没改模拟器

假设：远程访问受限于端点，而不是链路

支持的证据

  • 带宽和请求跟踪表项数成正比；放大 L1V 窗口无效，放大跟踪表窗口有效
  • 负载下远程延迟主要是排队，而且能定量解释：L1V 最多 448 个在途、跟踪表只放行 64 个，预测延迟 ≈ (448/64) × 网络接口往返。PagedAttention 平均 4.28 跳，往返约 390 ns，预测 2.73 µs，实测 2.87 µs；MoE 预测 2.4 µs、实测 2.2 µs
  • incast 时 owner 端封顶 113 B/周期
  • Little's law：用满一条链路（768 B/ns，读响应 80 B 上线）在平均 4.3 跳下需要约 3,700 条 line 同时在途；跟踪表只允许 64 条，只能用到约 1.4%；L1V 的 448 个槽位也只够约 9.5%

必须先排除的风险

  • 链路利用率是推算的，模拟器里从没压满过一条链路
  • 结论依赖两个没有硬件出处的参数：跟踪表 64、每跳 32 周期（单程约 36 ns）。参数这么设，端点必然先饱和
  • O2b 放开跟踪表窗口后 GMEAN 只有 1.17，下一个瓶颈是什么还不知道
  • 网络本身是 flit 级模型（32 级流水线、浅缓冲、仲裁、反压），不是理想链路，浅缓冲只会高估拥塞

用满一条链路（768 B/ns）需要多少请求同时在途

按网络接口往返 ≈ 84 + 71.4 ns/跳（由 T14 反推）、读响应在线上占 80 B 计算。现在的两层窗口（448 和 64）差了一到两个数量级。

需要您的意见
