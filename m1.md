# M1 Implementation Spec: L2 Cache Batch Helper + DRAM Batch Helper

## 0. One-Sentence Definition

**M1 reshapes local Enhanced-L1V request traffic in two stages:**

```text
M1a: L2 Cache Batch Helper
  group local cacheline requests before L2 service, probe L2 normally line by line

M1b: DRAM Batch Helper
  take only confirmed L2-miss lines and batch them into row/access-unit-friendly DRAM requests
```

Important wording:

```text
M1 does not bypass L2 correctness.
M1 bypasses the ordinary FIFO L2-miss-to-DRAM path after a line is confirmed to miss in L2.
```

So the safe path is:

```text
Enhanced L1V local miss/request
        |
        v
M1a: L2 Cache Batch Helper
        |
        v
normal cacheline-granular L2 tag probe
        |
        +-- L2 hit  -> respond immediately
        |
        +-- L2 miss -> M1b: DRAM Batch Helper
                            |
                            v
                       local DRAM / HBM
```

---

## 1. Scope

M1 handles only **local memory requests**.

M1 does:

```text
local read request batching before L2 probe
normal per-cacheline L2 tag lookup
L2-hit response demux
L2-miss collection
DRAM row/access-unit-aware batching for confirmed misses
response demux to original L1V/L1 waiters
metrics/counters
```

M1 does not do:

```text
remote RDMA bitmap batching              # M2
owner-side requester fairness            # M3
page migration or replication
coherence protocol redesign
store/atomic batching in v1
speculative issue to DRAM before L2 result
global memory-controller replacement
```

First implementation should batch:

```text
normal local read-only cacheline requests
```

First implementation should bypass M1 for:

```text
stores
atomics
fences
acquire/release/system-scope requests
uncacheable requests
page-faulting requests
remote requests
unknown ordering class
```

---

## 2. Why This M1 Exists

Enhanced L1V exposes many more local memory requests concurrently. FIFO lower-level paths can drain these requests as independent cacheline operations even when the requests are spatially or DRAM-row related.

The resulting problem is not just low L2 hit rate. The problem is poor request shape:

```text
many independent L2 probes
fragmented L2 ingress pressure
fragmented L2 miss queue pressure
fragmented DRAM row/bank service
too many small DRAM reads
high queueing latency despite available spatial locality
```

M1 tries to convert exposed memory-level parallelism into structured batches:

```text
cache-side batch:
  lets related lines enter L2 service together

DRAM-side batch:
  lets only the miss subset reach DRAM in row/access-unit-friendly form
```

Expected positive workloads:

```text
local streaming workloads
large local memory-footprint workloads
bandwidth-bound local workloads
Enhanced-L1V configs with many outstanding local requests
```

Expected weak workloads:

```text
low memory intensity
mostly remote traffic
high L2 hit locality where batching wait hurts
irregular local accesses without row/page locality
```

## 3. Architecture Overview

```text
                 local request only
Enhanced L1V / L1 miss stream
        |
        v
+---------------------------+
| M1a: L2 Cache Batch Helper|
|  - Cache Batch Queue      |
|  - L2 Probe Scheduler     |
|  - Response Demux         |
+-------------+-------------+
              |
              v
        normal L2 tag/data path
              |
      +-------+--------+
      |                |
      v                v
   L2 hit           L2 miss
      |                |
      v                v
respond to       +------------------------+
waiters          | M1b: DRAM Batch Helper |
                 |  - Miss Batch Queue    |
                 |  - Row/Unit Scheduler  |
                 |  - Fill Demux          |
                 +-----------+------------+
                             |
                             v
                         DRAM / HBM
```

M1 has two independent internal queues:

```text
CBQ: Cache Batch Queue
  before L2 probe

DBQ: DRAM Batch Queue
  after L2 miss is known
```

They should have independent enable flags and counters so the paper can run ablations:

```text
baseline
M1a only
M1b only
M1a + M1b
```

## 4. Placement Guide

### 4.1 M1a Placement: Before L2 Probe

Place M1a where local L1/L1V requests enter the L2 cache partition or L2 request port.

The insertion point must satisfy:

```text
1. Request is local, not remote.
2. L2 partition or L2 target is known, or can be computed.
3. Physical address is known.
4. Original requester/waiter context is still available.
5. Request has not yet consumed an L2 tag pipeline slot.
```

Good insertion point:

```text
local L1V miss -> route to local L2 partition -> M1a CBQ -> L2 tag probe
```

Bad insertion point:

```text
before address translation
after L2 miss has already been sent to DRAM
inside DRAM controller only
remote owner path
```

### 4.2 M1b Placement: After L2 Miss

Place M1b where an L2 miss would normally allocate or enqueue a lower-level DRAM/HBM read.

The insertion point must satisfy:

```text
1. L2 tag lookup has completed.
2. The line is confirmed to miss in L2.
3. Fill address and requester/waiter context are known.
4. Request has not yet been sent to DRAM/HBM.
```

Good insertion point:

```text
L2 miss detected -> M1b DBQ -> DRAM/HBM request
```

This is the "bypass" path:

```text
confirmed L2 miss bypasses normal FIFO miss queue and enters M1b DBQ
```

Do not do this in v1:

```text
L1 miss bypasses L2 directly
```

## 5. Address Metadata

M1 needs to decode each local request into cache and DRAM metadata.

Required request fields:

```text
pid
physical_address
cacheline_addr
access_type
ordering_class
requester_l1v_or_cu_id
original transaction / callback / waiter context
arrival_time
sequence_id
```

Derived metadata:

```text
line_addr       = physical_address / CACHELINE_BYTES
page_addr       = physical_address / PAGE_BYTES
line_in_page    = (physical_address % PAGE_BYTES) / CACHELINE_BYTES
l2_partition    = decode_l2_partition(physical_address)
l2_set          = decode_l2_set(physical_address)
mem_partition   = decode_mem_partition(physical_address)
dram_channel    = decode_dram_channel(physical_address)
dram_bank       = decode_dram_bank(physical_address)
dram_row        = decode_dram_row(physical_address)
dram_col        = decode_dram_col(physical_address)
access_unit     = physical_address / DRAM_ACCESS_UNIT_BYTES
```

Default constants if simulator does not expose them:

```text
CACHELINE_BYTES = 64
PAGE_BYTES = 4096
DRAM_ACCESS_UNIT_BYTES = 128
COLUMN_WINDOW_LINES = 8
```

If simulator-specific mapping exists, use the real mapping rather than approximations.

## 6. M1a: L2 Cache Batch Helper

### 6.1 Goal

M1a groups local cacheline requests before L2 probe so related requests are served together by the L2 path.

M1a must preserve:

```text
cacheline-granular L2 tag lookup
cache coherence semantics
per-request response correctness
bounded wait
forward progress
```

M1a is not a cache hit-rate optimization by itself. It is a request-shaping mechanism.

### 6.2 Cache Batch Key

Use a conservative key in v1:

```text
access_type
ordering_class
l2_partition
l2_set
mem_partition
dram_bank
dram_row
column_window_id
```

Where:

```text
column_window_id = floor(dram_col / COLUMN_WINDOW_LINES)
```

Rationale:

```text
l2_partition/l2_set:
  keep cache-side locality compatible with L2 organization

mem_partition/bank/row/window:
  make eventual L2 misses likely to be DRAM-row compatible
```

If the key is too restrictive and batches are too small, relax in this order:

```text
1. remove l2_set, keep l2_partition
2. increase COLUMN_WINDOW_LINES
3. group by page_addr instead of exact dram_row/window
```

Do not start with a very loose key because it may create batches that look large but are not useful for L2/DRAM.

### 6.3 Cache Batch Entry

Go-style structure:

```go
type M1OrderingClass int

const (
    M1Normal M1OrderingClass = iota
    M1Acquire
    M1Release
    M1Atomic
    M1Fence
    M1SystemScope
    M1Uncacheable
)

type M1CacheBatchKey struct {
    AccessType      AccessType
    OrderingClass   M1OrderingClass
    L2Partition     int
    L2Set           int
    MemPartition    int
    DRAMBank        int
    DRAMRow         uint64
    ColumnWindowID  uint64
}

type M1Waiter struct {
    RequestID     uint64
    SrcL1VID      int
    SrcCUID       int
    SrcMSHRID     int
    WarpID        int
    LaneMask      uint64
    SequenceID    uint64
    OriginalReq   interface{}
    ArrivalTime   sim.VTimeInSec
}

type M1CacheBatchEntry struct {
    ID             uint64
    Key            M1CacheBatchKey
    BaseLineAddr   uint64
    LineBitmap     uint64
    LineCount      int
    RequestCount   int

    OldestArrival  sim.VTimeInSec
    NewestArrival  sim.VTimeInSec

    // line offset within this batch window -> waiters
    Waiters        map[int][]M1Waiter

    Draining       bool
}
```

Bitmap width:

```text
Use uint64 for simplicity.
If COLUMN_WINDOW_LINES <= 64, one uint64 is enough.
```

### 6.5 M1a Fill Algorithm

```text
on local request arrival:
  if M1a disabled:
      send request to normal L2 path
      return

  if request is not safe to batch:
      flush conflicting cache batch if needed
      send request to normal L2 path
      record bypass counter
      return

  meta = decode address
  key = build cache batch key

  flush expired cache batches

  if key not found and CBQ full:
      drain oldest eligible cache batch

  entry = find or allocate cache batch
  merge request into entry

  if entry.LineCount >= m1-cache-batch-lines:
      drain entry
```

Safe-to-batch condition:

```text
local request
normal load
cacheable
not atomic
not fence
not acquire/release/system-scope
not page faulting
line offset valid
```

### 6.6 M1a Drain Conditions

Drain a cache batch when:

```text
LineCount >= m1-cache-batch-lines
LineCount >= min_lines and L2 has credit
OldestAge >= max_wait_ns
CBQ occupancy high
CBQ full and new entry needs allocation
simulation drain
conflicting ordered request arrives
```

Drain reasons:

```go
type M1CacheDrainReason int

const (
    M1CacheDrainFull M1CacheDrainReason = iota
    M1CacheDrainMinReady
    M1CacheDrainTimeout
    M1CacheDrainCapacity
    M1CacheDrainConflict
    M1CacheDrainDrain
)
```

### 6.7 M1a L2 Probe Scheduler

When draining a cache batch:

```text
for each line in LineBitmap:
  create a normal cacheline-granular L2 probe
  send probe through existing L2 tag/data path
```

Important:

```text
The batch is not one cache block.
Each bit still maps to one normal cacheline request.
L2 hit/miss is decided per line.
```

Pseudo:

```go
func DrainCacheBatch(batch *M1CacheBatchEntry) {
    batch.Draining = true

    for each lineOffset set in batch.LineBitmap {
        lineReq := MakeL2LineProbe(batch, lineOffset)
        SendToL2(lineReq)
    }
}
```

### 6.8 M1a L2 Hit Handling

If a line hits in L2:

```text
read data through normal L2 path
complete all waiters for that line
record L2-hit-in-batch counter
```

Pseudo:

```go
func OnM1L2Hit(batchID uint64, lineOffset int, data CacheLineData) {
    waiters := batch.Waiters[lineOffset]
    for _, w := range waiters {
        CompleteOriginalRequest(w.OriginalReq, data)
    }
    MarkLineComplete(batchID, lineOffset)
}
```

### 6.9 M1a L2 Miss Handling

If a line misses in L2:

```text
do not send immediately to normal FIFO DRAM path
send miss line to M1b DRAM Batch Helper
record L2-miss-in-batch counter
```

This is the key "bypass" action:

```text
confirmed L2 miss bypasses ordinary FIFO miss path and enters DRAM Batch Helper
```

Pseudo:

```go
func OnM1L2Miss(batchID uint64, lineOffset int, missReq L2MissReq) {
    dramReq := MakeM1DRAMMissLine(batchID, lineOffset, missReq)
    M1b.AddMissLine(dramReq)
}
```

## 7. M1b: DRAM Batch Helper

### 7.1 Goal

M1b receives only confirmed L2-miss lines and groups them by DRAM locality.

It should reduce:

```text
DRAM request queue entries
DRAM command/response pressure where multi-line service is modeled
row-buffer conflicts
response pressure
L2 miss fill latency
```

It must not:

```text
fetch lines that were not requested unless explicitly running an eager/overfetch experiment
drop any miss line
merge lines across incompatible banks/rows/partitions
break fill completion
```

### 7.2 DRAM Batch Key

Use:

```text
mem_partition
dram_channel
dram_bank
dram_row
column_window_id
access_type
```

Optional:

```text
l2_partition
request_priority
```

Column window:

```text
column_window_id = floor(dram_col / DRAM_BATCH_WINDOW_LINES)
```

Initial:

```text
DRAM_BATCH_WINDOW_LINES = 2 or 4 for conservative demand-confirmed batching
```

Use small window first to avoid broad overfetch-like behavior.

### 7.3 DRAM Batch Entry

```go
type M1DRAMBatchKey struct {
    MemPartition   int
    DRAMChannel    int
    DRAMBank       int
    DRAMRow        uint64
    ColumnWindowID uint64
    AccessType     AccessType
}

type M1MissLine struct {
    ParentCacheBatchID uint64
    LineOffsetInCacheBatch int

    PhysicalAddress uint64
    CachelineAddr   uint64
    DRAMCol         uint64

    Waiters         []M1Waiter
    ArrivalTime     sim.VTimeInSec
    SequenceID      uint64
}

type M1DRAMBatchEntry struct {
    ID             uint64
    Key            M1DRAMBatchKey
    BaseCol        uint64
    ColumnBitmap   uint64
    LineCount      int
    MissLines      map[int]M1MissLine

    OldestArrival  sim.VTimeInSec
    NewestArrival  sim.VTimeInSec
    Draining       bool
}
```

### 7.4 M1b Config

```text
-m1-dram-helper-enable
-m1-dram-batch-entries
-m1-dram-batch-lines
-m1-dram-batch-max-wait-ns
-m1-dram-batch-min-lines
-m1-dram-batch-window-lines
-m1-dram-singleton-fallback
-m1-dram-eager-access-unit-mode
```

Initial defaults:

```text
m1-dram-helper-enable = false
m1-dram-batch-entries = 16
m1-dram-batch-lines = 2
m1-dram-batch-max-wait-ns = 25
m1-dram-batch-min-lines = 2
m1-dram-batch-window-lines = 2
m1-dram-singleton-fallback = true
m1-dram-eager-access-unit-mode = false
```

Important:

```text
Start demand-confirmed.
Only batch lines that actually missed in L2.
Do not eager-fetch unrequested neighbors in the default design.
```

### 7.5 M1b Add Miss Algorithm

```text
on confirmed L2 miss line:
  if M1b disabled:
      send normal DRAM read
      return

  decode DRAM metadata
  key = build DRAM batch key

  flush expired DRAM batches

  if key not found and DBQ full:
      drain oldest eligible DRAM batch

  entry = find or allocate DRAM batch
  merge miss line into entry

  if entry.LineCount >= m1-dram-batch-lines:
      drain entry
```

### 7.6 M1b Drain Conditions

Drain DRAM batch when:

```text
LineCount >= m1-dram-batch-lines
OldestAge >= m1-dram-batch-max-wait-ns
DBQ full
memory controller has credit and LineCount >= min_lines
simulation drain
critical line age exceeded
```

### 7.7 M1b Request Emission Modes

Support at least two modes.

#### Mode 1: Demand-Confirmed Multi-Line Request

```text
Only requested L2-miss lines are included.
ColumnBitmap specifies exactly demanded lines.
No overfetch.
```

This is the default paper-safe mode.

#### Mode 2: Singleton Fallback

If batch has only one line:

```text
send normal single-line DRAM read
```

This avoids metadata overhead and wait cost on weak-locality streams.

#### Optional Mode 3: Eager Access-Unit

For comparison with current M1:

```text
one demanded 64B line may fetch full 128B access unit
```

Use only as ablation:

```text
Baseline-64B
Eager-128B
Demand-confirmed M1b
```

Do not make eager mode the default because it can overfetch.

### 7.8 DRAM Response Handling

When DRAM response returns:

```text
for each returned line:
  fill L2 normally
  complete all original waiters for that line
```

If response is per-line:

```text
handle each line independently
```

If response is batched:

```text
demux by ColumnBitmap / cacheline address
```

Correctness requirement:

```text
Every original miss waiter completes exactly once.
Every returned line corresponds to a requested miss line unless eager mode is explicitly enabled.
```

## 8. M1 End-to-End State Machine

### 8.1 Request Lifecycle

```text
Local L1V request arrives
  -> M1a accepts into Cache Batch Entry
  -> M1a drains batch
  -> each line probes L2 normally
       -> hit: complete waiters
       -> miss: send miss line to M1b
  -> M1b accepts miss line into DRAM Batch Entry
  -> M1b drains DRAM batch
  -> DRAM responds
  -> L2 fills line
  -> complete waiters
```

### 8.2 Completion Tracking

A cache batch may partially complete:

```text
line 0: L2 hit, completes early
line 1: L2 miss, waits for DRAM
line 2: L2 hit, completes early
line 3: L2 miss, waits for DRAM
```

Add batch line state:

```go
type M1LineState int

const (
    M1LinePendingProbe M1LineState = iota
    M1LineL2HitDone
    M1LineSentToDRAM
    M1LineDRAMDone
)
```

A cache batch can be freed when:

```text
all bitmap lines are in done states
```

### 8.3 Deadlock Rules

M1 must always have a way forward:

```text
if CBQ full:
  drain oldest or bypass incoming request to normal L2 path

if L2 has no credit:
  do not drain new cache batch, but still accept only if buffer has room

if DBQ full:
  drain oldest DBQ entry or send incoming miss line through normal DRAM path

if response path backpressured:
  stop draining new batches until response capacity returns

if ordered request arrives:
  bypass and optionally flush conflicting entries
```

## 10. Correctness Rules

### 10.1 L2 Correctness

```text
Every line in a cache batch must probe L2 normally.
L2 hit lines must not be sent to DRAM.
L2 miss lines must allocate/fill according to normal cache policy.
Coherence/replacement state remains cacheline-granular.
```

### 10.2 Ordering Correctness

Bypass M1 for:

```text
stores in v1
atomics
fences
acquire/release
system-scope
uncacheable
faulting accesses
```

Conservative rule:

```text
If an ordered request arrives to a page or line with pending M1 batches, flush or bypass those batches before processing ordered request.
```

### 10.3 Completion Correctness

```text
Each original request completes exactly once.
Duplicate waiters to same line all complete.
No waiter is dropped when a batch drains.
Cache batch entry is freed only after all lines are done.
DRAM batch entry is freed only after all miss lines are sent and tracked.
```

### 10.4 No Overfetch by Default

Default M1b should be demand-confirmed:

```text
Only confirmed L2 miss lines are requested from DRAM.
No unrequested neighbor line is fetched unless eager mode is explicitly enabled.
```

## 12. Unit Tests and Synthetic Microbenchmarks

### 12.1 L2 Hit Batch

Input:

```text
4 local reads mapping to same cache batch key
all hit in L2
```

Expected:

```text
one cache batch
4 L2 probes
0 DRAM batch lines
all waiters complete from L2
```

### 12.2 L2 Miss Batch

Input:

```text
4 local reads mapping to same cache batch key
all miss in L2
same DRAM row/window
```

Expected:

```text
one cache batch
4 L2 probes
one DRAM batch with 4 lines
all lines fill and complete
```

### 12.3 Mixed Hit/Miss Batch

Input:

```text
4 local reads in same cache batch
2 hit in L2
2 miss in L2
```

Expected:

```text
hit lines complete early
only 2 miss lines enter DRAM helper
no hit line enters DRAM
```

### 12.4 Different DRAM Rows

Input:

```text
4 local reads same L2 partition but different DRAM rows
```

Expected:

```text
either separate cache batches due to key
or same cache batch but separate DRAM batches after miss
no cross-row DRAM batch
```

### 12.5 Ordered Request Bypass

Input:

```text
normal read enters M1
atomic/fence to same region arrives
```

Expected:

```text
atomic/fence bypasses M1
conflicting pending batch drains or is bypassed conservatively
no deadlock
```

### 12.6 CBQ Full

Input:

```text
more unique keys than cache batch entries
```

Expected:

```text
oldest eligible cache batch drains
or incoming request bypasses
simulation makes progress
capacity drain counter increments
```

### 12.7 DBQ Full

Input:

```text
many L2 misses across many DRAM keys
```

## 15. Success Criteria

M1 is successful if:

```text
cache batch avg lines > 1.5 on local-heavy workloads
DRAM batch avg lines > 1.5 on local-heavy workloads
DRAM read transactions decrease
DRAM read latency decreases
L1V/L2 observed latency decreases
runtime improves on memory-path-critical workloads
overfetch bytes do not increase significantly in demand-confirmed mode
weak-locality workloads do not regress badly
```

Strong result:

```text
DRAM transactions -20% or better
DRAM latency -15% or better
runtime speedup on several local-heavy or LLM-like workloads
no large +50% DRAM bytes failures seen in eager-128B mode
```

Weak result:

```text
batch sizes near 1
latency reduction hidden from runtime
batch wait increases L2 hit latency
DRAM bytes or queue wait increases enough to hurt runtime
```

## 16. Paper Wording

Recommended M1 wording:

```text
M1 is a two-level local-path batch helper. It first groups Enhanced-L1V local requests into cache-side batches and probes L2 normally at cacheline granularity. It then bypasses the ordinary FIFO miss path for the confirmed L2-miss subset and compacts those misses into DRAM row/access-unit-friendly batches.
```

Avoid:

```text
M1 bypasses L2.
M1 changes coherence.
M1 always reduces DRAM command count.
M1 is a memory controller scheduler.
M1 handles remote RDMA batching.
```

Safe claim:

```text
M1 reduces local request fragmentation between Enhanced L1V, L2, and DRAM while preserving L2 cacheline-granular correctness.
```
