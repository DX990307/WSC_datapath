## M3 kernel-boundary invalidation (`-remote-reuse-kernel-invalidate`)

The HPCA paper (Section IV-C) says that the remote lines Remote Reuse keeps in
the requester L2 are invalidated at kernel boundaries. Before this flag the
simulator never did that (with `-magic-memory-copy` the timing model does not
invalidate any cache between kernels, not even L1). The flag (default
`false`, so every existing result is unchanged) adds:

- When a GPM's command processor accepts a kernel launch (before the first
  work-group of the kernel is dispatched), every L2 slice of that GPM drops
  all its remote replica lines (`writeback.Cache.InvalidateRemoteReplicas`).
  Local lines are untouched. Replica lines are never dirty, so nothing is
  written back. This is a flash clear; it takes no simulated time.
- A remote clean fill sent at or before the boundary is dropped when it
  arrives (its data was read before the boundary).
- In the RDMA engine, every remote line still in flight at the boundary is
  marked stale (`rdma.Comp.MarkRemoteReuseKernelBoundary`): it will not fill
  the requester L2, it is closed for M1 merging, and the line's epoch is
  advanced so a read of the new kernel opens a fresh entry (the same mechanism
  a requester write uses).
- Pending writes: a remote write is acknowledged by the owner before the
  wavefront that issued it can finish, so a kernel cannot complete (and the
  next one cannot launch) with an unacknowledged remote write. No extra wait
  is needed.

Metrics (only reported when the flag is on): per L2 slice
`remote_reuse_boundary_invalidations`, `remote_reuse_boundary_lines_invalidated`,
`remote_reuse_boundary_stale_fill_drops`; per RDMA engine
`remote_reuse_kernel_boundaries`, `remote_reuse_boundary_stale_entries`.

The flag has an effect only with `-remote-data-path-enable=true` and
`-remote-data-path-l2-enable=true`. All ISCA'27 configs that contain M3
(`m3`, `m2m3`, `m1m3`, `complete_new`) turn it on.
