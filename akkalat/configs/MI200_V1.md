# mi200 v1: the frozen ISCA'27 baseline

Tag `isca27-mi200-v1` (commit `67f1c03`, user decision 2026-10-16). From
this tag on, `configs/mi200.json` (the `mi200` GPM preset in
`baseline/runner/gpm_preset.go`) is the baseline of every new ISCA'27 run,
and `config_deviation` in `meta.json` is computed against it
(`deviation_base`). `configs/hpca.json` stays the HPCA submission and
`isca27_config.py --base configs/hpca.json` still compares with it. Any
change to a preset value needs the user's approval and a new tag (v2).

Each GPM is 1/4 of an AMD MI250X GCD, set from public specifications
without calibration (no MI200 hardware is available). The sources of every
value are in `gpm_preset.go`; the per-flag notes are the `_` keys of
`mi200.json`.

## Validation (2026-10-15/16, commit 67f1c03)

1. Old configurations are unchanged: hpca fir, hpca matrixtranspose, and
   mi300x fir statistics are identical before and after the change
   (sorted, every row); the hpca matrixtranspose baseline on the servers
   (12,747.6 us) equals the paper's.
2. The effective flags (`-config-out`) match the preset table (unit tests
   and the servers' `config_used.json`).
3. 14 workloads x baseline/m1/m2/m3/Complete (`-max-wg 32768`, spmv 1536)
   and the LLM/CNN operators all finish without deadlock or crash.
4. Deterministic: fir and pagerank, baseline and Complete, run twice give
   identical statistics.
5. Platform characterization (platbench, T14 items): see the deviations
   below for the HBM read bandwidth.
6. Run time: median 48 min per short-segment run; kmeans 11-13 h.

## Intended weaknesses and known deviations from a real MI200

The user chose a configuration slightly weaker than a real MI200, so that
optimizations have room (decisions D20, D21). The paper must state these.

| Item | mi200 v1 | Real MI200 |
|---|---|---|
| Remote data in the requester's L2 | Not cached (baseline) | Cached by default (MTYPE_NC) |
| Remote page-table walks | Go through the central IOMMU | Local translation hardware |
| L1 invalidation at kernel boundaries | None | Done by the runtime |
| Waves per SIMD | 10 | 8 |
| L2 line | 64 B | 128 B (32/64-B sector reads) |
| L2 MSHRs | 32 per slice (256 per GPM); not published by AMD | Unknown |
| HBM read bandwidth | 75 B/cycle, 31% of the 241 B/cycle peak (write about 120, 50%) | Typically 75-85% of peak |
| Data placement | Contiguous page segments, 48 equal shares; work-group segments by CU count (they misalign when CUs per GPM change, e.g. kmeans: 0% remote reads on hpca, 43% on mi200) | Driver and application dependent |

Why the HBM read bandwidth is low (diagnosis 10-15, temporary builds, HBM
read with 28 WGs): 74 B/cycle as configured; 111 with 128 MSHRs per slice;
129 without refresh; 135 with both; 52 without the per-request row hold.
Three limits stack: (1) 32 MSHRs per slice cannot cover the about 200-ns
HBM latency (about 94 would be needed); (2) the DRAM model opens a row for
every 64-B request and closes it after (close page, consecutive lines on
different banks), which caps the rate at one activate per tRRD_S per pseudo
channel, about 138 B/cycle; (3) refresh of one pseudo channel fills the
shared MSHRs and stalls the other pseudo channel too, which amplifies its
cost from about 12% to about 40%. The refresh model itself is correct. The
user kept 32 MSHRs at the freeze (2026-10-16).

## Related simulator behaviour (not part of the preset)

- No cache is invalidated at kernel boundaries, and with
  `-magic-memory-copy` memory copies do not flush either; lines that Remote
  Reuse (m3) keeps in the requester's L2 therefore live across kernels.
  The paper (IV-C) says they are invalidated at kernel boundaries; see
  STATUS "需要用户决定" (P08 a).
- Local Pairing (m1) does not reduce DRAM activates on this memory system:
  the paired 128-B request is split again into 32-B accesses on two pseudo
  channels (activates x1.00, against x0.48-0.59 on hpca).
